# Agentic AI Security RA Gaps

This register follows twelve implementation and scope questions raised by the [[agentic-ai-security-reference-architecture|Agentic AI Security Reference Architecture]]. The revised architecture now states a concrete trust-boundary design for a single agent, including startup confinement, separated policy and credential roles, independent audit, and release admission. Some items below therefore identify missing implementation evidence rather than an omitted architectural decision. The [[google-cloud-agentic-security-profile|Google Cloud Agentic Security Profile]] now provides an Agent Platform control procedure; it does not replace the reference architecture.

Items 1 to 11 compare a boundary outcome with shipped controls as of September 2026. Item 12 places development-time security in the architecture's admission and release path. Product status and scope claims retain their dated sources; the current architecture is the source for the logical component names.

Two gaps turn on a mechanism a vendor shipped under a heading other than security. Entra Agent ID ships lifecycle workflow templates that can transfer an agent's sponsorship when its sponsor leaves, once deployed, and revoke nothing (gap 7), and the AWS Well-Architected Agentic AI Lens puts consumption anomaly detection in its cost pillar and routes the alert to the team that owns the agent, while the same lens's security pillar detects cross-agent anomalies over message rates and topology and over no cost metric (gap 10). A control filed under governance or cost reaches the operator who reads that pillar and stays invisible to the security review that would look for it.

## Implementation and scope findings

### 1. Compartmentalized LLM (CaMeL) reference pattern

Privilege-based data flow control has one documented implementation and no vendor-neutral one. FIDES ships in Microsoft Agent Framework's `agent-framework-core` package from Python 1.3.0 under `agent_framework.security`, carrying an integrity and a confidentiality label on every content item, most-restrictive-wins propagation through tool calls, a policy check before each sink, and a tool-free quarantined model the main model reaches only through a variable reference.[^fides-ra] Microsoft ships it experimental and Python-only, and its documented limitations leave labels opt-in per data source, so a tool nobody labels is governed by the run's default label. Enforcement sits in tool-call middleware rather than in an interpreter over a generated program, which is the [[camel-pattern|CaMeL]] enforcement point and has no maintained implementation: the paper's own code is published as a research artifact its authors disclaim as unmaintained and possibly insecure.[^camel-artifact-ra]

### 2. Cross-tenant MCP server signing

Two signing paths reach MCP servers: a distributor signs the servers it rebuilds, and some authors attest their own npm packages, a path whose fit to the architecture's requirement is open. MCP revision 2026-07-28 states that the identity a server returns in `serverInfo` is self-reported and directs clients not to rest security decisions on it, and the official MCP Registry, in preview, verifies the publisher's DNS or GitHub namespace and delegates code scanning to package registries and downstream aggregators.[^mcp-signing-ra] Docker builds and signs the local servers in its MCP catalog, and `docker mcp gateway run --verify-signatures` checks an image against one Docker-held key compiled into the gateway binary and one Docker-controlled signature repository, failing closed where it finds no signature.[^docker-mcp-sign-ra] A tenant that verifies a server through Docker's gate therefore learns that Docker built it and nothing about who wrote it. A package registry carries the author's own attestation for some servers: the npm release 2026.8.31 of the MCP project's reference filesystem server carries a SLSA provenance attestation that the release workflow of the server's own repository signed through Sigstore, binding the npm package name and version to the tarball's digest, and `npm audit signatures` verifies such attestations.[^npm-prov-ra] Three limits remain on that path:

- The attestation names the npm package, not the `serverInfo` identity the server reports over the protocol.[^npm-prov-ra]
- It exists only where the publisher builds on a cloud-hosted GitHub Actions or GitLab CI/CD runner and publishes with provenance.[^npm-prov-ra]
- Provenance "does not guarantee the package has no malicious code", in npm's own documentation.[^npm-prov-ra]

Whether a check of that attestation before each server starts meets the architecture's name-to-binary requirement is open, and the two published designs for author-held attestation within the protocol or its registry are research proposals.[^mcp-attest-research-ra]

### 3. Multi-agent failure containment

The containment step ships and the detection that would trigger it does not in the products reviewed here. Copilot Studio's quarantine API marks an agent quarantined and restricts its availability and its interactions, and the Microsoft 365 admin center blocks an agent across the organization.[^ms-agent-quarantine-ra] Cascading failures and rogue agents each have a named conventional-security equivalent now. The Microsoft Agent Governance Toolkit v1.1 answers cascading failures with the circuit-breaker pattern plus rate limiting, and rogue agents with a per-agent behaviour monitor that quarantines an agent exceeding its thresholds, by the toolkit's own assessment of its own patterns.[^agt-crosswalk-ra] The generally available products surveyed here document no cross-agent cascade rollup with numeric thresholds. Microsoft Defender's agent detections stay in public preview and each one names a single-agent threat class.[^defender-agent-ra] Quarantine is an administrator's action downstream of a flag rather than propagation from a detection. The graph-walk monitors [[multi-agent-runtime-security|Multi-Agent Runtime Security]] tracks (SentinelAgent, TraceAegis) remain at v1 with no released code, and Oktsec supplies per-agent throttling and default-deny inter-agent ACLs with no cascade rollup above them.

### 4. AI-BOM operationalization

Generating an AI-BOM is automated, but the surveyed tools do not establish an admission gate that acts on one. cdxgen ships a dedicated `aibom` command that takes Hugging Face package URLs, Modelfiles and GGUF artifacts, emits CycloneDX 1.7 and submits the result to Dependency-Track, and Anchore Syft catalogues GGUF and SafeTensors components.[^aibom-tooling-ra] The architecture's [[agentic-ai-security-reference-architecture#admission-and-startup|release admission flow]] checks an approved artifact and configuration before startup, but does not claim that an AI-BOM is reconciled against advisories or exploitation status. Anchore lists vulnerability scanning of AI artifacts as unsupported. A pipeline using that scanner alone can inventory a model without evaluating AI-specific vulnerability records.[^aibom-tooling-ra] The disclosure norm gained a normative anchor without an operational layer, because CISA and the G7 published *Software Bill of Materials for AI — Minimum Elements* on 2026-05-12 and that guidance states that its elements are not mandatory, that implementation detail is outside its scope, and that an SBOM for AI by itself is insufficient until it connects to vulnerability scanning and advisory tooling.[^g7-aisbom-ra] A 2026 measurement generated roughly 97,500 AI-BOM artifacts from 2,942,466 public Hugging Face model records and scored mean completeness at 54.31 out of 100. That method does not establish what individual publishers supply with their models.[^aibom-completeness-ra] No AI-specific exploitability profile appears in the documents read, since the OWASP CycloneDX authoritative guide to AI/ML-BOM of June 2026 does not mention VEX and the G7 and CISA guidance's nearest element links to external vulnerability databases instead of asserting exploitability.[^aibom-vex-ra] See [[ai-bom|AI-BOM: AI Bill of Materials]].

### 5. Transitive egress constraint on allowlisted destinations

The [[agentic-ai-security-reference-architecture#boundary-inventory|boundary inventory]] explicitly names transitive reach as a residual question: filtering at the agent's interface says nothing by itself about what an allowlisted destination can reach. Internal package proxies, artifact caches, and build services routinely hold broad internet access, which turns an allowlist entry into a relay reachable by SSRF ([[openai-hugging-face-agent-incident|OpenAI–Hugging Face incident]], 2026). No listed reference implementation emits evidence that an allowed service is itself constrained, and the one tool that answers the question is a cloud-network analyser the operator runs separately: AWS Network Access Analyzer verifies from configuration whether a resource holds a path to an internet gateway and whether a firewall or NAT gateway sits on every such path, for resources inside that one cloud's VPCs and for nothing else.[^naa-ra] The reference deployment has one agent; its multi-agent adaptation calls for an authenticated broker. Shared writable build infrastructure remains a possible inter-run channel outside that broker. The gap is wider than relaying: a permitted general-purpose host serves content directly, so an allowlist entry for `github.com` or `pypi.org` admits whatever those hosts publish ([[kimi-k3-sandbox-escape|Kimi K3]], 2026). Cataloguing what each allowlisted destination serves is unaddressed by every reference implementation listed, and the enforcement point such a catalogue would need is absent as well: Docker Sandboxes carries host, domain and port granularity in its network rules and no path or method qualifier, although the proxy enforcing them already terminates TLS, and Anthropic documents domain fronting past a hostname-only allow decision as the operator's own residual risk.[^egress-granularity-ra]

### 6. Control initialization order

The [[agentic-ai-security-reference-architecture#admission-and-startup|startup flow]] now requires confinement before the runtime reads task data or tool configuration and a failed start to block the session. The unresolved question is whether each harness actually establishes that order. Agentic coding harnesses read workspace-supplied configuration during startup, and [[gemini-cli-workspace-trust-rce|GHSA-wpqr-6v78-jr5g]] shows that step preceding sandbox initialization, which puts the resulting execution outside the claimed sandbox.[^gemini-init] [[claude-code|Claude Code]]'s documentation states the ordering for repository content: a `claude -p` or Agent SDK run in a folder never trusted uses the repository's settings-file hooks, `env` block and `apiKeyHelper` and connects its `.mcp.json` servers without asking, and MCP servers and command hooks run unconstrained on the host, outside the per-command sandbox.[^cc-order-ra] For the other harnesses the wiki tracks, no vendor documentation the wiki holds states the ordering, so the property cannot currently be assessed for those harnesses even where an operator wants to. Two developments narrow the gap without closing it. Gemini CLI's trusted-folders documentation enumerates the workspace-supplied inputs that trust gates — project settings, `.env` files, extensions, MCP connections, memory loading and custom commands — and leaves the position of that check relative to sandbox initialization unstated, and NVIDIA's January 2026 sandboxing guidance records that hooks and MCP initialization functions often run outside the sandbox, answering it with OS-level write protection of configuration paths rather than with an ordering requirement.[^harness-init-ra] Ordering fixes also ship silently: `cursor-agent` moved its worktree setup command behind the workspace-trust prompt in build 2026.07.23-e383d2b with neither an advisory nor a changelog entry, so an operator learns the property retrospectively from third-party disclosure.[^cursor-worktree-ra]

### 7. Identity binding when humans are decommissioned

Ownership reassignment on a leaver event has a reference implementation. Entra Agent ID ships two lifecycle workflow templates that notify managers and cosponsors and can transfer sponsorship when a sponsor changes role or leaves. An administrator must deploy them, and the identity-governance overview names the departing sponsor's manager as the party sponsorship passes to.[^entra-sponsor-ra] Credential rotation and revocation do not travel with the transfer: every disabling, deleting and token-revoking task in that leaver catalogue is scoped to a user object, and disabling an agent stays a sponsor's manual decision in the My Account portal.[^entra-sponsor-ra] Ownership attestation, orphaned-identity detection and automatic revocation are three controls. The products reviewed here document no automatic agent revocation when its human owner leaves. [[okta-for-ai-agents|Okta for AI Agents]], generally available since 2026-04-29, ships shadow-agent discovery, access reviews and an operator-invoked deactivation switch, and the shadow-agent products name a departing employee's agents without revoking them.[^okta-ga-ra] The Cloud Security Alliance puts the unowned population at 8% of enterprise identities, which hold no HR-system ownership linkage after their creator departs.[^csa-nhi-vacuum-ra]

### 8. Shared services above the isolation boundary

A sandbox divides agent processes; it does not divide the services they share. The [[owasp-ai-exchange|OWASP AI Exchange]] names shared inference, credential, and policy services as implicit cross-agent channels.[^aix-sandbox-ra] The revised [[agentic-ai-security-reference-architecture#logical-components-and-trust-boundaries|architecture]] explicitly names a model gateway, policy service, credential broker, and evidence store. It separates the policy decision from credential dispensing, keeps the credential outside the runtime, sends mediator events to an evidence store the agent cannot change, and requires both denied and successful actions to carry a task identifier. Its [[agentic-ai-security-reference-architecture#boundary-contracts-and-verification|boundary tests]] include a direct-provider call refusal, an approval replay refusal, and a log-suppression refusal. These are real controls for one task, not a claim that the shared services are partitioned per agent.

The residual risk is cross-run influence inside a shared service. A policy rule, credential-broker configuration, model route, or evidence-store permission changed for one tenant or agent could affect another. A reviewer should test scope isolation and administrative change authority at each shared component, including an attempt to read another agent's decision or suppress its record. The [Exchange's monitoring control](https://owaspai.org/go/monitoruse/) specifies a tamper-evident action trail outside the agent's control, and its [testing guidance](https://owaspai.org/go/testing/) tests that the agent cannot suppress or alter logs.[^aix-monitoruse-ra][^aix-testing-ra] An individual IETF credential-broker draft goes further by separating audit, policy decision, and credential dispensing, but it is a proposal rather than a deployed standard.[^cb4a-ra] AgentCore Policy's engine can serve multiple gateways, so shared policy scope is a concrete product question.[^agentcore-policy-ra]

The present reference deployment's independent audit and separated roles narrow this gap. They do not establish tenant partitioning for a vendor-operated inference endpoint or for policy and broker internals the customer cannot test. Supplier boundary and administrative evidence must name the separation actually implemented. Gap 5 concerns a permitted destination's onward network reach; this item concerns influence and visibility among tasks that use a mandatory shared service.

### 9. Message-fabric integrity below the transport

The revised architecture's multi-agent adaptation requires an authenticated broker, schema validation and delegation without authority expansion. Its single-agent reference flow does not itself prove those controls for a multi-agent deployment. The Exchange states that peer-agent, tool, and orchestrator messages are untrusted input including inside single-agent tool loops, and that emergent collective behaviour can violate policy even where each agent complies in isolation.[^aix-amsm-ra] Signed delegation tokens with full-chain validation and scope non-expansion are the named control, and single-hop delegation is the part of it that ships: MCP's Enterprise-Managed Authorization extension has the enterprise identity provider mint an identity-assertion grant that the resource's own authorization server validates, and the extension defines one hop with no chained derivation.[^mcp-ema-ra] Full-chain validation with scope non-expansion still lacks an identified generally available reference implementation in the sources read. [[a2a-protocol|A2A]] through v1.0.0 establishes identity at the transport layer and assigns authorization logic to the agent's own implementation, defining no delegation token and no chain validation, and MCP revision 2026-07-28 widened `structuredContent` to any JSON value, leaves the output schema optional, and sets client-side validation of a structured result at SHOULD.[^a2a-authz-ra][^mcp-schema-ra] The chain-verification mechanism itself exists as an individual IETF draft, which requires that a derived token grant no broader authority than its parent and that any enforcement point holding the trust anchor verify the whole chain without a network call.[^attenuating-tokens-ra] See [[agent-message-structure-manipulation|Agent Message Structure Manipulation]].

### 10. Fleet-wide consumption correlation

Per-agent resource and gateway ceilings bound one agent at a time, while the revised reference deployment records no fleet-wide consumption detector. The Exchange requires monitoring consumption across the fleet for correlated spikes and slow exhaustion attacks, which detects a campaign spread thinly enough that no single agent breaches its own cap.[^aix-limitresources-ra] The architecture's evidence store makes a fleet detector possible, but the deployment contract does not specify one. One reference implementation specifies the detection and files it under cost: the AWS Well-Architected Agentic AI Lens of June 2026 baselines token consumption, tool-invocation frequency, memory growth and cost per completed task, sets the multi-agent workflow escalation threshold at twice the historical average, and routes the alert to the team that owns the agent.[^awslens-cost-ra] The same lens's security pillar detects coordination anomalies across agents over message rates, workflow frequencies, response latencies, per-pair error rates and graph topology, and over no consumption metric.[^awslens-sec-ra] [[mitre-atlas|MITRE ATLAS]] added an agentic resource consumption sub-technique under cost harvesting in March 2026 and attached no mitigation to it.[^atlas-arc-ra] A denial-of-wallet campaign shows what the omission costs: the service stays available and every response is correct, so an availability monitor stays silent and the only signal is cost per unit of completed work.[^aix-exhaustion-ra]

### 11. Phantom-step detection on the orchestrator

The revised architecture records proposals, policy decisions, approvals and API outcomes outside the agent, allowing reconstruction of the refund path. It does not claim that an independent plan was compared with every executed step. The [[owasp-ai-exchange|OWASP AI Exchange]] calls for an external tamper-evident workflow log and reconciliation of executed actions against it to expose unplanned steps.[^aix-oversight-ra] The comparison is what makes the log tamper-evidence useful: a log the orchestrator alone writes and alone reads records a compromised orchestrator's version of events. The artifact is available off the shelf from a component outside the reference deployment, since a durable-execution engine holds an ordered event history in a service the agent process does not write, and Temporal documents its OpenAI Agents SDK integration as running the agent loop, tool selection and handoffs inside a workflow.[^temporal-agents-ra] The comparison stays absent even there: Temporal's determinism check compares the commands a replay of the workflow code emits against the recorded history, and the same integration runs every model call as an activity outside that replay path, so a step the agent invented replays as recorded fact.[^temporal-ra][^temporal-agents-ra] Plan adherence is a measured quantity in the 2026 literature rather than an enforced one: one study analyses plan compliance across 21,120 agent trajectories on two software-engineering benchmarks, and a second frames self-reported divergence between plan and action as deception.[^plan-divergence-ra]

### 12. Development security in admission and release

The revised architecture puts development security at the [[agentic-ai-security-reference-architecture#admission-and-startup|admission and startup]] boundary. Engineering builds a versioned image and manifest, reviews the design, checks first-party changes, tests the assembled agent, and makes a release decision before the runtime starts. The [[agentic-ai-security-cmm-d8-supply-chain|D8 Engineering and Supply Assurance]] criteria grade those outcomes. A local coding agent also must be confined before it reads repository configuration, and the repository owner supplies configuration and dependency admission evidence. This makes development security part of the release chain rather than a seventh runtime component.

The [[owasp-ai-exchange|OWASP AI Exchange]] identifies sensitive training and test data, model parameters, configuration, and source code as development-environment assets.[^aix-devtime-ra] Its `DEV SECURITY` control calls for access control, monitoring and integrity checks there. `SEGREGATE DATA` restricts who can reach development datasets. `CONF COMPUTE` addresses data and parameters while in use. `SUPPLY CHAIN MANAGE` covers supplied components.[^aix-devsecurity-ra][^aix-devcontrols-ra] These map to the revised design as follows:

- The identity service and retrieval or development-data mediator establish who may reach each asset. A source entitlement check for production retrieval does not, by itself, partition training or test stores.
- The confined engineering runner and permitted network routes bound code and external components that run during development. The startup-order test remains important for local harnesses.
- Release admission and the D8 design, implementation, test and release records connect checked source and configuration to the promoted version. The evidence store preserves changes and test outcomes outside the agent process.
- Supplier-held model training, hosted inference and component builds require supplier evidence. The customer tests its integration and records any inaccessible material step as an assessment limit.

[NIST SP 800-218A](https://csrc.nist.gov/pubs/sp/800/218/a/final) separately calls for monitoring development environments and protecting training, testing, tuning data, model weights and configuration.[^218a-devenv-ra] The architecture's single-agent refund example does not prescribe a collaborative-training topology. `FEDERATED LEARNING` is a training design option, applicable only where training data is distributed across organizations, and it creates its own client-to-aggregator and poisoning boundaries.[^aix-devcontrols-ra] Its absence from the reference deployment is a scope limit, not a missing universal control. The customer's release record should identify the supplier-held training evidence when a produced model in scope uses that topology.

The AWS Well-Architected Agentic AI Lens names no development-environment capability in its agent-specific security set and instructs readers to use it alongside the base framework.[^awslens-scope-ra] The base framework's application-security section does cover design, build, test and dependency management.[^aws-appsec-ra] That division supports treating development security as a release-path obligation without inventing a separate agent runtime service.
