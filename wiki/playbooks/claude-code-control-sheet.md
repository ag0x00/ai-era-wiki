# Claude Code Control Sheet

The configurable controls of [[claude-code|Claude Code]], Anthropic's agentic coding harness, map to the criteria of the [[agentic-ai-security-cmm-2026|Agentic AI Security Capability Maturity Model]] (AAI-S CMM) in one section per domain. Each row pairs a criterion, by name where its deep dive names it and otherwise quoted as the deep dive words it, with the setting key, managed-only key, hook event, CLI flag or environment variable that implements it, the evidence an assessor collects and the harness's coverage, for the engineer who configures the control and the assessor who grades it. Each harness statement is footnoted to the section of Anthropic's Claude Code documentation, as published on 2026-09-24 or 2026-09-25, that states it.

The harness is strongest in the control domain, where a managed permission policy the session cannot widen is the decision point D3 L3 names, and weakest in identity, where a local session acts as the developer. With the organization's own records counted as present, Claude Code's controls reach L2 at most in any domain.

## Scope

### Surfaces and settings sources

The sheet covers six surface groups:

- **Local sessions.** The terminal CLI, the VS Code and JetBrains extensions, and the Desktop app's Code tab with Local selected run on the developer's machine,[^web-intro] and Desktop reads the CLI's settings files.[^desk-modes]
- **Desktop SSH and WSL sessions.** The SSH environment runs Claude Code on a remote machine the user connects to over SSH, under that host's managed settings file, and on Windows the WSL environment runs it in a WSL 2 distribution on the same machine.[^desk-env][^desk-managed] WSL reads only `/etc/claude-code` unless an administrator-only Windows source sets `wslInheritsWindowsSettings: true`, and Desktop turns WSL sessions off by default on devices it detects as organization-managed.[^as-wsl]
- **Non-interactive runs.** `claude -p` and the Agent SDK run without the interactive interface, which is all the Desktop app offers.[^desk-cli]
- **Cloud sessions.** Started from claude.ai/code, the Claude mobile app, the Desktop app with Cloud selected, `claude --cloud`, a routine or a Claude Tag channel, they share one set of environments, hosted by Anthropic or self-hosted, the latter in public beta on Team and Enterprise plans.[^web-intro][^web-env][^shi-beta]
- **CI integrations.** The Claude Code GitHub Action and GitLab CI/CD.
- **Remote Control.** A browser or the mobile app steers a session that keeps running on the user's machine.[^rc-vs]

The Desktop app's Cowork tab is graded under each deep dive's desktop-agent row.

Settings reach a session from ranked scopes: managed policy, the command line (`--settings`), then local project, shared project and user files. List keys merge across scopes, so a lower scope can add entries to a managed list it cannot override.[^set-prec] Managed policy reaches a device from four sources, highest priority first:[^as-deliver]

- Server-managed settings, from the claude.ai admin console or a Claude apps gateway.
- A macOS plist in the `com.anthropic.claudecode` domain, or Windows policy under `HKLM\SOFTWARE\Policies\ClaudeCode`.
- The file-based `managed-settings.json`, at `/etc/claude-code/` on Linux and WSL.
- The Windows user registry under `HKCU\SOFTWARE\Policies\ClaudeCode`, writable without elevation.

Under the default `managedSourcesBehavior`, `"first-wins"`, Claude Code applies the highest-ranked source delivering a policy key, apart from a few keys it reads from every admin source.[^ms-combine]

### Deployment shapes

[[generative-coding-deployment-shape-2026|Generative Coding Deployment Shapes]] defines the five shapes, and a row applies to every shape unless its bullets name one. The surface groups fall under them as follows:

| Shape | Surfaces | Settings that reach the session | Identity the session acts under |
|---|---|---|---|
| Interactive local | Local sessions, Desktop SSH and WSL sessions, Remote Control | Every scope, and managed policy from the host's own sources | The developer's account |
| Sandboxed autonomous local | The same surfaces with prompts suppressed, and non-interactive runs on a workstation | As interactive local, with the `sandbox` keys load-bearing | The developer's account |
| Delegated cloud | Cloud sessions | Server-managed settings, the repository's `.claude/settings.json` in a one-repository session, and a self-hosted runner image's managed file[^set-cloud] | The developer's account, or the organization's shared identity under Claude Tag[^tag] |
| CI-runner agent | CI integrations, and non-interactive runs on a build runner | The workflow's `settings` and `claude_args` inputs, and a managed file on the runner[^gha-params][^dc-policy] | A Console service account through federation, or a stored token[^gha-wif] |
| Fleet / parallel | Many of the above at once | The union of the above | Per shape |

Workload identity federation credentials do not trigger the server-managed settings fetch, so a CI run on federation takes its policy from the workflow or the runner.[^sms-platform]

### Provider routes

The route to the model decides which administrative channels exist:[^fa-admin]

- **Claude for Teams or Enterprise sign-in.** The Owner or Primary Owner role sets server-managed settings, and settings-change audit events come through the compliance API or audit log export.[^sms-req][^sms-audit] Enterprise sessions start in Manual mode, and Team sessions in a terminal or the VS Code extension in auto mode, from v2.1.228 on macOS, Linux and WSL and v2.1.233 on native Windows.[^pm-start] The extension's own `claudeCode.initialPermissionMode` outranks a managed `permissions.defaultMode`.[^pm-switch]
- **Claude Console API key.** Server-managed settings apply where the key belongs to a Team or Enterprise organization.[^fa-summary]
- **Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry and Claude Platform on AWS.** Server-managed settings and the analytics dashboard are unavailable, so policy arrives through device management, a managed file or a Claude apps gateway.[^fa-admin] Access is restricted through the provider's IAM or RBAC policies,[^tpi-compare] which `forceLoginOrgUUID` does not reach,[^as-enforce] and metrics and error reports to Anthropic are off by default.[^du-provider]
- **Claude apps gateway.** A self-hosted OIDC gateway built into the `claude` binary delivers managed settings per IdP group and stamps telemetry with the IdP identity, and it has no sign-in flow for unattended pipelines, so CI authenticates to the provider directly.[^gw-why][^gw-ci]
- **Another LLM gateway set through `ANTHROPIC_BASE_URL`.** Server-managed settings and Remote Control are off, so policy arrives through device management and OpenTelemetry export carries D7.[^fa-admin][^sms-platform]

Cloud sessions and Remote Control need a claude.ai account, so neither exists on a Console API key or a third-party provider.[^mob-signin]

## Instructions for use

### Reading a row

A criterion is one bullet in a deep dive's level detail list, or one item of a level statement where the deep dive grades that level from its statement, and alternatives satisfying one criterion, such as the three assurance routes D1-ASSURE accepts at [[agentic-ai-security-cmm-d1-governance|D1]] L5, count once. The coverage column takes four values:

- **Native**: Claude Code enforces the control, or emits the evidence, once the row's setting is in place.
- **Partial**: Claude Code covers part of the criterion, and a bullet names the rest and its supplier: an organization record, a hook the organization writes, or a control outside the harness.
- **External**: the control sits outside Claude Code, and the row names any input Claude Code supplies to it.
- **Not applicable**: the harness holds no instance of what the criterion governs in the shapes the bullets name.

Coverage grades the harness, and a natively covered criterion is still not met on a device without the setting. Bullets follow the table's levels in ascending order, with a whole-domain bullet, such as a dependency cap, last.

OpenTelemetry events appear under their short names, such as `tool_decision`, which Claude Code emits with a `claude_code.` prefix, and span and metric names appear in full. A named environment variable reaches every session through the managed `env` block,[^env-set] and sandbox keys sit under `sandbox`, `sandbox.network` or `sandbox.filesystem`, whether or not the text writes the prefix.[^sbx-enforce][^sbx-network][^sbx-fs]

### Columns each role adds

- **The platform engineer** copies each domain table into the assessment workbook and adds an *As deployed* column: the value set, its scope and the device's Claude Code version, with one entry per policy variant, keyed by its `managed_settings.resolved_sha256` digest, for a fleet.
- **The assessor** adds a *Verdict* column: the CMM verdict, its assurance class and, for inspected or attested evidence, the artifact record. A criterion is met only where every policy variant in the assessed scope meets it, because each deep dive counts two configurations as two agents and holds a criterion over every agent to each one.

### Verdicts and evidence

The deep dives grade each criterion met, not met, not applicable or unanswerable, and [[agentic-ai-security-cmm-measurement-protocol|CMM: Measurement Protocol (Assessor's Handbook)]] records an assurance class beside each met or not-met verdict:

- **Tested**: the organization or the assessor exercised the control, such as by attempting a denied tool call.
- **Inspected**: vendor tooling the customer can reach, such as `/status`, `claude doctor` or the fleet's OpenTelemetry events, or a record the organization keeps, such as a register or a runbook, shows the control's state in this deployment.
- **Attested**: a vendor document whose own scope names the control, such as a Claude Code documentation page, which reads the same in every deployment.

An inspected or attested verdict names its artifact by issuer, title and version, date, service and tenant, and period covered. Grading is cumulative, an unanswerable criterion holds its level and those above open, and a not-applicable verdict leaves the denominator with its reason in the strategic-rationale field. Every cited behavior belongs to a release, so the assessment names the harness version beside each artifact, and a device below a footnoted version floor lacks the control.

An external row is graded on the external control's evidence, recorded with the input Claude Code supplied and the harness version, and is not met where no external control operates, because the instance exists and nothing controls it. An instance inside Anthropic's service, such as the request and response screening, is graded on Anthropic's evidence instead, the deployment's own events or documentation whose scope names the control, and where neither exists on a test the customer runs, such as an attack presented again in each variant form for canonicalization. It is unanswerable only where no such test can be run.

## Domain summary

The harness ceiling is the highest level at which every mapped criterion can be met from Claude Code's own controls, counting hooks the organization writes as the harness's and the organization's records at that level, such as registers, runbooks and matrices, as present. *Ceiling set by* names up to two of the lowest criteria that need a control outside the harness, the domain sections name any others, and the last column names that control.

|---|---|---|---|---|

| D2 Identity and Authorization | 11 of 33 | L1 local, L2 cloud and CI | D2-IDENTITY locally, D2-DELEGATE-EXCHANGE in cloud and CI | A workload identity per agent that the called services verify |
| D3 Control and Least-Agency | 28 of 38 | L2 | D3-RIGHTS, D3-MEDIATE-FAILCLOSED | An approval service naming the approver per action class |
| [[agentic-ai-security-cmm-d4-runtime-guardrails\|D4]] Runtime and Guardrails | 23 of 29 | L2 | D4-SANDBOX-CLEAN, D4-SANDBOX-LIMITS | A container or VM per task that the platform destroys at task end and caps in CPU, memory and wall-clock time |

| [[agentic-ai-security-cmm-d9-operations\|D9]] Operations and Human Factors | 25 of 47 | L1 on a Fable, Opus 5.5 or Opus 5 model or in auto mode, L2 otherwise | D9-GUARD-RUNBOOK there, D9-HIGHRISK-SOD otherwise | Anthropic's statement of its classifiers' failure behavior, then an approval service that routes each critical action to two approvers and keeps a tamper-evident record |

Five ceilings need their basis stated:

- **D1's L2 rests on records alone.** No D1 L2 criterion bears on the harness, so the ceiling holds where the organization's accountable role, AI policy, risk-tier scheme and RACI exist, graded once for the program, and each deployment's register entry names its accountable person and its scored tier.
- **D2 decides two other domains.** Rules DR-001 and DR-002 cap egress and observability at D2's raw score, so a local estate whose sessions act as the developer reports both at L1 effective whatever it spends on proxies and collectors, and identity is the first control to add, as a CI run on federation with a custom GitHub App lifts all three to L2.
- **D3 stops at L2 on two criteria.** D3-RIGHTS needs an approver the session holder does not choose, and D3-MEDIATE-FAILCLOSED fails as written, because Claude Code starts when its managed source is absent, pending the decision in [#342](https://github.com/ag0x00/ai-era/issues/342) on whether delivery assurance can stand in.
- **[[agentic-ai-security-cmm-d5-egress-network|D5]]'s L2 needs every egress leg allowlisted.** D5-ALLOW fails an agent with any component whose connections bypass the list, the model client included. Claude Code allowlists shell commands through the sandbox, the fetch tool through `WebFetch` rules, remote MCP servers by `serverUrl` and the Desktop Browser pane by site, and only a whole-process boundary, such as the sandbox runtime or a dev container, confines the model connection, hooks and stdio MCP servers, so without one a host or network allowlist carries those legs, or D5 stays at L1.[^se-bash]
- **D9's L2 turns on Anthropic's documentation.** D9-GUARD-RUNBOOK reads a guardrail the vendor runs from the vendor's documentation or a customer test, and the pages read state no failure behavior for Anthropic's safety classifiers, which screen requests to Fable, Opus 5.5 and Opus 5 models, or for the server-side probe that auto mode runs over incoming tool results, while no customer test can make either fail.[^mc-fallback][^pm-classifier] D9's vendor-held rule leaves such a criterion unanswerable, so a deployment on those models or in auto mode stops at D9 L1 until Anthropic documents that behavior.

### Coding-tool evidence items

[[agentic-ai-security-cmm-2026|Agentic AI Security Capability Maturity Model]] adds four evidence items for a coding tool at L3 and above, drawn from [[ai-coding-agent-governance|AI Coding Agent Governance]]. The sheet grades each against the criterion that names its object, and the domain rows carry the controls:

| Evidence item | Criterion that grades it | Coverage |
|---|---|---|
| Agent rules-file integrity | D6-INSTRUCT, and D8-VERIFY-INSTRUCT | partial |
| IDE extension provenance | D6-EXTEND for an editor extension that indexes content for the harness, and D8-ABILITY-SOURCE, D8-ABILITY-SCAN and D8-VERIFY for one the harness loads to extend the agent | partial |
| Typosquat / dependency-hijack defense | D8-DEPS-SCAN, D8-DEPS-LOCK and D8-DEPS-INSTALL | partial |
| Destructive-action classification | D3-TIER-DESTRUCT, beside D3-TIER and D3-RIGHTS | partial |

D8 counts an editor extension the harness loads to extend the agent among its abilities, which D8-ABILITY-SOURCE, D8-ABILITY-SCAN and D8-VERIFY read, and D6-EXTEND reads one that indexes content for the harness, because such an extension adds a source to the corpus. A Claude Code plugin, which adds its skills, agents, hooks and MCP servers to the harness, is an ability, and the D8 rows grade it.[^pl-install]

## 1 — D1 Governance and Accountability

[[agentic-ai-security-cmm-d1-governance|D1]] fixes who is accountable for agent behavior and on what record, and its D1-HARNESS family of five criteria grades the coding harness's configuration. The sheet maps 11 of D1's 34 criteria, all at L3. D1-SHADOW and D1-SHADOW-REAP are organization criteria: the assessment grades each once for the program and reports it beside the deployment matrices, and either one not met or unanswerable holds every deployment at L2 in D1. The other nine are graded per deployment. The 23 left unmapped are records no harness setting produces:

- **Organization records, graded once for the program.** The accountable role, the AI policy, the risk-tier scheme and the RACI at L2, the risk body, its cadence, the gate rule and the publication rule at L3, the board's metrics report and the standards crosswalk at L4, the board's attestation of four quarters' reports, the risk body's year of minutes and the crosswalk's quarterly revisions at L5, and the standards contribution and published governance artifact at L5+.
- **Deployment records.** The register entry with its accountable person and scored tier at L2, the production approval and its conditions, the technical-detail inventory entries and the review of each publication at L3, the readiness assessment at L4 and third-party assurance at L5.

| Level | Criterion | Claude Code control | Evidence | Coverage |
|---|---|---|---|---|
| L3 | D1-SHADOW (organization) | None. `forceLoginMethod` and `forceLoginOrgUUID` restrict the login method and the organization a session signs in to | The discovery sources and schedule over endpoints, SaaS tenants, cloud accounts and code hosts, and the latest comparison with the AI register | external |
| L3 | D1-SHADOW-REAP (organization) | None | The time the organization sets, and each finding of the last twelve months with the date it was registered or removed | external |
| L3 | D1-BOUNDARY | None. Managed `permissions` rules and `autoMode.hard_deny` entries enforce what the record states | The dated boundary record for each agent type, set against the deployment's agents | external |
| L3 | D1-BOUNDARY-DATA | None. `Read` deny rules, sandbox `denyRead` and the sandbox network allowlist enforce part of the handling it states | The data-handling statement for each agent type, set against the classes its agents read | external |
| L3 | D1-ALLOCATE | None. Anthropic's security page and Trust Center state Anthropic's side | Matrix rows for Anthropic as model, hosting and extension supplier, and the threat identification over each component | external |
| L3 | D1-ALLOCATE-RESIDUE | None | The disposition of each residue with the party that decided it, model API calls from other tools among them | external |

- **Login restriction prevents, and discovery finds.** `forceLoginOrgUUID` is checked for claude.ai logins in the terminal, the VS Code extension and the Agent SDK, not for Console logins, gateway sign-in or cloud-provider sessions, and the section read names no such check for the Desktop app.[^as-enforce] D1-SHADOW reads scheduled discovery across the organization's endpoints, software-as-a-service tenants, cloud accounts and code hosts. Endpoint inventory finds installs on unmanaged devices, and inside a WSL 2 distribution only a sensor running there sees processes.[^as-wsl] D1-SHADOW-REAP then reads each finding registered or removed within the time the organization sets.
- **The boundary record is the organization's, and the permission rules enforce it.** D1-BOUNDARY counts a configuration that enforces the boundaries as technical policy and no boundary record, so the dated record states each agent type's decision rights and cites the managed rule set by version. Allow, ask and deny rules enforce its three rights, and managed `permissions.deny` rules act before the auto-mode classifier in every mode and cannot be overridden.[^amc-scope][^pm-modes] An ask rule's prompt reaches whoever holds the session, as the D3-RIGHTS bullet sets out, so the record names the approver. D1-BOUNDARY-DATA's statement for each agent type maps onto `Read` deny rules and sandbox `denyRead` for what its agents may read, and onto the sandbox network allowlist for where data may go.[^perm-read][^sbx-fs][^sbx-network]
- **Anthropic's side of the responsibility matrix comes from its own documents.** The Trust Center holds the SOC 2 Type 2 report and the ISO 27001 certificate.[^sec-found] Anthropic runs VM isolation, network access controls and credential protection for sessions in its hosted cloud environments, and leaves isolation, egress and git credentials to the organization in a self-hosted environment.[^sec-cloud] It reviews connectors for its directory and security-audits no MCP server,[^sec-mcp] so the matrix allocates each MCP server's threats to the organization or to that server's own supplier. Managed settings bind Claude Code only, so model API calls from another tool stay residue on the organization's side, and D1-ALLOCATE-RESIDUE reads a disposition for it.[^ms-dev]
- **D1-HARNESS reads the managed source Claude Code resolved, and Claude Code reports it.** Managed settings rank above every settings file.[^set-prec] `/status` names the managed source in force on its `Setting sources` line, and from v2.1.242 a `Skipped sources` line names any source a higher one overrode.[^ms-status] `claude doctor` lists each dropped entry with its source.[^ms-drop] `managed_settings_resolved`, from v2.1.274, lists the managed sources a session runs on, empty where none applies, and with `OTEL_LOG_MANAGED_SETTINGS=1` it carries `managed_settings.resolved_sha256`, so machines reporting one digest run one policy.[^mon-msr] Desktop SSH and WSL sessions each resolve policy as a device of their own.[^desk-managed][^as-wsl] A user on an unmanaged device bypasses server-managed settings, a client-side control, without administrator rights, for example by exporting a provider variable or a non-default `ANTHROPIC_BASE_URL`, which skips the fetch,[^sms-sec][^sms-platform] so there D1-HARNESS needs an endpoint-managed source and a fleet record from device management. For a few keys Claude Code honors a stricter value from a lower scope over the managed one,[^set-exc] and D1-HARNESS does not say whether a stricter value counts as an override.
- **Four managed-only locks close permission rules, hooks, MCP servers and user- or project-sourced customization.**[^ms-managedonly] Under the default `"first-wins"`, Claude Code reads `allowManagedMcpServersOnly` from every admin source and the other three locks only from the managed source it applies, so those three belong in that source.[^ms-every] `strictPluginOnlyCustomization` locks every kind as `true`, and an array that omits a kind leaves that kind's user and project sources open. `managed_settings.settings` exports the four values as set.[^mon-msr]
- **D1-HARNESS-EXTEND's record names the list keys a local scope can still extend.** List keys merge across scopes, and a lock makes one list managed-only: `allowManagedReadPathsOnly` for `allowRead`, `allowManagedDomainsOnly` for domains, and the permission and MCP locks for theirs.[^set-prec][^sbx-widen] With every lock set, the keys a developer can still extend include:
  - `sandbox.excludedCommands`, which has no managed-only lockdown, and `sandbox.filesystem.allowWrite`.[^sbx-widen]
  - The `autoMode` lists, where a developer's `allow` entry can override an organization `soft_deny` entry.[^amc-scope]
  - `allowedHttpHookUrls` and `httpHookAllowedEnvVars`, which merge across settings files.[^ms-failclosed]
- **D1-HARNESS-RESTORE is native for server-managed settings and sits outside the harness for a file or a profile.** The next server fetch restores an edited cache, apart from the keys that apply only at the next launch, and `forceRemoteSettingsRefresh` stops a client from starting on cached or absent settings.[^sms-sec][^sms-failclosed] A developer who administers the machine can edit an endpoint-managed source, so device management redeploys it on a schedule.[^ms-dev]
- **D1-HARNESS-REVIEW's review record is the organization's, and Claude Code supplies part of the change history.** A `ConfigChange` hook can block an in-session change to a user, project or local settings file or a skill file, logs an edit to a managed file without blocking it, and does not run when server-managed settings or an MDM profile change.[^hk-config] Audit events for server-managed settings changes name the account and device behind each change and reference its previous and new values.[^sms-audit] A `claude -p` run on a pull request's checkout loads that branch's settings-file hooks and `env`, as the D4-SANDBOX-FIRST bullet sets out, so the change takes effect before its review unless the run's flags keep the repository's configuration out. Instruction files sit outside the four locks, so a repository's CLAUDE.md or rules file passes review at the code host, and a managed `claudeMdExcludes` pattern can skip a developer's own.[^mem-exclude]

- **Local shapes fail D2-IDENTITY.** Claude Code acts under no separate service account: each event carries the developer's Claude account, or the developer's IdP identity through a gateway,[^mon-attr] so both local shapes stop at L1.
- **Anthropic-hosted cloud sessions meet D2's vendor-held identity condition.** A customer-verifiable session identity exists only for self-hosted environments, in public beta, and Anthropic-hosted sessions' tokens carry an `sk-ant-si-` prefix and a separate key set,[^shi-format] so, with no agent principal of the organization's own, D2-IDENTITY, D2-IDENTITY-VERIFY, D2-LIFECYCLE and D2-IDENTITY-ATTEST are not applicable. The GitHub proxy swaps a scoped in-VM credential for the user's GitHub token and limits API calls to the session's repositories, which holds D2-DELEGATE,[^ce-github] while the downstream call carries the human's own token, where D2-DELEGATE-EXCHANGE wants one naming both parties.
- **A CI run holds two credentials, and D2-IDENTITY reads both.** Federation exchanges the workflow's GitHub OIDC token for Claude API access through a Console service account, leaving no long-lived key in the workflow.[^gha-wif] The repository credential defaults to the Claude GitHub App, shared by every Claude feature that integrates with GitHub, Code Review and cloud auto-fix included, and able to write to Actions, Workflows and repository hooks among others,[^gha-app] so the sheet reads D2-IDENTITY against a custom app whose `github_token` covers only the action.[^gha-params]
- **A human-triggered CI run acts for that human.** An `@claude` mention starts it, and the action requires the triggering user's write access and rejects a bot actor unless `allowed_bots` lists it,[^gha-trigger] so D2-DELEGATE sets the app's unchanged grant against that user's own access.
- **Self-hosted environments are the one route to the L3 identity criteria.** The session token proves that Anthropic issued it for a specific session in a specific environment and how the session was created, and not which runner process presents it.[^shi-proves] `act.sub` names the creating user or service identity, and `act.attested_by.sub` the SSO provider's subject.[^shi-act] With no revocation feed, a token stays valid until its `exp`, four hours by default and eight at most, so a service scopes what it derives from it,[^shi-claims][^shi-scope] and the beta route counts from its documented production date under the CMM's rule 2.
- **The harness supplies D2-TRACE's human half from outside the model.** Each event carries the human identity the D7 identity bullet lists per route, and with `OTEL_LOG_TOOL_DETAILS=1` `tool_result` records `git_commit_id` for a commit Claude makes.[^mon-toolresult] The `attribution.commit` trailer is no evidence, because the model writes the line even where a managed value outranks repository instructions.[^sr-attr]
- **D2-NOCRED turns on the route.** The environment scrub strips credentials from the Bash tool, hooks and MCP stdio servers while the parent process keeps them for its own API calls,[^env-vars] so a stored API key, or a long-lived token from `claude setup-token`, sits in the agent's process.[^auth-token] Gateway sign-in keeps the upstream credential in the organization's infrastructure behind a short-lived token, and federation leaves CI no stored key.[^gw-why][^gha-wif]
- **D2-KILL has a documented path on the gateway route only.** A user disabled in the IdP loses gateway access at the next failed refresh, within `ttl_hours`, and `/logout` sends a best-effort revocation from v2.1.275, while the gateway server advertises no revocation endpoint, so JWT secret rotation forces its sessions out.[^gw-enforced]
- **D2-AUTHZ finds no agent to name.** Permission rules name tools and paths, a subagent's `tools` and `disallowedTools` bind a tool list to a subagent definition, and a gateway policy binds settings to an IdP group of people, so no rule keys on an agent identity.[^sub-fields][^gw-avail]
- **D2-MUTUAL covers two legs.** The client certificate authenticates the model connection, which cloud sessions leave to the hosting environment by ignoring the variables in a settings file.[^nc-mtls] OAuth covers the remote MCP servers that use it.[^mcp-auth] Calls from shell commands, hooks and stdio MCP servers rest on each called service's own authentication.
- **D2-AUDIT covers grant changes.** Server-managed changes reach the compliance API, and `ConfigChange` hooks record local settings-file changes.[^sms-audit][^hk-config] Identity and credential events come from the identity provider's and the device-management system's own logs.

## 3 — D3 Control and Least-Agency

In [[agentic-ai-security-cmm-d3-control-least-agency|D3]] the harness is the decision point itself: Claude Code, not the model, applies the resolved allow, ask and deny rules before each tool call runs, and instructions that reach the model change nothing the rules allow.[^perm-manage] The sheet maps 28 of D3's 38 criteria. The other 10 fall into three groups:

- **Delegation criteria with no harness form.** Validation of the whole delegation chain and a coordination-only orchestrator at L4 (D3-CHAIN, D3-ORCHESTRATE), as the last delegation bullet below sets out.
- **L5 controls no harness setting implements.** The per-request approval token, anomaly-driven adaptation and cryptographic segregation of duties (D3-APPROVE-TOKEN, D3-ADAPT, D3-SOD-CRYPTO).
- **The L5+ criteria.** Per-task capability tokens and their narrowing at each hop, the privileged/quarantined split, formal analysis of each policy release, and rules on the order of a session's actions (D3-TASKTOKEN, D3-CHAIN-ATTENUATE, D3-QUARANTINE, D3-POLICY-FORMAL, D3-LEDGER-SEQUENCE).

- **D3-ALLOW reads a shell or fetch tool by its entries.** For a tool that runs arbitrary commands or requests, it counts the commands or destinations the agent runs without a person's approval, and it fails an entry that admits every one, so a `Bash` or `Bash(*)` allow rule, which matches every command, fails it, and so does a bare `WebFetch` allow rule.[^perm-syntax] Claude Code splits a compound command at its shell operators and holds each subcommand to the rules, so `Bash(npm test *)` admits no command chained after it.[^perm-compound] Anthropic counts blanket `Bash(*)`, wildcarded interpreters such as `Bash(python*)`, package-manager run commands and `Agent` allow rules as broad rules that grant arbitrary code execution, and drops them on entering auto mode.[^pm-classifier] Whether an interpreter or run-command entry, which runs code the agent can write, admits every command is the reading [#372](https://github.com/ag0x00/ai-era/issues/372) leaves open.
- **The allowlist is consulted in every mode and bounds the tool set only in some.** In `auto` the classifier decides calls outside the allow list,[^pm-classifier] `bypassPermissions` runs everything outside the deny and ask rules,[^pm-bypass] and `acceptEdits` adds file edits and `mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp` and `sed` inside the working directories to what runs unprompted.[^pm-accept] D3-ALLOW holds under every autonomy mode the deployment permits, so the sheet reads the rule set under the most permissive mode the surface offers and the deployment permits, and records D3-ALLOW not met under `auto` or `bypassPermissions` unless `--tools` and bare-name deny rules remove every tool the mode could run beyond the list.[^cli-flags] The surfaces offer different modes:
  - Managed `permissions.disableAutoMode` and `permissions.disableBypassPermissionsMode`, set to `"disable"`, remove the two permissive modes in the CLI and the Desktop app, and `permissions.defaultMode` sets only the starting mode.[^as-enforce][^desk-managed][^pm-start]
  - The Desktop app has no `dontAsk` and no equivalent of the tool flags, and shows Bypass permissions only once a Settings toggle on Pro and Max, or organization policy on Team and Enterprise, enables it.[^desk-modes][^desk-cli]
  - Cloud sessions offer Accept edits, Plan and Auto, pre-approve file edits in every mode, and ignore `bypassPermissions` and `dontAsk` from settings files.[^pm-switch][^pm-bypass]
- **D3-APPROVE reads every destructive action, through any tool, rule or mode.** D3 sets a floor of six classes the organization can add to: deletions, unrecoverable overwrites, bulk writes, transfers of value, access-right changes and sends outside the organization. For a coding agent the classes include force-push, branch deletion, a mass refactor and any write to production configuration, and a confirmation that the person the agent acts for gives in the session is an approval. Ask and deny rules act before the auto-mode classifier, and ask rules match command text,[^pm-classifier][^perm-bash] so in `auto` a destructive command written another way reaches the classifier, which can approve it, and D3-APPROVE holds only where managed settings remove `auto` and `bypassPermissions`. `acceptEdits` runs `rm` and `rmdir` inside the working directories unprompted unless an ask rule names them,[^pm-accept] and a routine runs without stopping for approval, so in a routine a rule has to refuse each destructive action.[^rt-create] Whether an agent's write to the working copy is a draft or a destructive write, and where a bulk write starts, are the readings [#372](https://github.com/ag0x00/ai-era/issues/372) leaves open.
- **Bash rules match command text, which D3-MEDIATE-EXACT grades advisory.** A rule matches the text Claude writes after Claude Code splits compound commands and strips a fixed set of wrappers, so Anthropic states that a Bash rule is no security boundary around the program: `Bash(git push *)` stops `git push origin main` and misses `git -C . push origin main` and `git 'push' origin main`.[^perm-bash] [[guard-canonicalization-gap|Guard Canonicalization Gap]] explains the advisory grade. The OS sandbox is the harness control independent of command text, and a `PreToolUse` hook that reads the command as the shell will run it, before the call runs, is the route to D3-MEDIATE-EXACT.[^perm-bash][^hk-pretool]
- **Every tool call reaches the permission system in every mode.** Deny rules block in every mode, `bypassPermissions` included, and a subagent's calls fall under the same rules and its own tool list.[^pm-modes][^sub-tools] The one tool that deny and ask rules and the permission hooks leave alone while any other tool remains is `EndConversation`, which ends only the main conversation.[^pm-modes][^hk-permreq][^tools-endconv] `tool_decision` records each decision with the tool's name, and a user-configured MCP server's tool appears there as `mcp_tool` unless `OTEL_LOG_TOOL_DETAILS=1` names it.[^mon-decision]
- **D3-MEDIATE-OUTSIDE takes the four in-process substitute artifacts, and each has a harness instrument:**
  1. The policy as resolved on an enrolled device, with its scope: the `Setting sources` line in `/status`, and `managed_settings.sources` on `managed_settings_resolved`.[^ms-status][^mon-map]
  2. The record that the model cannot write that scope. The plist and HKLM sources need administrator rights to write.[^as-deliver] The sandbox denies sandboxed commands any write to `.claude` settings files, skills, agents, hooks and `.mcp.json`, with no exemption, including the target of a symlink planted at a protected path.[^sbx-protected] `ConfigChange` hooks audit in-session changes to user, project, local and policy settings files and to skills, and do not run for server-managed, MDM or registry changes.[^hk-config]
  3. A denied action under the most permissive mode the deployment permits, since deny rules block in every mode, `bypassPermissions` included.[^pm-modes]
  4. The documented behavior when the policy source is absent or malformed, which the D3-MEDIATE-FAILCLOSED bullet below reads.[^ms-drop]
- **The second artifact leans on the managed-only locks.** `bypassPermissions` allows writes to protected paths, so the model can edit a project `.claude/settings.json`, and native Windows has no sandbox to stop a shell command writing it.[^pm-protected][^sbx-platform] Under `allowManagedPermissionRulesOnly` and `allowManagedHooksOnly` that file holds no permission rule or hook the harness honors.[^ms-managedonly] The audit half needs a `ConfigChange` hook the organization writes, which makes the D3-MEDIATE-OUTSIDE row partial.
- **A hook that routes decisions to a policy engine withdraws the substitution for the calls it decides**, which then need the direct-invocation and unreachability tests. A timed-out `command`, `http` or `mcp_tool` hook lets the call continue through the normal permission flow,[^hk-timeout] so the engine's failure falls back to the rule set, which in `dontAsk` denies every call that neither an allow rule nor Manual mode's unprompted set covers.[^pm-dontask]
- **Three records outside the harness narrow the circularity** the protocol records for these artifacts:
  - The managed settings as the device-management system or the admin console holds them.
  - The target system's own log of a denied action, such as the Git host's audit log.
  - The OpenTelemetry events in the organization's store.
- **Each call waits for its decision.** Claude Code evaluates deny, then ask, then allow rules before a call runs,[^perm-manage] and a hook holds the call until it completes unless it runs `async`, which can neither block nor decide.[^hk-async] In the beta traces each tool span has one child span for the permission wait and another for the execution, which D3-MEDIATE-SYNC's trace reads.[^mon-traces]
- **D3-MEDIATE-FAILCLOSED is not met as written.** It reads an in-process enforcement point from the behavior the vendor documents for the running version, and fails one that proceeds when its policy source is absent or falls back to a policy wider than the one that failed to load. A managed file, plist or HKLM value that does not parse refuses start, even beside a valid source, and a managed file that cannot be read ends a claude.ai or Console session at startup when no admin source supplies a policy. A malformed HKCU value never blocks launch, and an absent source is no failure: Claude Code runs without it. Claude Code skips a schema-invalid entry, such as one invalid permission rule, with a warning, drops a top-level key whose value still fails and keeps every valid key, so a skipped deny rule leaves a wider policy, and only the keys that fail closed fall back to a stricter value.[^ms-drop][^ms-failclosed] A `policyHelper` whose startup run fails, its file missing included, refuses start, and an invalid `policyHelper` value is dropped, starting the session on the remaining managed settings.[^sr-helper] Server-managed delivery proceeds on cached or absent settings unless `forceRemoteSettingsRefresh` is set, which exits when no fresh policy arrives and covers first launch from an endpoint-managed source.[^sms-failclosed] A shell that exports a provider variable skips the fetch and starts without waiting, and a gateway-signed-in session exits at startup when the gateway is unreachable.[^sms-platform][^sms-failclosed][^gw-enforced] Until [#342](https://github.com/ag0x00/ai-era/issues/342) decides whether device management, fleet digests and `forceRemoteSettingsRefresh` can stand in for the absent case, the sheet records the criterion not met, which holds every Claude Code estate below D3 L3.
- **D3-DENY holds where a call no rule matches prompts or is denied.** Manual mode prompts for it, `dontAsk` denies it, `auto` hands it to the classifier and `bypassPermissions` runs it,[^pm-modes][^pm-dontask][^pm-classifier] so D3-DENY holds where managed settings remove the last two. The sheet reads the built-in read-only set, which runs unprompted in every mode, and `acceptEdits`' approvals inside the working directories as rules the harness applies, which an ask or deny rule narrows.[^perm-readonly][^pm-accept]
- **D3-POLICY-LOCK needs the locks and a managed source the developer cannot edit.** `allowManagedPermissionRulesOnly` ignores permission rules from user, project, local and `--settings` files and from `--allowedTools`, hides the always-allow choices in prompts and saves no new rule.[^sr-lockrules] These routes stay open to the agent's principal:
  - A hook from a lower scope, whose `"allow"` skips the prompt and in `dontAsk` runs a call no rule allows, until `allowManagedHooksOnly` runs only the hooks the organization deploys.[^hk-pretool][^pm-dontask][^ms-managedonly]
  - A user or project skill's `allowed-tools`, which workspace trust never gates, until `strictPluginOnlyCustomization` blocks skills from user and project sources.[^perm-trust][^sr-strict]
  - A developer's `autoMode` `allow` entry, which can override an organization `soft_deny` entry where `auto` is permitted.[^amc-scope]
  - An endpoint-managed source that a developer who administers the machine can edit, and on an unmanaged device a provider variable that skips the server-managed fetch.[^ms-dev][^sms-sec][^sms-platform]
  - In CI, the workflow's `settings` and `claude_args` inputs, which carry the run's policy and change with the workflow file.[^gha-params]
- **The rule set is the tier record.** D3-TIER accepts an allowlist whose unlisted calls are refused as a record, with its entries at auto and every other call at block, so a rule set run in `dontAsk` is one, and in Manual mode an unlisted call prompts, which places it at confirm.[^pm-dontask][^pm-modes] The record is dated where the managed settings are versioned. In `auto` the classifier decides a call no rule names, which gives that call no recorded tier.[^pm-classifier]
- **D3-TIER-DESTRUCT's classification is a managed rule set, with the classifier as a second gate in auto mode.** The classifier blocks by default, among others, force push, production deploys and migrations, `terraform destroy` and irreversible destruction of files that existed before the session.[^pm-blocks] User intent and `allow` exceptions can clear a `soft_deny` rule, and a `hard_deny` rule blocks unconditionally.[^amc-rules] The managed ask and deny lists, which act before the classifier, are therefore the evidence item's confirm and block tiers.[^amc-scope] An allow entry whose prefix admits a destructive command places that command at auto, which fails the criterion, so a CI run in `dontAsk` is read on the destructive commands its allow entries admit. `rm` and `rmdir` on a critical path prompt even in `bypassPermissions`.[^pm-noauto]
- **D3-TIER-ENFORCE maps the four tiers onto three rule kinds and a hook.** An allow rule, or auto mode's approved set, is the auto tier, an ask rule the confirm tier and a deny rule the block tier, and notify, which has no rule kind, is a `PostToolUse` hook that sends the notification. Outside plan mode, with sandboxing on and `autoAllowBashIfSandboxed` at its default, a bare `Bash` ask rule stops prompting for sandboxed commands, while content-scoped ask rules keep prompting.[^perm-sbx] `dontAsk` denies an ask-rule call, and from v2.1.259 `--permission-prompts none` denies every prompt in print mode.[^pm-dontask][^cli-flags]
- **D3-APPROVE-GATE holds where an ask rule names the action.** No mode auto-approves an explicit ask rule: the call prompts, or `dontAsk` denies it, apart from the bare `Bash` rule the D3-TIER-ENFORCE bullet names.[^pm-noauto][^pm-dontask] A hook's `"ask"` forces a prompt in auto mode, where the classifier can still deny the call and cannot approve it silently,[^hk-pretool] so no clean classifier result stands in for the approver, as D3-TIER-DESTRUCT and D3-APPROVE-GATE require of each destructive action at the confirm tier.
- **D3-RIGHTS has no field in the harness.** The approval prompt reaches whoever holds the session, a `PermissionRequest` hook can answer it for the user, and a session that cannot show a prompt denies the call when no hook decides.[^hk-permreq] A hook forwarding the request to an approval service moves the matrix into that service, graded on its own record against [[decision-rights|Decision Rights for AI Agents]].
- **Live observation at L3 draws its three records from the harness.** For the protocol's live trace, decision and gate fire, a denied call emits `tool_decision` with `source` set to `config`, and a prompt appears as a `claude_code.tool.blocked_on_user` span in the beta traces.[^mon-decision][^mon-traces]
- **D3-PROMOTE has stages and no promotion record.** The modes run from Manual through `acceptEdits` and `auto` to `dontAsk` and `bypassPermissions`, each change emits `permission_mode_changed` with `from_mode`, `to_mode` and `trigger`, and the promotion criteria are the organization's document.[^pm-modes][^mon-map]
- **D3-APPROVE-COVERAGE reads the decision records.** `tool_decision` reports `user_temporary` or `user_permanent` for a person's answer, and `config` or `hook` for a decision taken without one, which in the interactive CLI includes a later call under an earlier session grant.[^mon-decision] The share of each action class's calls a person approved comes from those events, and the cadence and the review are the organization's. In Agent SDK and `-p` sessions a later call under an earlier grant still reads `user_temporary` or `user_permanent`, as the D7-CONTROL-APPROVE bullet sets out.
- **Task scope is a hook the organization writes, and the trifecta breaker needs more.** Claude Code holds no task scope, so the organization declares one and writes the `PreToolUse` hook that denies an out-of-scope call, which D3-TASKSCOPE reads, and logs the denial as an agent-escape event naming the agent, the task, the tool and the scope, which D3-TASKSCOPE-RECORD reads. The harness enforces the deny and records it on `tool_decision` with `source` set to `hook`.[^hk-pretool][^mon-decision] The D3-TRIFECTA row stays external, because D3 evaluates its external-communications leg across every permitted dependency, which the harness does not hold.
- **D3-ELEVATE has no native control, and a prompt's standing grant fails it.** A "Yes, and don't ask again" answer saves an allow rule for the repository, for a Bash command, a fetch domain or web search, and a file-edit approval lasts until the session ends,[^perm-tools] so a grant given at a prompt outlives its task. `allowManagedPermissionRulesOnly` hides the always-allow choices and saves no new rule,[^sr-lockrules] and a grant with an expiry the decision point enforces comes from a broker outside the harness.
- **D3-SOD needs three principals the pipeline keeps apart.** A cloud session pushes only to its working branch,[^ce-github] and D3-SOD fails a pipeline in which the approver's merge is itself the deployment, so its evidence is the code host's and the deploy pipeline's role assignments. The default Claude GitHub App can write to Actions, Workflows and repository hooks, so a CI run holds only the proposer's role where a custom app and the code host's protections confine it, as the D2 CI bullet sets out.[^gha-app]
- **D3-NOREPLAY has no instance.** Subagents run in the parent session's process,[^sbx-scope] so every agent of a session calls under the session's credential, which D3 counts as no authorization of any one agent, and D2-IDENTITY grades the sharing.
- **D3-LEDGER has one native cap.** `CLAUDE_CODE_SCRIPT_CAPS` limits how often named scripts run per session when the environment scrub is set, and Anthropic calls it defense in depth that misses fan-out through `xargs` or `find -exec`,[^env-vars] so a stateful `PreToolUse` hook the organization writes carries the cumulative threshold. D3-LEDGER fails a limit that a restart resets while the session continues, which the hook's ledger has to survive.
- **Delegation is capped in depth and narrowed by default.** A subagent spawns subagents of its own down to `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` layers below the main conversation, three by default, a limit that can be adjusted and not removed. At the limit the harness withholds the `Agent` tool, and a fork's call to it returns an error, which meets D3-CHAIN-DEPTH.[^sub-depth][^env-vars] Teammates in an agent team cannot spawn teammates.[^teams-limits] A subagent inherits the main conversation's built-in and MCP tools, narrowed by harness filters and by its `tools` and `disallowedTools` fields.[^sub-tools] `strictPluginOnlyCustomization` keeps user and project subagent definitions out, so the definitions left to review come from plugins or managed settings,[^sr-strict] and D3-CHAIN-SUBSET fails a definition that takes one of these routes past the main conversation's tools:
  - An inline `mcpServers` entry connects a server the main conversation lacks.[^sub-mcp]
  - Under a main conversation in Manual, `dontAsk` or plan mode, a subagent runs in its own `permissionMode`, `bypassPermissions` excepted.[^sub-mode]
  - On macOS, Linux and WSL a subagent can receive the Glob and Grep tools the main conversation lacks.[^sub-tools]
  - A `memory` field enables Read, Write and Edit so the subagent can manage its memory files, and the pages read do not say whether it does so where the main conversation lacks them, so a test decides a definition that sets one.[^sub-memory]
- **D3-CHAIN and D3-ORCHESTRATE have no harness form.** D3-CHAIN reads a credential issued for each step of the chain, and a session's agents share one. D3-ORCHESTRATE reads an orchestrator that holds coordination grants only, and the delegates of an orchestrator holding no destructive built-in tool inherit none.[^sub-tools] Of the routes above, only a server an inline `mcpServers` entry connects, and possibly the `memory` route, can give a delegate a destructive grant its orchestrator lacks, and each such grant fails D3-CHAIN-SUBSET.
- **The policy-release criteria read the managed settings as the policy.** D3 counts each change to the policy that reaches production as a release. Anthropic publishes a JSON schema for settings files, which can lag behind new releases, and `claude doctor` lists each invalid managed entry, so D3-POLICY-COMPILE reads a schema check or a `claude doctor` run on a test device in the pipeline that ships the file, with the step that stops a failing release.[^set-schema][^ms-drop] Audit events for server-managed settings name the account behind each change,[^sms-audit] and D3-POLICY-REVIEW's second reviewer is the organization's. `managed_settings_resolved` carries the resolved digest under `OTEL_LOG_MANAGED_SETTINGS=1`, at session start and again when the policy changes,[^mon-msr] so D3-POLICY-DRIFT compares it with the reviewed release's digest in the SIEM, which raises the alert.

## 4 — D4 Runtime and Guardrails

[[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] grades screening on the model's input and output, injection classifiers on the prompt and on every route that carries untrusted content, the sandbox around everything an agent executes, and checks on the agent's intent and on the effect of its calls. Claude Code supplies a shell sandbox, hook events where a screen the organization writes can block a prompt or a tool call and replace a tool result, and, in auto mode, a classifier that reviews actions before they run. Anthropic's service runs the safety classifiers. The sheet maps 23 of D4's 29 criteria. The other 6 have no control in the Claude Code pages read: groundedness checking at L4, the injection classifiers' miss-rate measurements per language and per bypass class and their refresh at L5, and guardrail attestation and bypass remediation at L5+. Beside D4-SANDBOX-CLEAN and D4-SANDBOX-LIMITS, which set the ceiling, D4-SANDBOX-CREDS needs a control outside the harness: a proxy or credential store outside the sandbox boundary that attaches the harness's own credentials to its calls.

- **The L2 input filter is Anthropic's, and the organization reads it in its own telemetry.** Fable, Opus 5.5 and Opus 5 models run with safety classifiers that most often flag cybersecurity and biology content. A flagged request re-runs on a fallback model where its category has one, and with `switchModelsOnFlag` set to `false` it pauses the session instead, or ends a `-p` run with an error.[^mc-fallback][^sr-switch] Claude Code emits `api_refusal` when a request ends in a refusal, which arrives on the response stream, and with `OTEL_LOG_TOOL_DETAILS=1` its `category` names `cyber`, `bio`, `frontier_llm` or `reasoning_extraction`.[^mon-refusal] The pages read name no classifier for requests to other models, such as a subagent whose `model` field names Haiku, so D4-INPUT is met where every model call goes to a classified model or a `UserPromptSubmit` filter screens the prompt first.[^sub-fields]
- **D4-OUTPUT has no documented scope over what the model returns.** The pages read give the classifiers no scope over replies or tool-call content, so D4-OUTPUT rests on a test that blocked a reply and a tool call, or on hooks the organization writes. A `PreToolUse` hook screens the content Claude passes to a tool before the call runs.[^hk-pretool] `MessageDisplay` can redact a reply on screen, fails open on an error or a timeout, and leaves the transcript and what Claude sees unchanged.[^hk-msgdisplay]
- **D4-INJECT-DIRECT rests on a hook the organization writes.** The security page credits Claude Code with context-aware analysis that detects potentially harmful instructions, and names no category, threshold or action for it, which D4 counts as attesting no control.[^sec-pi] A `UserPromptSubmit` hook can run an injection classifier and block the prompt, which erases it from context. A command, HTTP or MCP tool hook that times out passes the prompt through, and an Agent SDK callback that times out blocks it,[^hk-prompt] so on an agent that can make a high-impact call only the callback meets D9-GUARD-FAILMODE, as the D9 fail-mode bullet sets out.
- **D4-INJECT-INDIRECT has a vendor probe in auto mode.** A server-side probe scans incoming tool results and flags suspicious content before Claude reads it, and tool results are stripped from the classifier's own requests.[^pm-classifier] No event in the pages read records the flag, and the pages do not say whether a flagged result is withheld or delivered with a mark, so each route's verdict rests on a crafted file planted on the path a tool reads. Subagent reports arrive under a header marking them as subagent output, after a scan that marks instruction-shaped text without judging whether it is malicious, so the scan labels the route and D4-INJECT-INDIRECT still needs a classifier on it.[^sub-scan]
- **A `PostToolUse` hook covers tool results, and no hook covers instruction files.** A `PostToolUse` hook can run a classifier on each tool result and replace a flagged one through `updatedToolOutput` before Claude sees it, and a timed-out hook leaves the result unchanged,[^hk-posttool][^hk-timeout] which on an agent that can make a high-impact call fails D9-GUARD-FAILMODE. Instruction files form a route no hook can hold, because `InstructionsLoaded` cannot block.[^hk-instr] Where outside parties can change the workspace, D4-INJECT-INDIRECT therefore needs those files kept out of the run: `--bare` and `claudeMdExcludes` keep out CLAUDE.md files, and `includeGitInstructions: false` drops the git status snapshot.[^cli-flags][^mem-exclude][^sr-git]
- **No canonicalization is documented.** The pages read describe no Unicode normalization, invisible-character removal, case folding or confusable mapping ahead of the probe, so D4-INJECT-CANON reads the probe from a blocked attack presented again in each variant form, and a classifier hook the organization writes canonicalizes the text before its own classifier reads it.
- **D4-OUTPUT-SCOPE is the organization's record.** The refusal event names four categories, `cyber`, `bio`, `frontier_llm` and `reasoning_extraction`, and the pages read state no exposure-restricted data class for any classifier.[^mon-refusal] The record lists those categories and states, for each exposure-restricted class the model can reach, system prompts included, and for other technical detail about the system, whether a classifier detects it. The classes are graded where content leaves: at a gateway under D5-GATEWAY-SCREEN, in answers under D6-LABEL-GATE at D6 L4 and, for credentials, under D4-OUTPUT-LEAK.
- **The sandbox covers shell commands, and D4-SANDBOX reads the whole run.** It applies to Bash, PowerShell and Monitor commands and their child processes.[^perm-sbx] Read, Edit and Write use the permission system, and MCP servers and command hooks are separate processes that run unconstrained on the host,[^sbx-scope][^se-bash] so D4-SANDBOX is not met while any of them runs outside a sandbox. The sandbox runtime `@anthropic-ai/sandbox-runtime`, a beta research preview, puts the whole process inside one, as a dev container, a VM or a cloud session does.[^se-runtime][^se-bash] [[anthropic-sandbox-runtime|Anthropic Sandbox Runtime]] tracks the runtime, and [[claude-code-github-action-credential-exposure|Claude Code GitHub Action Credential Exposure]] records an exfiltration through the unsandboxed Read tool while the shell boundary held.
- **Three settings make the sandbox mandatory for the commands Claude runs.** `sandbox.enabled`, `failIfUnavailable` and `allowUnsandboxedCommands: false` enable it, refuse start when it cannot initialize, and remove the model's unsandboxed retry.[^sbx-enforce] Four paths stay outside it:
  - `excludedCommands`, which a developer's own scope can extend, because the key has no managed-only lock.[^sbx-widen]
  - Commands a person types at the `!` prompt, except in background sessions and in Linux sessions with the environment scrub set. D4-SANDBOX counts an agent's executions, and these are the person's.[^sbx-retry]
  - Native Windows, which has no sandbox.[^sbx-platform]
  - Computer use, a research preview on Pro and Max plans that is off by default and acts on the actual desktop outside the sandbox.[^desk-cu][^cu-cli]
- **The trust table answers D4-SANDBOX-FIRST for repository content.** In a folder never trusted, a `claude -p` or SDK run uses the settings-file hooks, the `env` block and helpers such as `apiKeyHelper`, and connects `.mcp.json` servers without asking,[^perm-trust] since trust verification is off under `-p`,[^sec-add] and those hooks and servers run on the host outside the command sandbox.[^se-bash] Such a run also counts as trusted for the git commands Claude Code runs itself, which the command sandbox does not cover,[^perm-local][^perm-sbx] so a boundary started before Claude Code, such as the sandbox runtime, a container or a VM, meets D4-SANDBOX-FIRST whatever the run reads. D4 reads this harness's verdict from that documentation. Without such a boundary, each flag keeps part of the repository's configuration out of the run:[^perm-trust]
  - `--setting-sources user` reads neither the project's settings files nor its `.mcp.json`.
  - `--bare` reads no project hooks, skills, commands, subagents, plugins or `.mcp.json` servers, and still applies the project's `env` block and helpers such as `awsAuthRefresh`.
  - `--settings '{"disableAllHooks": true}'` turns hooks off for that run.
  - A `disabledMcpjsonServers` entry rejects a named `.mcp.json` server in every session type.
- **D4-SANDBOX-CONFINE's four refusals each turn on a setting.**
  - Starting a process outside the sandbox: a command's child processes stay inside it, and `allowAppleEvents` on macOS, or a socket such as `/var/run/docker.sock` in `allowUnixSockets`, reopens the path.[^perm-sbx][^sbx-limits]
  - Reaching host files outside the workspace: the default read policy covers the whole machine, including `~/.aws/credentials` and `~/.ssh/`, until `denyRead` narrows it.[^sbx-fs]
  - Changing the agent's configuration: protected paths deny writes to the settings files, skills, agents, hooks and `.mcp.json`, with no exemption.[^sbx-protected]
  - Interacting with the host: Apple Events are blocked by default on macOS, and on Linux `enableWeakerNestedSandbox` exposes process information that a fresh `/proc` mount would hide.[^sbx-limits][^sbx-trouble]
- **D4-SANDBOX-MAC is documented for macOS.** The sandbox uses Seatbelt on macOS and bubblewrap on Linux and WSL2.[^sbx-os] D4 names Seatbelt among the profiles it grades, and the pages read name no seccomp, AppArmor or SELinux profile under bubblewrap and no capability set on either platform, so the Linux profile and each platform's capability set are read from a running sandboxed process.
- **D4-SANDBOX-CREDS needs a proxy outside the boundary.** The sandbox denies no credential by default. `sandbox.credentials` entries deny credential files and unset variables for sandboxed commands, and `mask` entries, with the experimental `network.tlsTerminate`, show commands a placeholder that the sandbox proxy swaps for the real value on requests to allowed hosts.[^sbx-creds] `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips credentials from the Bash tool, hooks and MCP stdio servers, while the parent process keeps them for its own API calls.[^env-vars] The whole-process boundary D4-SANDBOX needs therefore holds the harness's own credential, and a cloud session holds a scoped credential inside its VM,[^sec-cloud] which D4-SANDBOX-CREDS counts, short-lived tokens included. The criterion is met where a proxy or credential store outside the boundary attaches the harness's credentials to its calls.
- **D4-SANDBOX-CLEAN and D4-SANDBOX-LIMITS need an environment per task.** Locally the sandbox wraps each command, and sandboxed commands share the session temp directory, so a later task in the session can read what an earlier one left there.[^sbx-tmp] On Linux and WSL2 a forced stop, such as SIGKILL, leaves the sandbox's placeholder files at protected paths behind.[^sbx-trouble] A cloud session gets a fresh VM, which serves every task in the session until it is reclaimed after a period of inactivity.[^ce-vm][^sec-cloud] Cloud VMs run with approximate ceilings of 4 vCPUs and 16 GB of RAM, the pages read state no wall-clock limit on a running session in either shape, and the Bash tool's timeout, which the model sets up to `BASH_MAX_TIMEOUT_MS`, is a limit the harness keeps and counts for none of the three.[^ce-vm][^env-vars] A container or VM that the platform creates for each task, destroys at its end or on a forced stop, and caps in CPU, memory and wall-clock time meets both criteria.
- **Code-safety analysis is advisory inside the harness.** The [[security-guidance-plugin|Security Guidance Plugin]] reviews each edit, turn and commit and blocks none of them.[^sg-limits] Code Review, a research preview on Team and Enterprise plans, posts findings and always completes its check run neutral, so it never blocks a merge.[^cr-note][^cr-check] D4-CODESCAN requires a finding at the organization's severity to hold the code until a person clears it, so static analysis in CI that blocks the merge carries the criterion.
- **D4-CONTEXT has no native rule.** WebFetch uses a separate context window to keep hostile page content out of the main conversation,[^sec-add] and subagent reports arrive under a marking header. D4-CONTEXT grades a rule outside the model that holds outbound calls once untrusted content enters a session, and a context window or a label holds no call. A `PostToolUse` hook can mark the session when a tool returns untrusted content, and a `PreToolUse` hook then deny each call that sends content outside the organization until the task ends.[^hk-posttool][^hk-pretool]
- **The auto-mode classifier meets part of D4-ALIGN and is a same-family judge.** In auto mode a separate classifier model reviews actions before they run and blocks one that escalates beyond the request, targets unrecognized infrastructure or appears driven by hostile content Claude read.[^pm-auto] Actions an allow, ask or deny rule settles skip it, and so do read-only actions and working-directory file edits, apart from the read-only and sandboxed shell commands that server-side review checks.[^pm-classifier] In its own requests the classifier sees the user's messages, the tool calls and CLAUDE.md, and no tool result.[^pm-classifier] D4-ALIGN reads each tool call, so the calls that skip the classifier, and every call outside auto mode, go unchecked. The classifier runs on Claude Sonnet 5 by default, and a model Anthropic configures server-side takes precedence,[^pm-auto] so D4-VALIDATE-JUDGE, which asks for a judge from another model family, stays open until a `PreToolUse` hook passes high-impact calls to such a judge.
- **D4-VALIDATE-DRYRUN and D4-VALIDATE-IMPACT rest on hooks.** Permission rules match tool names, paths and command text, and none reads a call's parsed impact.[^perm-bash] A `PreToolUse` hook receives each call's input before it runs and can deny it or force a prompt,[^hk-pretool] so a hook the organization writes can run a tool's own preview mode, such as a plan command, record the proposed change, and refuse or hold a call whose parsed arguments pass a per-call limit.
- **D4-PLATFORM reads the managed locks.** A hook in managed settings stays on when user, project or local settings set `disableAllHooks`, and `allowManagedHooksOnly` runs only the hooks the organization deploys,[^hk-disable][^ms-managedonly] so a hook-based L4 control holds against the developer as far as the managed source does against a developer who administers the machine.[^ms-dev] Managed settings can disable auto mode, and no setting in the pages read keeps a developer in it, because `permissions.defaultMode` sets only the starting mode,[^pm-start] so the classifier the D4-ALIGN row reads is a control the developer can leave.
- **D4-OUTPUT-LEAK and D4-BUDGET rest on hooks.** `MessageDisplay` can redact API keys from what renders and fails open, and a `PreToolUse` hook can scan the content Claude passes to a tool,[^hk-msgdisplay][^hk-pretool] while the test against encoded forms is the organization's. A hook's `timeout` is a latency budget Claude Code enforces: it cancels the hook and discards its output, and a timed-out `PreToolUse` hook lets the call continue through the permission flow, the fail mode the D9 section's first bullet lists.[^hk-timeout] The pages read give no setting that caps a guardrail's cost, and none that budgets the auto-mode classifier.
- **D4-SHARED starts from what subagents share.** Subagents run in the parent session's process and use its sandbox configuration,[^sbx-scope] and a subagent definition with its own instructions and tools is a different agent under D4's definition. The register records each service they share, the process, the sandbox proxy and the model connection among them, with the organization's written residual risk for each. The proxy, MCP servers and hooks sit outside the sandbox.[^sbx-network][^se-bash] D4-SHARED is not applicable to a deployment that runs one agent.
- **Rule DR-003 caps D4 at D3's raw score.**

- **The sandbox allowlist covers shell commands and their children.** Claude Code pre-allows no domain, prompts on a new one, and blocks instead under `strictAllowlist`, which a repository's settings files cannot set, or a managed `allowManagedDomainsOnly`.[^sbx-network]
- **The Desktop Browser pane is a further leg.** Outside Auto and Bypass permissions a domain allowlist check precedes navigation to a new site, and safety classifiers review Claude's write actions on external pages in every mode. The pane follows the organization's Claude in Chrome site allowlist and blocklist, `browserExternalPageTools` set to `"disabled"` removes Claude's tools from external pages, and `disableBrowserExternalNavigation` set to `true` blocks external navigation for users and Claude.[^desk-browser][^desk-managed]
- **Cloud sessions bypass the environment allowlist on four paths.** GitHub traffic through its proxy, enabled MCP connectors, the hosts of the environment's API credentials, and Claude Code's own calls to the Anthropic API all skip it.[^ce-levels] No organization-level allowlist reaches every member's environments, and an Owner standardizes one through an organization-shared environment.[^ce-allow]
- **D5-REACH covers each allowlisted host, external ones included.** The cloud environment's default Trusted level allows package registries, GitHub and cloud SDKs,[^ce-levels] and D5-REACH records what each of them reaches, the outside parties who publish there included, such as the package authors on a registry and the other accounts on a code host. D5 cites two cases: an internal package mirror with open internet access, and a public code host that served a benchmark's answers.
- **D5-ALLOW-LOCK needs the managed locks.** `allowedDomains` merges entries from every scope the session loads, so a repository's or a developer's settings file can add a domain unless a managed `allowManagedDomainsOnly` limits the list to managed entries.[^sbx-widen] Without that lock or `strictAllowlist`, an approval at the prompt allows a host, and in auto mode from v2.1.271 a command can name hosts beyond the list for the classifier to review.[^sbx-network] `allowManagedMcpServersOnly` locks the MCP server allowlist the same way, and `allowManagedPermissionRulesOnly` the permission rules that govern the fetch tool.[^mmcp-lock][^ms-managedonly] A lock is as strong as the managed source, which a developer who administers the machine can edit.[^ms-dev] In the cloud each environment carries its own allowlist, set by whoever creates the environment, so the list holds against a member only in an Owner's shared environment.[^ce-allow]
- **The gateways sit on the model leg.** A Claude apps gateway sits between the client and the model provider and disables WebSearch on its sessions,[^gw-why][^gw-avail] and Claude Code honors `forceLoginMethod` set to `"gateway"` only from a managed source on the machine, and a cloud-provider environment variable skips the gateway sign-in.[^sr-login] Another LLM gateway sits in the same position,[^as-data] and D5-GATEWAY also requires every tool and MCP call to leave through the gateway, so either meets it in part. D5 states that a decision the harness holds, with no gateway on the path, fails D5-GATEWAY-AUTHZ, so the permission rules the D3 section maps evidence nothing here.
- **No harness screen on the egress path states its classes.** The gateway pages read describe no content screen, and a cloud session's security proxy lists content filtering without naming its classes or directions,[^ce-proxy] so D5-GATEWAY-SCREEN rests on a gateway outside the harness. Anthropic's own screening of requests and tool results is graded in the D4 section.
- **The ceilings sit on the model leg as well.** A Claude apps gateway caps each developer's spend by day, week or month, metered from the token counts of each response, and refuses requests once a cap is passed, which meets D5-CEILING-TOKENS in part, keyed on the developer rather than on an agent.[^gw-spend] The gateway pages read describe no call-count or tool-invocation ceiling, and `CLAUDE_CODE_SCRIPT_CAPS` runs inside the agent, so D5-CEILING and D5-CEILING-TOOLS rest on a component outside it.[^env-vars]
- **MCP brokering has one harness path, the cloud session's proxy.** That proxy authenticates to delivered connectors with the authorization the member granted in claude.ai.[^mcp-auth] Elsewhere Claude Code connects to each MCP server itself and stores the OAuth token for a remote one, and D5-MCP-BROKER names a developer's own OAuth grant, and a local server started with no authentication, as failing it, so the broker is a gateway outside the harness. A managed allowlist by `serverUrl`, or a deployed `managed-mcp.json`, bounds which remote servers the agent reaches, and server-managed settings cannot carry that file, delivering servers through `managedMcpServers` without its exclusive control.[^mmcp-excl] In the Desktop app's local and SSH sessions the claude.ai connectors arrive in-process, beyond every MCP setting, and only the organization's `blocked` connector tool controls reach them.[^mcp-connectors]
- **Tool definitions move at runtime.** Claude Code accepts `list_changed` notifications and refreshes a server's tools without reconnecting.[^mcp-dynamic] D5-MCP-PIN compares the served definitions with the recorded fingerprints each time the agent connects, and a refresh arrives without a new connection, so the comparison belongs in a gateway that sees each refresh, where D5-MCP-RUGPULL's refusal also runs.
- **Agent teams carry an inter-agent channel on local files.** The experimental agent teams, disabled by default, exchange messages through a mailbox file per agent under `~/.claude/teams/`.[^teams] D5 grades inter-agent traffic whatever its protocol, and a teammate spawned from a subagent definition takes that definition's tools, model and instructions, which makes it a different agent under D3's delegation hop.[^teams-def] Its messages therefore fall under D5's A2A criteria, and the agent-teams pages read describe no authentication, replay check or signature on the mailbox. In auto mode the classifier reviews each message between agents before delivery, which bears on D5-A2A-SCREEN at L4.[^teams-msg]
- **A hostname allowlist can meet D5-ALLOW and fails D5-INSPECT.** The built-in proxy decides from the client-supplied hostname without inspecting TLS, so code in the sandbox can potentially use domain fronting to reach hosts outside the allowlist, and a broad entry such as `github.com` can itself create a path for data exfiltration.[^sbx-limits] D5-INSPECT, at L4, requires the proxy for the connections an agent's code and commands open to terminate TLS and refuse a request whose inner host differs from the name the connection was allowed on. The experimental `network.tlsTerminate` terminates TLS for credential masking without adding content filtering, and Anthropic directs a stronger threat model to a custom proxy that terminates TLS and inspects traffic, so a fronted request refused at the proxy is the evidence for either.[^sbx-limits][^sbx-proxy]
- **The L5 closure needs the network around the host.** D5-GATEWAY-ONLY and D5-SSRF read every route an agent's processes can take, and the sandbox's proxy route, which a custom proxy reached through `httpProxyPort` and `socksProxyPort` can take over, holds shell commands and their children alone.[^sbx-network][^sbx-proxy]
- **Rule DR-001 caps D5 at D2's raw score.**

## 6 — D6 Data, Memory and RAG

- **D6-EXTEND has a trust gate for project MCP servers.** From v2.1.196 a cloned repository cannot approve its own `.mcp.json` servers, which wait for the workspace trust dialog.[^mcp-trust] Under `claude -p` in a folder never trusted they connect without asking, as the D4-SANDBOX-FIRST bullet sets out. The `vcs.*` attributes name the repositories the sessions run in, and with `OTEL_LOG_TOOL_DETAILS=1` `mcp_server_connection` names each server.[^mon-repo][^mon-mcp] D6 records that no product in its control landscape applies a data classification to a repository.

The header on a subagent's report marks another agent's output, as the D4-INJECT-INDIRECT bullet sets out, and gives no source a trust level.

- **D6-INSTRUCT reads the instruction files, and the baseline comes from the organization.** Its files are the ones the agent loads as instructions, CLAUDE.md, `.claude/rules/` files, AGENTS.md and a subagent's definition among them. The settings files, hooks and `.mcp.json` are the agent's configuration, which D4-SANDBOX-CONFINE and D3-MEDIATE-OUTSIDE grade. A managed CLAUDE.md, deployed as a file or through the `claudeMd` key, cannot be excluded.[^mem-managed][^mem-exclude] `InstructionsLoaded` fires as CLAUDE.md and rules files load, cannot block, and does not fire for an AGENTS.md read directly.[^hk-instr] A `SessionStart` hook can check every instruction file against its baseline and return `watchPaths` for them, and a `FileChanged` hook then checks a file again whatever changed it, each raising an alert on a mismatch.[^hk-session][^hk-filechanged] `ConfigChange` hooks and the protected paths the D3 second artifact describes cover the settings files, skills, agents, hooks and `.mcp.json`, and neither reaches a CLAUDE.md at the repository root.[^hk-config][^sbx-protected] The same baseline evidences D8-VERIFY-INSTRUCT only where its digest traces to a signed revision or a release's pin and a mismatch stops the load, which no hook can do, as the D8-VERIFY-INSTRUCT bullet sets out.
- **D6's store criteria have no instance in the harness.** A store holds a copy of corpus content for the retrieval layer. Claude Code reads the working copy through its file tools, and the local state the pages describe is transcripts, history, file snapshots and memory, with no index or embeddings.[^cd-clear] Transcripts hold copies of what a session read, unencrypted at rest,[^cd-plain] and they are session state kept so a session can resume, which the store criteria do not range over. An MCP server or an editor extension that indexes content keeps a store, and D6 grades it on that component.
- **D6-SCOPE's excluded paths are enforced for the file tools and sandboxed commands.** Read and Edit deny rules cover the built-in file tools and the file commands Claude Code recognizes in Bash, and miss a script that opens files itself.[^perm-read] The sandbox's default read policy covers the whole machine until `denyRead` narrows it.[^sbx-fs] `permissions.blockReadsOutsideWorkingDirectories`, from v2.1.257, makes the Read, Grep, Glob and LSP tools refuse reads outside the working directories in every mode, and makes a recognized file-reading Bash command prompt even in auto and bypass modes.[^sr-blockreads] The scope decision naming each repository's excluded paths is the organization's record.

A cloud session reaches GitHub with the developer's token, which the proxy swaps in for a scoped credential inside the VM, and its API requests reach only the repositories attached to the session, as the D2 cloud bullet sets out.[^ce-github] An interactive `@claude` run acts for the commenter, whose write access the action checks, and reads under the Claude GitHub App's grant,[^gha-trigger][^gha-params] so D6-ENTITLE holds there only where the app reaches no repository the commenter cannot read.
- **D6-ENTITLE-TASK reads the CI token's reach.** An automation-mode run starts on an event or a schedule with no asking principal and reads what the Claude GitHub App installation or the passed `github_token` reaches.[^gha-params][^gha-app] An organization installs the app on all its repositories or on a selected list,[^gha-org] and D6-ENTITLE-TASK sets that reach against the repositories the workflow's task reads.
- **Memory is partitioned by repository and by subagent.** Auto memory lives at `~/.claude/projects/<project>/memory/`, keyed to the git repository, and a repository-chosen `autoMemoryDirectory` is honored only under workspace trust.[^mem-auto] The main conversation's auto memory is not loaded into subagents, and a subagent's `memory` field gives it a directory of its own at user, project or local scope.[^mem-how][^sub-memory] Under `permissions.blockReadsOutsideWorkingDirectories` the file tools refuse another repository's memory directory,[^sr-blockreads] while a project-scope subagent directory sits inside the working copy, where every agent in the session can read it.
- **Memory writes are held by permission rules.** Writes under the project's `.claude` directory, where project-scope subagent memory and rules files sit, are protected: prompted in default and `acceptEdits` modes, routed to the classifier in auto mode, denied in `dontAsk` and allowed in `bypassPermissions`.[^pm-protected] A CLAUDE.md at the repository root is no protected path, so a session in `acceptEdits` or auto mode edits it unasked unless a deny rule names it,[^pm-accept][^pm-classifier] and D6-MEMORY-WRITE fails an instruction file every session can change unasked. `autoMemoryEnabled: false` turns auto memory off.[^mem-toggle]
- **The harness stamps a memory write's time.** When Claude writes a memory file that begins with YAML frontmatter, Claude Code records the write time in a `modified` field, from v2.1.214, and it adds no frontmatter to a file without it.[^mem-how] Claude writes the `type` field itself, and no field in the pages read records the writing session or the source, so D6-MEMORY-PROVENANCE takes those from outside the harness. The D7 memory-write bullet covers the telemetry record of the same write.
- **Rollback rests on version control.** A subagent's `project`-scope memory sits in the repository, shareable through version control,[^sub-memory] so where the team commits it the repository's history restores an earlier state, and an instruction file the agent edits is restored the same way. Auto memory is machine-local and stays until someone edits or deletes it,[^mem-auto] and the pages read describe no history for it, so a backup the organization runs restores it. D6-ROLLBACK also asks for a test that restored each store.

| L4 | D7-LOG-OUTSIDE | None native. A managed `http` `PreToolUse` hook can send each call to a decision service outside the session | The service's record of each call, and its store's access policy against the developer's identities | external |
| L4 | D7-LOG-TAMPER | A hook in managed settings, which `disableAllHooks` from other scopes cannot turn off | A test from each identity the session holds against the service's pipeline and store | external |

- **Identity on the events depends on the route.** With a Claude account the events carry `user.email`, `user.account_uuid` and `organization.id`, and on a gateway `user.id` is the IdP subject. With an API key or a cloud-provider route only `user.id` and `session.id` exist, and `user.id` identifies an installation, so `OTEL_RESOURCE_ATTRIBUTES` set through managed settings attaches the user.[^mon-attr] D7-LOG and D7-ATTRIBUTE read the human under D7's grading word "names", which the route's identity attribute meets where it resolves to one person.
- **MCP calls need `OTEL_LOG_TOOL_DETAILS=1` for D7-LOG.** Without it an event names a user-configured MCP server's tool only as `"mcp_tool"`, a record from which D7-LOG cannot read the tool.[^mon-mcp] Content capture is otherwise off by default: prompts, tool details, tool content and raw API bodies each need their own opt-in.[^mon-common]
- **Managed settings pin the destination and leave the selectors per key.** A managed `OTEL_EXPORTER_OTLP_*` variable removes conflicting developer-set endpoints and credentials, while the exporter selectors follow normal precedence, so a developer's setting can disable a signal unless managed settings set the selectors too.[^mon-lock] Spawned processes receive no `OTEL_*` variables.[^mon-admin] A session signed in to a Claude apps gateway exports to the gateway, which forwards metrics by default, logs and traces only to a destination that opts in to them, and discards a signal no destination takes.[^gwc-telemetry] The test that export holds disables it from user settings, project settings and a Bash command, and confirms the events still arrive in the store.
- **A gateway or cloud-provider route takes sessions off the analytics dashboard, and OpenTelemetry stays.** OpenTelemetry metrics work on every provider.[^fa-every] For the sessions a gateway or a cloud-provider endpoint carries, D7-LOG and D7-LOG-SCHEMA are met only by the exported tool events, each joined to its session and naming the developer, which on a cloud-provider route takes the `OTEL_RESOURCE_ATTRIBUTES` entry the identity bullet describes.
- **The spans are Claude Code's, with a few GenAI attributes.** Each prompt starts a `claude_code.interaction` root span with `claude_code.llm_request`, `claude_code.tool` and, under detailed beta tracing, `claude_code.hook` children, and a subagent's spans nest under the Agent tool's span. The model-request span carries `gen_ai.system`, `gen_ai.request.model` and `gen_ai.response.id`, and a tool span carries `gen_ai.tool.call.id`.[^mon-traces] The conventions name an inference span `{gen_ai.operation.name} {gen_ai.request.model}`, require `gen_ai.operation.name` and `gen_ai.provider.name`, which replaced `gen_ai.system`, and define execute-tool and invoke-agent spans.[^otel-genai] D7-SPANS therefore needs a collector that renames Claude Code's spans and maps their attributes, turning the Agent tool's span into an invoke-agent span. Traces are beta, so a trace-based verdict records the date they entered production.
- **The convention version is the organization's to name.** The monitoring documentation names no convention version, and `gen_ai.system` predates the rename in semantic conventions v1.37.0, so the collector's mapping names the release or commit it follows.[^mon-traces][^otel-genai] Managed `requiredMinimumVersion` and `requiredMaximumVersion` set to one release pin the harness that emits the spans, because each refuses to start a version outside its bound.[^sr-version]
- **An agent is one configuration, so attribution turns on the inventory.** D7-ATTRIBUTE counts an identity in the record, in a record joined on a session identifier, or in metadata the pipeline adds, where it resolves to one agent in the inventory. Every metric and event carries `service.name`,[^mon-service] `OTEL_METRICS_INCLUDE_REPOSITORY=true` adds the repository's `vcs.*` identity,[^mon-repo] and under `OTEL_LOG_MANAGED_SETTINGS=1` the session's `managed_settings_resolved` event carries the policy digest,[^mon-msr] so records joined on `session.id` resolve to one configuration where the inventory registers each policy variant and repository as an agent. A managed `OTEL_RESOURCE_ATTRIBUTES` entry per policy variant can name the agent directly. A subagent is a different agent, and `tool_result` events carry no agent attribute, so a subagent's calls name it only on traces, where each tool span carries `agent_id` and nests under the Agent tool's span, which names the subagent type with `OTEL_LOG_TOOL_DETAILS=1`.[^mon-traces]
- **The action schema carries a write reference for commits and file edits.** With `OTEL_LOG_TOOL_DETAILS=1`, `tool_result` gives the arguments in `tool_input`, each value truncated at 512 characters, the outcome in `success` and `error_type`, and `tool_use_id`, `prompt.id` and `session.id` to join the rest of the session.[^mon-toolresult] The target resource sits in the arguments: a file path, a command line, or an MCP server, tool and call arguments. A successful `git commit` adds its commit SHA,[^mon-toolresult] and with `OTEL_LOG_TOOL_CONTENT=1` beside the details flag an Edit's `tool.output` span event carries the patch it applied.[^mon-tooloutput] Another write, such as a file a Bash command writes or a record an MCP tool creates, carries a reference only where the tool's result names one and detailed beta tracing, outside the stable span schema, records that result, so D7-LOG-SCHEMA takes those references from outside the harness.
- **A memory write is recorded where a file tool makes it.** A subagent with a `memory` field manages its own memory directory through the Read, Write and Edit tools, and Claude writes the main session's auto memory as files under `~/.claude/projects/<project>/memory/`.[^sub-memory][^mem-auto] A write through a file tool emits a `tool_result` event with its time and session, and `OTEL_LOG_TOOL_DETAILS=1` adds the file and the arguments, the written text among them, while the writing subagent is named only on traces, as the attribution bullet sets out. The pages read do not name the tool behind a main-session memory write, so a sampled write set against its file shows whether the record exists. A CLAUDE.md the agent edits is agent memory under D7's grading word, and one record can evidence D7-LOG-SCHEMA and D7-LOG-MEMORY. D7-LOG-MEMORY is not applicable only where auto memory is off, no subagent sets `memory` and deny rules keep the agent from editing instruction files.
- **The sandbox reports two of the three indicator classes, in the command's result.** Claude Code names each path or host the sandbox denied in the blocked command's result, and Claude may retry the command outside the sandbox with the `dangerouslyDisableSandbox` parameter, which Bash events carry in `tool_parameters` with `OTEL_LOG_TOOL_DETAILS=1`.[^sbx-retry][^mon-toolresult] The result reaches the telemetry only as tool content under the trace content flags, and the pages read name no system-call class, so D7-FORWARD-ESCAPE's three classes reach the backend through a collector on the host.
- **Ingest-scan forwarding is not applicable where no ingest scan runs.** D6-SCAN grades the scan itself, at D6 L3.
- **Baselines and drift scoring run in the SIEM.** Claude Code emits the raw event stream only.[^mon-map] A baseline of each agent's tool calls reads `tool_result` events grouped by configuration, as the attribution bullet resolves it. D7-DRIFT scores each session across its turns, which `prompt.id` separates, for a refused request that a later turn fulfils or for tool calls that widen from turn to turn, and `tool_decision` rejections and `api_refusal` events mark the refusals.[^mon-decision][^mon-refusal] The disposition each drift alert reaches, review by a named role or suspension of the session, is D7-DRIFT-ROUTE's and sits outside the harness.
- **Control-state signals are native.** `permission_mode_changed` reports mode escalation, `managed_settings_resolved` the sources, the policy helper's health and the digest, and `plugin_installed` and `hook_registered` additions to the configuration,[^mon-map][^mon-hookreg] beside the two policy-change sources the D2-AUDIT bullet names. D7-CONTROL-RELAX reads a mode escalation, a changed policy digest and a hook missing from a later session's registrations as relaxations, and the rule that alerts on each is the SIEM's.
- **An approval turned automatic shows on `tool_decision`.** The event's `source` reads `config` for a call decided without a prompt, a session-scoped grant from an earlier prompt included, `hook` for a hook's decision, and `user_temporary` or `user_permanent` for a person's answer.[^mon-decision] A rule that alerts when a call an ask rule covers is decided by `config` or `hook` meets both of D7-CONTROL-APPROVE's cases, an action that needs an approval running with none and an approval step that starts approving without a person, and it reads the managed rule set beside the event, because `config` does not say which rule or mode matched. In Agent SDK and `-p` sessions a later call under a person's earlier grant still reads `user_temporary` or `user_permanent`, so the rule there matches each call with the prompt that granted it.
- **The harness's own events count toward no part of D7-LOG-OUTSIDE.** D7 excludes the agent's own spans and log lines whoever ships them, so neither the managed endpoint nor the gateway's relay makes them an outside record, and the Claude apps gateway stores no prompt or completion content, so it keeps no record of a tool call.[^gw-see] A managed `http` `PreToolUse` hook can send each call to a decision service outside the session, which writes a record of its own, and a hook that times out or cannot connect lets the call continue, so that record misses those calls.[^hk-timeout][^hk-http] D7-LOG-TAMPER tests the service's record from each identity the session holds, and a hook deployed in managed settings stays on when user, project or local settings set `disableAllHooks`, as far as the managed source holds against a developer who administers the machine.[^hk-disable][^ms-dev] The same writer rule governs D7-ORCHESTRATE, so the `subagent_completed` events and the nested subagent spans are the orchestrator's own record.
- **Rule DR-002 caps D7 at D2's raw score.**

## 8 — D8 Supply Chain and AI-BOM

[[agentic-ai-security-cmm-d8-supply-chain|D8]] sets the coding shape's highest target, L4, because slopsquatting lands on the dependency channel, and its right-sizing puts the harness configuration tree, as [[harness-config-as-supply-chain-artifact|Harness Config as Supply-Chain Artifact]] describes it, in scope. - **The inventory is read per device, from device management and the event stream.** D8-INVENTORY lists each component on each device the organization's device management reports, so a device that stops reporting fails it. `plugin_loaded` records each enabled plugin at session start with its marketplace, scope and declared version, `mcp_server_connection` each server and whether a plugin provides it, and `skill_activated` each skill a session invokes with its source, and third-party names appear only under `OTEL_LOG_TOOL_DETAILS=1`.[^mon-plugin][^mon-mcp][^mon-skill] `claude plugin details <plugin>` prints an installed plugin's component inventory.[^dp-sec] None of the events the monitoring page lists gives an MCP server's version or source, or any component's maintainer or digest, so those fields come from the organization's marketplace entries and the allowlist the D8-ABILITY-SOURCE row sets.
- **Versions are in the telemetry, apart from MCP servers.** Every metric and event carries `service.version`, the running Claude Code version or, for a Desktop Code tab session, the Desktop app's, and each `api_request` event names the model the call used, the record D8-VERSION accepts for an alias.[^mon-service][^mon-api] `plugin_loaded` carries the version a plugin's manifest declares, where the name is not redacted.[^mon-plugin] D8-VERSION reads twelve months of that record, which the organization's backend keeps, and an MCP server's version comes from the command the allowlist admits, where that command names one. Pinning a version is D9's.
- **D8-AIBOM reads each release of the agent.** A managed configuration the organization's device management pushes is a release, and so is a runner image the organization builds with the harness inside. A setting changed in the claude.ai admin console is no release, so a deployment configured only through server-managed settings holds no instance of D8-AIBOM or D8-AIBOM-RUNTIME. The AI-BOM lists each model with its version, each plugin, skill and MCP server, each library and each configuration file the agent loads, with the digest of each file the release holds, in CycloneDX 1.5 or later or SPDX 3.0, and the pages read describe no command that writes one.
- **Package installs lock only where a plugin ships a lockfile.** Claude Code installs a plugin's Node.js dependencies with `npm ci --ignore-scripts` or `bun install --frozen-lockfile --ignore-scripts`, which install exactly what the lockfile pins, and it skips, without a log entry, a plugin that ships a `package.json` and no lockfile.[^plg-deps] An npm plugin source takes a version or a range,[^pmk-sources] `npm install -g` installs the harness by name,[^setup-npm] and an MCP server started through `npx`, as the allowlist examples show, fetches its package by name, so each of the three fails D8-DEPS-LOCK.[^mmcp-lock] D8-DEPS-SCAN reads the pipeline that installs the harness or builds a runner image, and the pages read describe no scan in the harness.
- **The install-time check sits at the registry.** By default the auto-mode classifier blocks downloading and executing code, such as `curl | bash`, and from v2.1.195 routing a package install around an internal registry to a public one, and an ask rule on an install command matches text and is advisory.[^pm-blocks][^perm-bash] A sandbox allowlist naming only the internal registry bounds where a sandboxed install fetches from, while hooks and MCP servers run outside the sandbox.[^dp-sec] D8-DEPS-INSTALL is met only where that registry refuses a package that fails a check of its name, its publisher and its age.
- **The model criteria have no instance.** Each session calls a model Anthropic or a cloud provider hosts, so no file of it loads on a system the organization runs, and D8-MODEL-SCAN, D8-MODEL-INSPECT, D8-MODEL-PROBE and D8-VERIFY-BUNDLE are not applicable.
- **A hosted runner and a cloud session's VM are systems the organization runs.** D8 counts a runner or a virtual machine that a service provides for the organization's own jobs, such as a GitHub-hosted runner, as a system the organization runs, and the sheet reads the VM a cloud session runs on the same way. The plugins, skills, MCP servers and instruction files that a CI run or a cloud session loads therefore fall under D8-ABILITY-SCAN, D8-VERIFY and D8-VERIFY-INSTRUCT, and under D8-SIGN-MCP at L5+.
- **Ability approval is allowlisting, and a public marketplace is a class.** `strictKnownMarketplaces` matches marketplace sources and restricts no entry inside an allowed marketplace, so admitting a public one, the official marketplace included, admits every plugin in it, and D8-ABILITY-SOURCE fails for each. A managed `enabledPlugins` entry set to `false` blocks one plugin.[^pmk-restrict] The approval record is the organization's own marketplace: a repository whose `.claude-plugin/marketplace.json` lists each reviewed plugin with its author and source, and the only marketplace `strictKnownMarketplaces` admits.[^pl-create][^pmk-sources] `disableSideloadFlags` rejects the sideload flags, `syncClaudeAiPlugins: false` stops the plugins synced from members' claude.ai accounts, and `strictPluginOnlyCustomization` blocks skills, agents, hooks and MCP servers from user and project sources.[^pmk-restrict][^as-enforce] For MCP servers, `allowedMcpServers` with `allowManagedMcpServersOnly: true` makes the managed allowlist authoritative, matching a stdio server by its exact command and a remote one by its URL, and a `serverName` entry is no security control.[^mmcp-lock] On Team and Enterprise plans only admins add claude.ai connectors, which in Desktop sessions bypass the MCP allowlist, as the D5 MCP bullet sets out.[^mcp-claudeai] From v2.1.277 a managed `strictKnownMarketplaces` that fails validation is enforced as an empty allowlist.[^ms-failclosed]
- **The scan runs outside the harness.** A plugin can execute arbitrary code with the user's privileges, and the plugin pages read describe a trust warning, to which `pluginTrustMessage` appends the organization's text, and no scan of a plugin's contents.[^dp-sec][^pmk-restrict] Anthropic's Enterprise skill and plugin scanning checks each third-party skill or plugin a member or owner uploads, on Enterprise plans in Claude, Claude Cowork and Enterprise plugin marketplaces, before it can run in the organization. It scans no hook or MCP server, and it is off by default until 2026-10-02.[^claude-scan] A remote MCP server installs nothing on a system the organization runs, so D8-ABILITY-SCAN is not applicable to it. A scan the organization runs meets the criterion where it reads each plugin, skill and local MCP server version before the allowlist admits it.
- **The supplier assessment starts from Anthropic's documents**, the Trust Center reports the D1-ALLOCATE bullet names among them. Anthropic reviews connectors against its listing criteria before listing them and does not security-audit or manage any MCP server,[^sec-mcp] and its plugin trust warning states that it does not control what a plugin includes.[^dp-sec] D8-SUPPLIER reads each supplier on the seven evaluation items: Anthropic, the cloud provider where the model runs on Bedrock, Agent Platform or Foundry, and each marketplace publisher and MCP server supplier. Zero Data Retention disables cloud sessions and Remote Control where it is enabled,[^zdr] and a BAA extends to Claude Code traffic where ZDR is enabled.[^lc-baa]
- **Signing is the organization's.** D8-SIGN reads each artifact the organization builds for a release, such as a plugin or skill revision its marketplace distributes, which a signed commit signs, or a plugin archive. D8 counts a managed configuration the organization's device management pushes as a release of the agent it defines and each file it ships as an artifact D8-SIGN reads, so the managed settings file, or the MDM profile that carries it, needs a signature too. A `sha` pin or an archive `sha256` checks integrity and signs nothing, the plugin pages read describe no signature check on a plugin, a marketplace or an MCP server,[^pmk-sources][^pmk-archive] and the managed-settings page describes none on a managed source.[^ms-when]
- **Verification holds for pinned plugins and for package-manager installs of the harness.** A marketplace entry that pins a git source to a full commit `sha` makes Claude Code check out that commit, an archive pinned to a `sha256` digest is refused on a mismatch, and the community catalog pins nearly every entry to a commit.[^pmk-sources][^pmk-archive][^dp-sec] A marketplace source takes a `ref` and no `sha`, so a plugin stored inside the marketplace carries no pin, and neither does an npm source at a version or an MCP server fetched at launch. D8-VERIFY counts such a pin where managed settings bind the installer to the marketplace that holds it. For the harness, apt, dnf and apk check the repository's signature. On Linux a native install or a direct download is checked against the signed release manifest by hand, macOS and Windows binaries carry platform code signatures, and the pages read document no check by the auto-updater, which leaves a self-updating native install unanswerable.[^setup-integrity] `DISABLE_UPDATES` blocks every update path, for an organization that distributes a verified build itself.[^setup-updates]
- **D8-VERIFY-INSTRUCT needs a stop no hook can give.** The D6-INSTRUCT hooks check a baseline and raise an alert, and `SessionStart`, `InstructionsLoaded` and `FileChanged` hooks have no decision control, so none of them stops an instruction file loading.[^hk-decision][^hk-instr] D8-VERIFY-INSTRUCT also needs the digest to trace to a signed revision or a release's pin, such as a rules file in a signed commit or a prompt built into a runner image deployed by digest, and a check outside the harness that stops the load on a mismatch.
- **Runtime reconciliation needs the release AI-BOM.** The load events, aggregated per device, and `managed_settings.resolved_sha256`, exported under `OTEL_LOG_MANAGED_SETTINGS=1`, are the runtime record.[^mon-msr] D8-AIBOM-RUNTIME reconciles that record against the AI-BOM of the managed configuration released, at each deployment and on a schedule the organization sets, and records each difference as a finding, so a runtime inventory with nothing to reconcile against fails it.
- **Disclosure response raises a floor that fails open.** `requiredMinimumVersion` refuses start below the floor, and like `requiredMaximumVersion` it drops an invalid value by design.[^sr-version][^ms-failclosed] D8-DISCLOSE also needs an intake source for each component type, the advisories of each plugin and MCP server included, and the [[claude-code|Claude Code]] entity page tracks the harness advisories a floor responds to.
- **Containment uses the harness's own switches.** The procedure D8-DISCLOSE-CONTAIN reads names four compensating controls, and Claude Code carries one for each: a deny rule or a managed `enabledPlugins` entry set to `false` restricts the affected tool, the sandbox network allowlist narrows its reach, the `OTEL_LOG_*` content gates raise monitoring, and `deniedMcpServers` disables an affected server.[^pmk-restrict][^mmcp-lock][^mon-common] The procedure and each containment record are the organization's.
- **Retirement reads the model's warning and the marketplace's removals.** When the requested model has a scheduled retirement date, Claude Code shows a warning naming it.[^mc-retire] A marketplace has no deprecation state, so the organization removes a retired plugin's entry, and `forceRemoveDeletedPlugins` uninstalls it from users' machines, apart from a plugin only managed settings installed.[^hm-remove] The review, its cadence and its inactivity rule are the organization's.
- **Registry write access turns on the credentials a session can read.** D8 counts a token in a package manager's configuration file or in the environment as an identity the agent holds. `sandbox.credentials` deny entries deny such a file and unset such a variable for sandboxed commands, a `Read` deny rule covers the file tools, and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips credentials embedded in package registry URLs, and the variables Claude Code recognizes as credentials, from the Bash tool, hooks and MCP stdio servers.[^sbx-creds][^perm-read][^env-vars] A deployment whose sessions can read no registry write token holds no instance of D8-REPO-WRITE, while hooks and MCP servers run outside the sandbox and can still read such a file.[^dp-sec] Where a session must publish, the repository's own permissions decide the criterion.

## 9 — D9 Operations and Human Factors

[[agentic-ai-security-cmm-d9-operations|D9]] grades the operating model around the agents. For a coding deployment its load-bearing question is approval fatigue, which D9 names as the mechanism that converts an interactive deployment into an unattended one. The sheet maps 25 of D9's 47 criteria, all graded per deployment. The other 22 fall into three groups:

- **Organization criteria, graded once for the organization.** The assessment grades each once and reports it beside the deployment matrices, and one not met or unanswerable holds every deployment below its level in D9. They are the disclosure community, the AI security role and a deputy for each duty, and the AI incident playbook with its exercise, its notification path and its compromised-model scenario at L3 (D9-SHARE, D9-ROLE, D9-ROLE-DEPUTY, D9-IR, D9-IR-EXERCISE, D9-IR-NOTIFY, D9-IR-SCENARIO), the coordinated-disclosure exercise at L4 (D9-SHARE-EXERCISE), the deputies' continuity test at L5 (D9-ROLE-CONTINUITY), and published metrics, standards contribution and disclosure coordination at L5+ (D9-PUBLISH, D9-STANDARDS, D9-SHARE-LEAD).

- **A criterion with no instance in the harness.** D9-MODEL-DEPRECATE applies only where the deployment publishes a model, skill, MCP server or agent for use outside the organization, such as a plugin in a public marketplace.

- **Anthropic runs part of the operations.** Anthropic writes Claude Code's own system prompt and runs its safety classifiers, the auto-mode classifier, and the server-side probe and review, so D9 grades each on the evidence Anthropic produces or on a customer test, and the runbooks, the playbook and the measures stay the organization's.[^mc-fallback][^pm-classifier][^pm-server]
- **A hook that fails lets the event proceed.** A command, HTTP or MCP tool hook that errors, cannot start or times out renders no decision, and what follows depends on its event:[^hk-errors][^hk-http][^hk-timeout]
  - On `PreToolUse`, the call continues through the permission flow.
  - On `UserPromptSubmit`, the prompt reaches Claude without the hook's context.[^hk-prompt]
  - On `PostToolUse`, the result reaches Claude unchanged.[^hk-posttool]
  - On `MessageDisplay`, the original text is displayed.[^hk-msgdisplay]
- **An Agent SDK callback, the auto-mode classifier and server-side review fail closed.** An Agent SDK callback that times out blocks the tool call on `PreToolUse` and the prompt on `UserPromptSubmit`.[^hk-timeout][^hk-prompt] The auto-mode classifier denies an action it returns no verdict for, and server-side review denies one the server returns none for.[^pm-fallback][^pm-server] After 3 consecutive or 20 total blocks, auto mode pauses and prompting resumes, at thresholds that are not configurable.[^pm-fallback] The pages read state no failure behaviour or latency for Anthropic's safety classifiers or the server-side probe, and no customer test can make either fail or separate its latency from the request's, so D9's vendor-held rule leaves D9-GUARD-FAILMODE and D9-GUARD-LATENCY unanswerable for both, and D9-GUARD-RUNBOOK short of met, as the D9 bullet in the domain summary sets out.
- **Owner departure ends a person's access, and the runbook states what happens to their agents.** A routine belongs to one person's claude.ai account and acts as that person on GitHub and through connectors, and the pages read describe no transfer to another account, so D9-OFFBOARD's step for a leaver's routine retires it.[^rt-create] An Owner's Routines toggle stops every routine at once.[^rt-toggle] A token from `claude setup-token` lasts a year, is tied to the subscription of the person who generated it and has no revocation route in the pages read, so a CI secret holding one falls under D9-OFFBOARD-CREDS when that person leaves, while federation leaves CI no stored key.[^auth-token][^gha-wif] A gateway session ends within `ttl_hours` of the person's deprovisioning in the IdP.[^gw-enforced]
- **The approval record is the event stream, and the measures are the organization's.** `tool_decision` reports `config` for a decision a rule, a mode or an earlier session grant made, `hook` for a hook's, and `user_temporary`, `user_permanent`, `user_reject` or `user_abort` for a person's answer at a prompt, and a `config` decision does not name the rule that matched.[^mon-decision] Each tool call's `claude_code.tool.blocked_on_user` span in the beta traces carries the wait for its decision in `duration_ms`, with the decision and its source.[^mon-traces] Claude Code keeps a permission prompt open until the person answers, so no request expires, and `user_abort` records a prompt dismissed unanswered.[^rc-limits][^mon-decision] Claude Code emits the raw events and leaves baselining and alerting to the backend,[^mon-map] so the organization computes each measure for each approval path and period: the approval rate, the median and 95th-percentile queue age, and the rubber-stamp rate, which D9 defines as the share of approvals given with no sign of review by a method the organization states, such as an approval given within a stated number of seconds of its prompt. The analytics dashboard's suggestion accept rate reads code-editing suggestions only, Edit, Write and NotebookEdit among them.[^an-summary] An estate where no call can prompt, such as a CI run in `dontAsk`, holds no approval path, so the QUEUE and OVERSIGHT rows are not applicable to it.[^pm-dontask]
- **The system prompts D9 reads are the organization's standing instructions.** The managed CLAUDE.md, or the managed `claudeMd` key, reaches every session on a device and cannot be excluded, a repository's CLAUDE.md and rules files reach the sessions in that repository, and a developer's own user and local CLAUDE.md files sit outside the organization's configuration.[^mem-managed][^mem-where] `InstructionsLoaded` reports each CLAUDE.md or rules file as it loads, with its scope, and cannot block the load.[^hk-instr] D9-PROMPT-CLEAN reads each of the organization's files for a credential or key, a database name, the users' roles and the permission structure, and the pages read describe no check of that content in the harness. It reads Claude Code's own system prompt, which is vendor-held, from a customer test such as the leak probes the canary bullet names.
- **Two hooks the organization writes carry the canary check.** A canary planted in the managed CLAUDE.md reaches every session's context, a `PreToolUse` hook receives each tool call's full input before it runs, and a `MessageDisplay` hook receives each reply's text, so the two hooks can check both and raise the alert.[^hk-pretool][^hk-msgdisplay] The event stream covers less: on `tool_result`, `tool_input` truncates each value over 512 characters and the whole payload at about 4,000 characters, and `assistant_response` redacts the reply text by default.[^mon-toolresult][^mon-response] Claude Code's own system prompt is Anthropic's: leak probes can test it, and the pages read document no canary check in it, which no customer can plant. D9's vendor-held rule therefore leaves D9-PROMPT-CANARY unanswerable for that prompt unless a run replaces it with `--system-prompt`, which also drops its tool guidance and safety instructions.[^cli-sysprompt] D9-PROMPT-PROBE runs the probes before each change to the instructions or the model reaches production.
- **Guardrail latency arrives per hook event, and cost per request.** `hook_execution_complete` carries `total_duration_ms`, and the detailed beta `claude_code.hook` span `duration_ms`, each the wall-clock time of all the hooks matching one event, so a series for each guardrail needs one guardrail hook per event and matcher, or a hook that times itself.[^mon-hookdone][^mon-traces] Each `api_request` event carries its `cost_usd`, `duration_ms` and `query_source`, and `claude_code.cost.usage` the session's cost by `query_source`, `agent.name` and `skill.name`.[^mon-api][^mon-metrics][^mon-cost] The auto-mode classifier's calls count toward token usage on Enterprise plans, the Claude API and cloud providers, each check adds a round trip before execution, and the monitoring page names no `query_source` value for those calls.[^pm-fallback] Server-side review makes no separate calls and so carries no charge of its own, which puts it outside D9-GUARD-COST, and the pages read name no charge for Anthropic's safety classifiers.[^pm-fallback] A hook that calls an outside classifier is billed outside the harness.
- **Failing closed turns on the hook's event.** Where an agent can make a high-impact call, D9-GUARD-FAILMODE holds each guardrail on its model calls to fail closed. A `PreToolUse` guardrail fails closed only where the permission flow then holds or denies the call, which an allow rule does not, and a `UserPromptSubmit` guardrail only as an Agent SDK callback.[^hk-timeout][^hk-prompt] The pages read describe no fail-closed route for a `PostToolUse` hook, so the classifier on tool results that the D4-INJECT-INDIRECT row names fails the criterion, and so does the D4-INJECT-DIRECT row's prompt classifier unless it runs as an Agent SDK callback.[^hk-posttool] The test makes each guardrail error or time out: the organization stalls or breaks each hook, and for server-side review the documentation names a proxy that cuts the review results off as one cause of a missing verdict.[^pm-server]
- **The reaper runs outside the harness.** D9-REAP sweeps for orphaned agents and orphaned credentials on a schedule, so the events that end access bound what the sweep finds and meet no part of it: a gateway session ends within `ttl_hours` of IdP deprovisioning, cloud session VMs are reclaimed after inactivity, and a self-hosted session token stays valid until its expiry.[^gw-enforced][^sec-cloud][^shi-scope] The orphans a sweep finds include a leaver's routines and each CI secret holding a token a leaver generated.
- **Containment names the harness's stop controls and record stores.** Most changes in managed settings reach a running session without a restart: hourly from the admin console, every 30 minutes from device management, and when a managed file changes.[^ms-when] An Owner's Routines toggle stops every routine, IdP deprovisioning ends one person's gateway session within `ttl_hours`, and replacing the gateway's JWT secret outright, the only way to end sessions before they expire, ends every one at once.[^rt-toggle][^gw-rotate] The records sit in each device's transcripts under `~/.claude/projects`, kept in plaintext and deleted after `cleanupPeriodDays`, 30 days by default, in the OpenTelemetry backend, in the gateway's audit events and, for Anthropic-hosted cloud sessions, in Anthropic's audit logging.[^cd-auto][^cd-plain][^gw-logs][^sec-cloud] A vulnerability in the harness goes to Anthropic through its HackerOne program, a step the playbook takes with the vendor.[^sec-report] D9-IR-CONTAIN reads these steps for the deployment, and D9-IR the playbook the organization keeps for all its AI systems.
- **High-risk approval needs a service outside the session for its delay and its second approver.** The category definitions along the Exchange's four dimensions are the organization's record, and managed ask rules apply them to tool names, paths and command text, while a financial threshold or a data class inside a call's arguments needs a `PreToolUse` hook.[^perm-bash][^hk-pretool] The prompt reaches whoever holds the session. A `PermissionRequest` hook, or in a `-p` run `--permission-prompt-tool` or a `PreToolUse` hook that defers the call, hands the decision to an approval service the organization runs, which can hold a call for the policy's delay and route a critical action to two approvers in different roles.[^hk-permreq][^cli-flags][^hk-defer] A `PermissionRequest` hook that renders no decision, a timed-out one included, leaves the prompt to the session's user, and where no prompt can show, the call is denied.[^hk-permreq][^hk-timeout]
- **The approval record needs a tamper-evident store.** D9's record holds the request, the parameters presented, the approver's identity and authentication method, the approver's explicit confirmation of the key parameters, the decision and the outcome. `tool_decision` with `OTEL_LOG_TOOL_DETAILS=1` supplies the request, its parameters and the decision, and `tool_result` the outcome.[^mon-decision][^mon-toolresult] Each event names the signed-in account, or on a gateway session the IdP identity, marked `identity.source: gateway-oidc`, and on an API key or a cloud provider only an installation identifier unless `OTEL_RESOURCE_ATTRIBUTES` attaches one.[^mon-std][^mon-attr] The authentication method follows from the sign-in route. A prompt records one yes or no for the call it showed, so the explicit confirmation and the tamper evidence come from the organization's approval service and its store.
- **The attribution lines carry the notice outside the organization.** Each developer works in the harness itself, so D9-NOTICE turns on the people outside the organization who receive what an agent sends with no person reviewing it first, such as the readers of a commit or a pull request a CI run pushes. Claude Code passes the `attribution` commit trailer and pull-request line to the model, which writes them, and a managed value outranks a repository's instructions to drop them.[^sr-attr] The pages read describe no notice on other content an agent posts, such as a review comment.
- **Approval volume changes the shape.** D9 reads a falling prompt count against a rising action count as a shape change, which rising `config` decisions against falling decisions from people, alongside `permission_mode_changed` events into `auto` or `bypassPermissions`, record in the organization's own data.[^mon-map]
- **The oversight path has no native limit or flag.** D9-OVERSIGHT-LIMIT holds or reroutes an approver's requests past a limit for a session or a window, and no setting in the pages read does so: auto mode's fallback thresholds count classifier blocks, and spend limits, the gateway's per-developer caps among them, cap what a person spends, which meets no part of the criterion.[^pm-fallback][^costs-org][^gw-spend] D9-OVERSIGHT-FLAG compares each approver's approval rate in a session with a historical baseline the organization defines, a detection the SIEM runs over the `tool_decision` stream.[^mon-map] D9-OVERSIGHT-TEST's four techniques are the testing programme's.
- **Model pinning covers the session model, its aliases and its fallbacks.** An alias such as `opus` resolves to the provider's recommended version and changes over time, while a full model name such as `claude-opus-5-5`, or `ANTHROPIC_DEFAULT_OPUS_MODEL` and its siblings, pins a version.[^mc-pin][^tpi-pin] `model` sets only the starting model, so `availableModels` with `enforceAvailableModels` holds the session and the Default option to the list.[^mc-control][^as-enforce] A request a safety classifier flags re-runs on a fallback model only where the allowlist permits it, and on a cloud provider it re-runs on the pinned `ANTHROPIC_DEFAULT_OPUS_MODEL` where one is set.[^mc-fallback] The auto-mode classifier runs on Sonnet 5 unless Anthropic configures another model server-side, and on the session's model, or an Opus model in a Fable session, where `availableModels` excludes Sonnet 5.[^pm-auto]

## Adaptation by deployment shape

- **Interactive local.** Every row applies, and the D9 approval rows carry the most weight, because the developer is the approver and prompt volume is the documented pressure on the shape.
- **Sandboxed autonomous local.** The D4 sandbox and D5 allowlist rows carry the weight. Set the three D4-SANDBOX settings in managed settings, and wrap the whole process in the sandbox runtime where MCP servers or hooks handle untrusted content.[^se-runtime]
- **Delegated cloud.** A one-repository session reads the repository's `.claude/settings.json`, hooks and permission rules included, so that file is policy and its changes fall under D1-HARNESS-REVIEW.[^set-cloud] A routine runs without stopping for approval, so no action in it waits for one: the D9 approval rows are not applicable to it, and on the D3 approval rows a rule has to refuse each destructive action.[^rt-create]
- **CI-runner agent.** Keep repository hooks, `env` and `.mcp.json` servers out of the run with the flags the D4-SANDBOX-FIRST bullet lists, and project skills, whose `allowed-tools` workspace trust never gates, with `--bare` or a managed `strictPluginOnlyCustomization`.[^perm-trust] Run in `dontAsk` or with `--permission-prompts none`, so a call that would prompt is denied.[^pm-dontask][^cli-flags] Authenticate through federation with a custom GitHub App, and deliver policy through the `settings` input or a managed file on the runner.[^gha-wif][^gha-app][^gha-params] D3-MEDIATE-FAILCLOSED holds the run below D3 L3 whatever else it meets, and [[claude-code-github-action-credential-exposure|Claude Code GitHub Action Credential Exposure]] is the case the shape is assessed against.
- **Fleet and parallel.** The D1-HARNESS digest, the D8 load events and the D9 decision stream carry the population view, `disableAgentView` turns off background sessions, and `processWrapper` prefixes the background supervisor and its workers with a required corporate launcher.[^as-enforce]

## Scoring and reporting

Score each domain with the protocol's rubric, whose score of 3 adds operational ID tagging and live observation, which static configuration never satisfies. The D3 section names the live records. An estate where no call can prompt, such as one running every session in `dontAsk`, records the gate fire not applicable, while one where an ask rule or a mode's default prompts and no fire is produced has not met the requirement.

Resolve effective scores and the headline under [[agentic-ai-security-cmm-dependency-rules|CMM: Effective-Score Dependency Rules]], whose active rules the D4, D5 and D7 sections apply. On Claude Code's controls alone, an interactive-local estate reports L1 raw in D2, and in D9 on a Fable, Opus 5.5 or Opus 5 model or in auto mode, L1 effective in D5 and D7, and L2 in the other domains, so its typical score is L2, its weakest L1 and its strongest L2.

The ceilings bound the harness's contribution and grade nothing. [[cmm-stress-test-canadian-fi-google-2026-09|CMM Stress Test: Canadian FI on Google Cloud]] grades a Claude Code estate for a regulated bank on the same domains, and a re-grade reads its evidence against these rows.
