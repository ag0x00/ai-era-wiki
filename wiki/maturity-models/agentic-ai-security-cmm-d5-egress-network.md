# Agentic AI Security CMM — D5 Egress & Network (Deep Dive)

D5 mediates agent egress at the network layer. The criteria below are written under the [[agentic-ai-security-cmm-recalibration-method-2026|recalibration method]], and [[agentic-ai-security-cmm-2026|the CMM]] grades each deployment against them. The LLM-egress gateway and the MCP-authorization leg are GA platform-native for an all-Microsoft buyer, so the residuals an assessor prices are few and named. Every criterion carries a name, D5 and a mnemonic such as D5-ALLOW, and §Assessor detail per level states each one with the evidence it names.

> [!gap] Single-source grounding
> The levels and the cost model synthesize the recalibration method against the [[agentic-cmm-regulated-fi-stress-test|regulated-FI stress test]] and vendor documentation. The status column of the control landscape is a May 2026 snapshot; rows re-read since carry their own retrieval dates in the notes.

**Three of the eight capabilities the control landscape tracks ship GA platform-native for a Microsoft shop, and a fourth ships in part.** The LLM-egress gateway, MCP brokering with authorization, and network-layer prompt-injection filtering with shadow-AI discovery run GA on the Azure and Entra stack. The third screens staff use of AI applications, and no D5 criterion grades it. Per-agent network policy is the partial one. Entra Agent ID names each agent, and Global Secure Access applies its network controls for Copilot Studio agents through one baseline profile per tenant.[^gsa-agents] Four capabilities are off-stack, and none blocks an L3 target:

- MCP tool-integrity and rug-pull detection, a residual the regulated-FI stress test names. D5-MCP-RUGPULL grades the in-path refusal at L4, and the fingerprint comparison D5-MCP-PIN grades at L3 runs as a registry-and-checksum pattern any stack can compose.
- Per-task capability tokens, the stress test's second residual, which D5-TASKTOKEN grades at L5+.
- A2A authorization beyond identity, its third, which the stress test lists as message signing, cross-agent access control lists and content-scanning rule packs. D5-A2A-SCREEN grades the content scanning at L4 and D5-A2A-SIGN the signing at L5, and no D5 criterion grades the access control lists.
- The mesh-deployed proxy sidecar, which no platform ships natively and D5-MESH grades at L5.

## Threat coverage

D5 is the primary domain for ASI07 (Insecure Inter-Agent Communication), a secondary control surface for ASI02 (Tool Misuse) through tool authorization, and one of the four domains, with D4, D7 and D9, that carry Class 2 (long-running APT campaigns). [[agentic-ai-security-cmm-d2-identity|D2]] caps per-agent egress mediation, because a policy cannot name an agent the platform does not identify. [[threat-taxonomy-reconciliation|The Threat Taxonomy Reconciliation]] matrix and [[agentic-ai-threat-classes-2026|the threat classes]] carry the mapping.

ASI07 coverage in this domain assumes inter-agent communication runs over an inter-agent protocol. The [[openai-hugging-face-agent-incident|OpenAI–Hugging Face incident]] realized it over shared build infrastructure instead: a single repository on an internal [[artifactory|JFrog Artifactory]] package manager, writable by the whole training and evaluation fleet, became a persistent message board across otherwise-isolated runs, so an exploit found in one run became available to every run that read it.[^bhusa] Every ASI07 control in the landscape below — A2A signing, MCP brokering, agent-aware proxies, content scanning — sits on protocol traffic that this channel never generated, because the messages were ordinary package-manager writes. Read the domain's ASI07 coverage as protocol-scoped. [[agentic-ai-security-cmm-d8-supply-chain|D8]]'s D8-REPO-WRITE scopes each agent's write access to internal artifact repositories at L4, and no D5 criterion reads a message carried inside an authorized package-manager protocol.

**No D5 criterion grades a security test of the broker and protocol implementations its controls run on.** Document 5 of the [[owasp-ai-exchange|OWASP AI Exchange]] directs that agentic red teaming be combined with conventional application security testing, because an integrated view is more effective than either alone, and gives as its example an MCP server that may be reachable for SSRF, SQL injection, or cross-site scripting. It also directs that MCP, A2A and other inter-agent protocol implementations be red-teamed for implementation weaknesses as well as for prompt-layer attacks.[^aix-testing] D5-MCP-BROKER and D5-A2A-BROKER are read from a deployed configuration, with a refused call for D5-MCP-BROKER, so a broker that authenticates every message and is itself vulnerable as a service meets them. The tests the criteria name each exercise one control on the egress path, such as the replayed message D5-A2A-REPLAY names, the bypass attempt behind D5-GATEWAY-ONLY and the closure verification behind D5-SSRF. An MCP server's web-service test bears on D5-RELAY where it finds an SSRF, because the server then sends requests on the agent's behalf, and its injection and cross-site scripting findings bear on no D5 criterion. Whether the implementation test belongs in this domain's level definitions or stays a method the assessor runs is unresolved.

## Capability-decoupled levels

Stated as capabilities per [[agentic-ai-security-cmm-recalibration-method-2026|rule 1]]; a control counts when it operates in production per rule 2. A control implemented through a product in the organization's approved-vendor pipeline with a documented production date satisfies its criterion on that basis alone, and the production date is the date the control entered the organization's production. A planned date satisfies none, and neither does a product the organization does not yet run in production, whatever the vendor has announced.

- **L1 — Initial.** Agents have unrestricted network egress.
- **L2 — Developing.** Each agent's egress passes a destination allowlist enforced outside the agent, and the reach of every destination on that list is recorded.
- **L3 — Defined.** An agent-aware gateway carries every model, tool and MCP call, authorizing, screening and metering each one. The allowlist is locked against the agent, the resolver answers only listed names, MCP calls are brokered against pinned tool definitions, and inter-agent traffic runs mutually authenticated and replay-protected.
- **L4 — Managed.** Topology carries the control: agents reach one another only through a broker, agents that take in untrusted content are segmented from sensitive services, and the orchestrator holds no path of its own. The gateway exchanges a token per tool call and refuses changed tool definitions and drifted supplier contracts.
- **L5 — Optimizing.** A proxy runs beside each agent, the network layer leaves no path around the gateway, SSRF routes and open relays are closed, inter-agent messages carry signatures under an audited profile, and a vulnerable MCP server is quarantined without a human.
- **L5+ — Leading Edge.** Egress tokens bind to one task, one holder and one upstream resource, MCP tool definitions carry signatures other tenants can verify, inter-agent behavior is baselined, and egress policy federates and reconciles across clouds.

The L3 gateway criteria state a capability. The products that implement it differ in what they broker, as the control landscape above records, so an assessor grades what the deployment's gateway brokers rather than which product it runs, and [[cmm-known-limitations|CMM Known Limitations]] item 1 records what an assessor grading the products as one settled standard would miss. The gateway and MCP-brokering criteria have a GA production path on Azure, AWS and Google Cloud, which the control landscape above records. Tool fingerprinting has no dedicated platform service. Microsoft's MCP03 guidance prescribes a registry of approved tools pinned to verified versions and suggests checksums or signatures to verify their integrity.[^zt4ai]

**Per-task egress capability tokens sit at L5+.** The control landscape above carries one open-source implementation for them and no platform-native equivalent. Its maintainers have classified that implementation as Production/Stable since release 0.2.0 of 2026-06-22,[^tenuo-pypi] and the vault holds no production evidence for it from an organization that did not write it. [[agentic-ai-security-cmm-recalibration-method-2026|Rule 2]] holds a capability at L5+ until a production-hardened implementation path exists. [[agentic-ai-security-cmm-d2-identity|D2]] and [[agentic-ai-security-cmm-d3-control-least-agency|D3]] grade the capability at L5+ on the same basis, and D3 carries the full reasoning.

## Assessor detail per level

L1 describes where a deployment starts and carries no criterion, so a deployment that does not meet every L2 criterion scores L1. It scores 0 under the measurement protocol's rubric only where no evidence of the L1 baseline exists, meaning the assessment holds no record and no interview answer about the domain for that deployment. The levels from L2 to L5+ each carry a criteria list below, each list stating what its own level adds.

Grading is cumulative: Level N requires every Level N–1 control plus the new criteria at Level N ([[agentic-ai-security-cmm-2026|the CMM]]), so a level is met only where every level below it is met.

Each criterion takes one of four verdicts. **Met** and **not met** are read from the evidence the criterion names, whoever operates the control. The assessment records the evidence's assurance class beside the verdict and names the artifact behind it, its issuer and its date, per [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]]:

- **Tested**: the customer or the assessor exercised the control and recorded what it did.
- **Inspected**: vendor tooling the customer can reach, or a record the organization keeps, such as an inventory or a plan, shows the control's state in the deployment.
- **Attested**: the vendor states the control in a document the customer holds, and the document's own scope names the control.

**Not applicable** is recorded where the deployment holds no instance of what the criterion governs, and the reduced scope is recorded as an intentional trade-off in the [[agentic-ai-security-cmm-dependency-rules|effective-score]] strategic-rationale field. **Unanswerable** is recorded where the instance exists, the customer can run no test and keeps no record of the control's state, and the vendor supplies neither inspectable output nor an attestation that names the control. An unanswerable criterion never counts as met: its level stays open, and every level above it stays open under cumulative grading. The assessment names what would close it. A criterion that can be not applicable states that condition alongside the criterion. Each level's list below holds criteria only, and a paragraph after a list states no criterion: it carries maturity, market or provenance commentary, or the boundary between this domain and another.

**D5 grades one deployment at a time.** A deployment is the unit the assessment scope names: one agent application, or one agent platform a vendor provides together with the agents the organization runs on it. Evidence of a control counts only for the deployments the control covers. The D2→D5 cap reads the D2 score of the same deployment, so an assessment grades D5 on the scope it graded [[agentic-ai-security-cmm-d2-identity|D2]] on. Four terms fix what the criteria range over:

- **An agent** is one deployed configuration: its code, instructions, tools and grants as the deployment runs them. Replicas of one configuration are one agent, and two configurations are two agents even where they share code.
- **The agents in scope** are those the deployment runs in production, per rule 2. An agent outside production enters scope once it holds a production credential or reaches production data. Evidence from a pilot outside scope counts for no criterion, and the gap report can cite it as the planned route to a level. A deployment with no agent in scope, such as a pilot that holds no production credential and reaches no production data, takes no D5 result, and the assessment records it as outside scope.
- **An agent's egress** is every connection its components open to a destination outside the agent: its model calls, its tool, connector and MCP calls, the calls of the tools and MCP servers the deployment runs for it, and the connections of the code and commands it runs, under every autonomy mode the deployment permits, internal destinations included. A connection a vendor's service opens on the agent's behalf, such as an in-suite assistant's web search, is part of the agent's egress, and the vendor-held egress rule below states how it is read. An agent whose components open no connection holds no egress, so every criterion is not applicable to it.
- **A destination** is a host, a service endpoint, or an address and port that a connection reaches. Its **reach** is what an agent can reach through it: the hosts it forwards to, fetches from or sends to on the agent's request under its configuration, such as a proxy's upstreams, a package mirror's remote repositories or a mail service's recipients, and the parties outside the organization who publish content there that the agent reads, or who can read what the agent sends there, such as other accounts on a code host.

A criterion that names every agent, connection or destination is met only where it holds for each one. No percentage threshold applies, because the deployment's configuration enumerates its agents and their egress, and one agent outside the rule is the failure D5 grades. An agent whose configuration the organization cannot produce, such as a workstation that has stopped reporting to device management, does not meet a criterion that ranges over it. The deployment's verdict is the weakest among its agents: not met where any agent fails the criterion, then unanswerable where any agent's verdict is unanswerable, and not applicable only where the criterion is not applicable to every agent. The assessment names the scope it graded, and where a narrower scope would change an agent's result, such as one repository of a shared CI workflow, it reports that agent beside the deployment's result.

**Grading words.** The criteria use these terms in one sense each:

- **Allowlist**: an enumerated set of destinations that a component enforced outside the agent applies to the agent's egress, refusing a connection to any destination the set does not hold. An entry that admits every destination, or every host under a domain in which parties outside the organization can create hosts, such as a cloud provider's shared service domain, enumerates nothing.
- **Enforced outside the agent**: applied by a component that neither the model's output nor the code and commands the agent runs can reconfigure or bypass, such as a network policy, a firewall, a proxy, a resolver policy, a platform's egress or connector policy, or a sandbox proxy that the runtime hosting the model runs outside the sandbox.
- **Agent-aware gateway**: a component outside the agent that parses the model-API and MCP protocols, and any inter-agent protocol the deployment uses, identifies the calling agent on each call and applies its policy per call. It can run centrally or beside each agent, such as a mesh sidecar. An API gateway that routes by host, path or consumer and parses neither protocol is not agent-aware. A call to a tool or MCP server the deployment runs for an agent as a local process goes over the network wherever that tool or server opens its own connection to another host to carry out the call, such as a local MCP server calling a code host's API, and D5-GATEWAY, D5-GATEWAY-AUTHZ and D5-GATEWAY-EXCHANGE read that connection as the call's network leg.
- **Inter-agent traffic**: every message one agent sends another, over the [[a2a-protocol|A2A protocol]] or any other, such as an MCP call to an agent or a platform's call to a connected agent. A child session that runs the parent's configuration under the parent's identity is part of the parent's run, as [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s delegation hop defines it, and its messages are not inter-agent traffic. The A2A family below grades inter-agent traffic whatever its protocol.
- **Delegation**: one agent passing a task to a different agent, a delegation hop in D3's sense. An **orchestrator** is an agent that delegates tasks and receives their results. A call to an agent of another deployment is part of the calling agent's egress and inter-agent traffic, and no delegation within the calling deployment, so the Microsoft 365 Copilot deployment grades a call its assistant makes to a Copilot Studio agent published to Copilot, and the Copilot Studio deployment grades the called agent's own egress and delegations. The called agent is one of the calling agent's destinations, so the calling deployment's D5-REACH record states the called agent's reach.
- **Tool definition**: the name, description and parameter schema a server gives an agent for a tool, such as an entry in an MCP server's tool list. Its **fingerprint** is a hash over all three.
- **Untrusted content**: content an agent takes in from a party outside the organization, or from a source the organization does not control, such as a claimant's document, an inbound mail, a web page or a third-party tool's output.
- **Internal service**: a service the organization operates, on its own infrastructure or in its own cloud accounts. A **sensitive internal service** holds data the organization's classification scheme restricts, or can release a payment or another transfer of value, change an access right or deploy to production.
- **Screen**: compare content against the classes a policy names, and block or redact a match before the content passes.
- **Release**: a change to an agent that exchanges inter-agent messages, or to its signing configuration, that reaches production.
- **Tested**: a test counts where it ran in production, or in another environment on the network policy, gateway configuration and code that production runs, and its record names the environment and the revisions. A demonstration the organization runs and the assessor observes is a test.

**Names and precedence.** Each criterion carries a stable name, D5 and a mnemonic for what the criterion requires, and the name leads the criterion in bold. The level is an attribute recorded beside the name, so a criterion that changes level keeps its name. Members of a family share its first mnemonic, as D5-DNS and D5-DNS-ONLY do, and each member is a separate criterion because a deployment can hold one without the other and an assessor collects different evidence for each. [[agentic-ai-security-cmm-2026|The CMM]]'s D5 levels restate each criterion under the same name, and [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]]'s D5 questions and artifacts cite each one by that name, in plain text. A level's statement above summarizes its list, and where the two read differently the list governs.

**Vendor-held egress.** A vendor holds part of an agent's egress where the vendor's service opens the connection on the agent's behalf and the customer holds no position in its path, as with an in-suite assistant's web search or a maker platform's connector calls. The criteria stand for that egress and are graded on the evidence the vendor produces, because the agent still holds the egress each criterion governs: vendor operation of the path is no ground for a not-applicable verdict. D5-ALLOW reads each vendor-held channel's destinations from the vendor's own statement of them, in the administrative console or in a vendor document whose scope names the product, narrowed by the customer's enablement settings, such as a switch that turns web search off or the list of apps and agents an assistant can call. Where neither the console nor such a document states a channel's destinations, D5-ALLOW is unanswerable for that agent, and so is D5-REACH for the destinations that channel reaches. A data-loss-prevention rule bounds the content an assistant draws on and names no destination, so it evidences no D5 criterion. An agent the organization builds on a vendor's platform, such as a Copilot Studio agent, reaches the destinations its maker configured, so its allowlist is the customer's own configuration, such as the platform's connector policy and endpoint filters, and the platform's enforcement of that configuration is graded on the evidence the vendor produces.

**Not applicable across a level.** A level at which every criterion is not applicable for the deployment is not reached, and neither is any level above it, because a not-applicable verdict records that the deployment holds nothing for a criterion to govern and records no control. A deployment whose agents hold no egress holds no instance of any D5 criterion, so it takes no D5 result, and the assessment records the domain as not applicable to it, with the reason.

**Conditions the rubric adds.** [[agentic-ai-security-cmm-measurement-protocol|The measurement protocol]]'s rubric adds two conditions to score 3 that no domain's criteria state: operational ID tagging of the domain's findings, and the live observation it requires, a trace, a policy decision and, where D3-APPROVE-GATE applies, a gate fire. A deployment that meets every D5 L3 criterion without them scores 2 under the rubric, and the assessment records which condition held it there.

### L2 detail

- **D5-ALLOW.** Every connection in each agent's egress, other than its name lookups, passes an allowlist enforced outside the agent, which refuses a connection to a destination the list does not hold. The list can sit at any layer that enumerates destinations, such as a resolver policy, a proxy, a firewall rule set, a network policy or a platform's connector policy, and a list the enforcing component also applies to other workloads counts, with every entry on it then one of the agent's destinations. A list enforced at the resolver governs only the connections that resolve a name, so an agent whose code or tools can connect to an address needs its list at a layer that sees the address. An agent whose list holds an entry that enumerates nothing does not meet the criterion, and neither does an agent with a component whose connections bypass the list, such as a model client or an MCP server that runs outside the sandbox the list governs. The list holds under every autonomy mode the deployment permits, and a mode that suppresses it, such as a harness's sandbox bypass, fails the criterion for every agent that can run in that mode. *Evidence:* each agent's allowlist as the enforcing component applies it at the production version, set against the parts of the agent's egress, with a connection to an unlisted destination refused.
- **D5-REACH.** A dated record the organization keeps states the reach of each destination on each agent's allowlist, external destinations included, and it matches the deployed configuration of the list and of each destination the organization operates or configures. A destination the record omits, or one whose recorded reach its configuration contradicts, fails the criterion, and so does a record of the agent's intended destinations where the enforced list holds more. *Evidence:* the reach record, set against each agent's deployed allowlist and the configuration of each destination the organization operates or configures.

An allowlist bounds an agent's reach only as far as each destination on it cannot make the request the agent was denied. OpenAI ran evaluation and training agents with the internet disabled and one permitted dependency, an internal [[artifactory|JFrog Artifactory]] package manager and caching proxy that held broad internet access. On 2026-05-26 an agent obtained indirect egress by SSRF against that proxy while the sandbox network policy stayed correctly enforced.[^bhusa] D5-REACH records a relay like that proxy at L2, and D5-RELAY requires its own egress to be constrained at L5.

The reach record covers external destinations because an allowed public host serves more than the purpose it was allowed for. [[kimi-k3-sandbox-escape|Kimi K3]] reached its benchmark's published answers through an allowlist that was present and correctly enforced: outbound 443 and DNS were permitted to package-maintenance destinations including `github.com`, which also served the benchmark repository. A public host permitted for package metadata also serves repositories, gists and raw file content, and a record of that reach names the exposure before an incident does.

### L3 detail

- **D5-ALLOW-LOCK.** Each agent's allowlist changes only through its own administration: neither the agent, nor content it reads, such as a file in the repository a run checks out, nor the principal it acts for can add a destination to it. A list assembled from settings an agent's run or its principal can edit, such as a project settings file a pull request can change for its own run or a user settings file on a developer's own machine, fails the criterion. *Evidence:* the source of each agent's allowlist, with the principals able to change it.
- **D5-GATEWAY.** Every call each agent sends to a model, a tool or an MCP server over the network leaves through an agent-aware gateway outside the agent, whatever its destination, internal services included, and under every autonomy mode the deployment permits. A call that reaches its destination by another route, such as a model endpoint the agent calls directly or a tool reached through an API gateway that is not agent-aware, fails the criterion. *Evidence:* the route each class of call takes, such as the endpoint, proxy or network setting that directs it, set against the gateway's configuration and its log of each class.
- **D5-GATEWAY-AUTHZ.** The gateway authorizes each tool and MCP call against a rule that names the calling agent, or a named group of agents, and the tool, and it refuses a call no rule permits. A gateway that authorizes by route or network source alone fails the criterion. Not applicable where no agent sends a tool or MCP call over the network. *Evidence:* the gateway's policy for each tool, with the agent each rule names, and a refused call in its log.
- **D5-GATEWAY-SCREEN.** The gateway screens the content of each call it carries, in both directions: what the agent sends, and the responses and tool results it receives. The screen runs inline, so content its policy matches is blocked or redacted before it passes, and the policy's classes include prompt injection in what the agent receives and the organization's restricted data classes, such as payment-card numbers or personal identifiers, in what it sends. A screen that runs after delivery, or one that reads a single direction, fails the criterion. *Evidence:* the gateway's content policy with its classes and directions, and a request or response it blocked.
- **D5-CEILING.** A component outside the agent that each of the agent's model, tool and MCP calls passes, such as the gateway, counts the calls each agent makes in a window the policy sets, keyed on the agent's identity, and refuses or holds a call past the ceiling.[^aix-sandbox][^aix-limitresources] A ceiling held in the agent's own code, or one that counts only part of the agent's calls, fails the criterion. *Evidence:* the ceiling policy with its key and window, and a call it refused or held.
- **D5-CEILING-TOKENS.** The gateway meters the model tokens each agent sends and receives, keyed on the agent's identity, and refuses a model call that would take the agent past the token ceiling the policy sets for a window. A cap set per call, such as a maximum output length, bounds no window and fails the criterion. *Evidence:* the gateway's token policy per agent, and a model call it refused past the ceiling.
- **D5-CEILING-TOOLS.** A component outside the agent, such as the gateway, counts the tool and MCP invocations each agent makes in one task or session, keyed on the agent's identity, and refuses an invocation past the ceiling the policy sets.[^aix-limitresources] A turn or step limit the agent's own harness enforces fails the criterion. Not applicable where no agent invokes a tool. *Evidence:* the invocation ceiling per agent with its key, and an invocation it refused.
- **D5-DNS.** The resolver that answers each agent's lookups returns an answer only for names on the agent's allowlist and refuses every other name, so a lookup cannot carry data to a nameserver the list does not name, whichever layer the allowlist sits at. A resolver that answers every name outside a blocklist fails the criterion. The [[owasp-ai-exchange|OWASP AI Exchange]] lists restricting DNS under network segmentation.[^aix-sandbox] *Evidence:* the resolver's policy for the agent's lookups in allow form, and a lookup outside the list refused.
- **D5-DNS-ONLY.** Each agent's name lookups reach no nameserver but the resolver D5-DNS grades: the network layer refuses the agent's DNS traffic to any other server, on the DNS ports or over DNS over TLS, and the allowlist names no DNS-over-HTTPS endpoint. *Evidence:* the network policy on DNS traffic from each agent's workload, and a query to another nameserver refused.
- **D5-MCP-BROKER.** Every call an agent makes to an MCP server passes a broker outside the agent, such as the gateway, that validates an OAuth access token or a signed JWT issued for that server and identifying the calling agent, or the human it acts for, and the broker refuses a call that carries none. A server the agent reaches directly on a credential no broker validates, such as a developer's own OAuth grant, fails the criterion, and so does a server the agent starts as a local process that nothing authenticates it to. Not applicable where no agent calls an MCP server. *Evidence:* the broker's token-validation configuration for each MCP server, and a call refused without a valid token.
- **D5-MCP-PIN.** A registry records the approved version of each MCP server an agent calls and the fingerprint of each tool definition it serves, and the definitions the agent receives are compared with the recorded fingerprints each time the agent connects, with a mismatch recorded and alerted. A server pinned by version tag alone, whose served definitions nothing compares, fails the criterion. Not applicable where no agent calls an MCP server. *Evidence:* the fingerprint registry, and the comparison record of a connection.
- **D5-A2A-TLS.** Every endpoint that receives inter-agent traffic accepts TLS 1.3 and no earlier version. Not applicable where the deployment carries no inter-agent traffic. *Evidence:* the TLS policy of each receiving endpoint, and a handshake offering an earlier version refused.
- **D5-A2A-AUTH.** Both ends of every inter-agent exchange authenticate each other cryptographically before it starts, by mutual TLS or a signed token each side verifies, and no exchange relies on a shared static key.[^aix-mac] Not applicable where the deployment carries no inter-agent traffic. *Evidence:* the authentication configuration of each endpoint that sends or receives inter-agent traffic, and an unauthenticated message refused.
- **D5-A2A-REPLAY.** Each inter-agent message carries a nonce or a sequence number, and its receiver refuses a message it has already accepted, because transport authentication alone lets a captured message validate when it is sent again ([[owasp-ai-exchange|OWASP AI Exchange]]).[^aix-mac] The deployment's enforcement profile states the check, and a profile whose check no receiver runs fails the criterion. Not applicable where the deployment carries no inter-agent traffic. *Evidence:* the enforcement profile's replay rule, and a replayed message refused.
- **D5-A2A-CHAIN.** Each message an agent sends to an agent it delegates to carries a verifiable reference to the delegating agent and to the human accountable for the run, as [[agentic-ai-security-cmm-d2-identity|D2]]'s D2-TRACE defines that human, beside the sender's own credential, and the receiving agent's downstream calls carry the reference on.[^aix-mac] Not applicable where no agent delegates a task to another agent. *Evidence:* a delegated message sample showing the reference to the delegating agent and to the accountable human.

L2 admits a list enforced at the proxy, which leaves an agent free to query an arbitrary nameserver, and DNS is itself an exfiltration path. D5-DNS and D5-DNS-ONLY close name resolution as an independent channel whichever layer the allowlist sits at.

The ceiling criteria split with [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] on where a ceiling is enforced. D4-SANDBOX-LIMITS grades the CPU, memory and wall-clock limits the platform imposes on each sandbox the agent's code runs in, and D5 grades the call, token and invocation ceilings the in-path gateway imposes on what leaves it. The Exchange's sandboxing control lists per-agent CPU, memory, API volume, tool invocations and wall-clock limits, enforced by the platform and not by the agent itself.[^aix-sandbox] `LIMIT RESOURCES` names six resources — CPU time, memory, disk I/O, network egress, tool invocations, and wall-clock execution time — and states the bound an assessor carries with them: resource limits bound cost and availability impact and do not prevent all harm within the allocated budget.[^aix-limitresources] The ceilings are credited for what they cap, and harm done inside the budget is outside what they grade.

D5-GATEWAY-AUTHZ, D3-MEDIATE and D2-AUTHZ can read one policy. [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s D3-MEDIATE grades that every tool call reaches a decision point before it runs, [[agentic-ai-security-cmm-d2-identity|D2]]'s D2-AUTHZ that its rules name the calling agent, and D5-GATEWAY-AUTHZ that the enforcement sits on the network path, so a call that bypasses the agent's harness still meets it. Where the gateway hosts the decision point, one policy export evidences all three, and a decision the harness holds with no gateway on the path meets D3-MEDIATE and fails D5-GATEWAY-AUTHZ. [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] grades the injection classifier on the model's request path, and D5-GATEWAY-SCREEN grades the screen on the gateway every call passes, in both directions, so a component that does both evidences both.

The A2A criteria grade the inter-agent leg, and D2-MUTUAL grades the agent-to-service call. D2-DELEGATE-TOKEN and D2-DELEGATE-LINK grade the credential that carries a delegation, [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s D3-CHAIN grades its validation, and D5-A2A-CHAIN grades that each inter-agent message carries the reference across the hop.

### L4 detail

- **D5-GATEWAY-EXCHANGE.** For each tool call, the gateway exchanges the credential the call arrives with for a token issued for that tool alone, through OAuth 2.0 token exchange or an equivalent platform flow, so no tool receives a token the agent holds, and each tool refuses a token issued for another. A gateway that passes the agent's own token through to the tool fails the criterion. Not applicable where no tool an agent calls authenticates its caller. *Evidence:* the gateway's token-exchange logs, showing a token issued for each call's tool, and a token refused by a tool it was not issued for.
- **D5-MCP-RUGPULL.** The gateway refuses a tool definition whose fingerprint differs from the approved one D5-MCP-PIN records, so a definition a server changes after approval reaches no agent until a person approves the change. Not applicable where no agent calls an MCP server. *Evidence:* the gateway's refusal rule, and a changed definition it refused.
- **D5-MCP-POISON.** Each tool definition is screened before an agent can load it, at approval and again at each change, for instructions addressed to the model, such as a directive hidden in a description or a parameter schema, and a definition the screen flags stays unapproved. A fingerprint detects a changed definition and passes one that was poisoned from its first version, which is the case this screen reads. Not applicable where no agent calls an MCP server. *Evidence:* the screening rule set, and a definition it flagged or a test of it.
- **D5-MCP-CVE.** The gateway matches each MCP server an agent connects to, by its identity and, where the server reports one, its version, against a vulnerability feed that covers MCP servers and packages, and a match raises an alert tagged with the vulnerability's identifier. Not applicable where no agent calls an MCP server. *Evidence:* the feed subscription, and the gateway's CVE-tagged match log.
- **D5-CONTRACT.** The gateway validates each response a supplied model or AI service returns against the contract pinned for it, such as its response schema and its declared model version, and rejects a response that departs from that contract.[^aix-supplychainmanage] Not applicable where no agent calls a model or AI service a third party supplies. *Evidence:* the pinned contract for each supplied service, with the validation rule and a response it rejected.
- **D5-A2A-SCREEN.** Each inter-agent message is screened before it reaches the receiving agent's context, for prompt injection and for the organization's restricted data classes, and a message the screen matches is blocked or held. Not applicable where the deployment carries no inter-agent traffic. *Evidence:* the screen's configuration on the inter-agent path, and a message it blocked.
- **D5-A2A-BROKER.** No network path runs directly from one agent to another: every inter-agent message transits a broker outside both agents, such as an orchestration layer or a message bus, which authenticates the sender, validates the message against its protocol's schema and refuses a message that fails either.[^aix-sandbox] A receiving agent's own inbound endpoint is not a broker. Not applicable where the deployment runs a single agent. *Evidence:* the network policy between agents, showing no direct path, with the broker's authentication and validation rules.
- **D5-SEGMENT.** Each agent that takes in untrusted content reaches no sensitive internal service at the network layer beyond the tool endpoints on its allowlist, and network policy denies its traffic to every other sensitive internal service.[^aix-sandbox] Not applicable where no agent takes in untrusted content. *Evidence:* the segmentation policy, set against the list of sensitive internal services.
- **D5-ORCHESTRATE.** An orchestrator holds no network path of its own beyond its model endpoint and the agents it delegates to: every tool, data store and external destination it needs is reached through a sub-agent it delegates to, and a path through the gateway counts as the orchestrator's own.[^aix-oversight] Not applicable where no agent delegates a task to another agent. *Evidence:* the orchestrator's network policy, showing no outbound path beyond its model endpoint and its sub-agents.
- **D5-INSPECT.** Where an agent runs code or commands that open network connections, the egress control for those connections terminates TLS and decides on the host each request names inside the connection, refusing a request whose inner host differs from the name the connection was allowed on, so a fronted request cannot reach a host outside the allowlist. Not applicable where no agent runs code or commands that open network connections. *Evidence:* the egress proxy's TLS-termination configuration with its certificate authority, and a fronted request refused.

In-path rug-pull protection over MCP tool definitions is off-stack for all three hyperscalers and ships as developing COTS, so a program reaches D5-MCP-RUGPULL by buying a product or by building the refusal into its own gateway, rather than by enabling a feature it already owns. D5-CONTRACT runs at the gateway D5-GATEWAY already puts in path, so it costs schema pinning and response validation rather than a product. A contract check catches a changed interface. A silent model update or altered behavior behind an unchanged interface passes it, and the Exchange lists managing those provider-driven changes among the control's objectives and assigns them to no runtime check.[^aix-supplychainmanage] [[agentic-ai-security-cmm-d8-supply-chain|D8]] grades the assessment of a model's supplier (D8-SUPPLIER), the scan of an MCP server that installs on a system the organization runs (D8-ABILITY-SCAN) and the handling of AI-dependency advisories within their deadlines (D8-DISCLOSE), and this level grades what the gateway rejects or flags once a model or an MCP server is in use. A scanner that reads the tool definitions a running server serves, at approval and at each change, evidences D5-MCP-POISON. D8-ABILITY-SCAN reads a local server's code and instructions before the server installs, and a remote server takes no D8 scan.

D5-A2A-BROKER makes the broker the only inter-agent channel, where the L3 A2A criteria authenticate a channel that already exists. Both bound reach after an [[agent-escape|agent escape]]: an escaped agent that cannot open a peer connection is confined to the broker's validated path. D5-A2A-BROKER, D5-SEGMENT and D5-ORCHESTRATE are ordinary network controls with no AI-specific product dependency, so they are reachable on any of the three platforms, and their cost is topology design labor.

D5-ORCHESTRATE constrains which component may hold an egress path, and D5-GATEWAY-ONLY at L5 constrains where an existing path terminates. A deployment that routes orchestrator traffic through the gateway meets D5-GATEWAY-ONLY and still leaves the orchestrator reaching outside directly, which is the case the [[owasp-ai-exchange|OWASP AI Exchange]] addresses when it treats the orchestrator as the highest-leverage target in an agentic system.[^aix-oversight] Sub-agent routing bounds what a compromised orchestrator can send, because the request then leaves through a component whose own egress the criteria above already constrain. [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s D3-ORCHESTRATE grades the orchestrator's grants, and D5-ORCHESTRATE grades its network paths.

### L5 detail

- **D5-MESH.** An agent-aware proxy runs beside each agent, such as a mesh sidecar, and the agent's traffic is directed through it, so each agent's policy applies at the agent's own boundary, to its internal calls as well as its outbound ones. *Evidence:* the mesh topology, showing the proxy beside each agent and the policy it applies.
- **D5-GATEWAY-ONLY.** The network layer leaves each agent's workload no route to any destination except through the gateway or the proxy beside it: routes and network policy refuse every other connection, calls to internal services on the allowlist included. *Evidence:* the zero-bypass proof, the routes and network policy around each agent's workload with a direct connection refused.
- **D5-SSRF.** No request an agent's code or tools send reaches a destination outside the agent's allowlist by naming an internal, link-local or metadata address, by following a redirect, or by resolving an allowed name to another host. The egress control binds each name the allowlist or a proxy exemption admits, a name matched by suffix included, to the addresses the organization's resolver returns for it, so an entry in the agent's hosts file cannot carry an allowed name to another host. *Evidence:* the SSRF closure verification, a test from the agent's position of each route, each refused.
- **D5-RELAY.** Each internal service an agent reaches, on its allowlist or behind a destination that passes the agent's requests on, holds egress that a component outside it limits to named destinations, so no request the agent can make it send reaches a host outside that set. A service with open egress fails the criterion whether or not it relays by design, because an SSRF or a compromise turns it into a relay. Not applicable where the agents reach no internal service. *Evidence:* the egress policy of each internal service the agents reach.
- **D5-MCP-QUARANTINE.** A match D5-MCP-CVE raises removes the matched MCP server from every agent's reach at the gateway without waiting for a human, and the server stays out of reach until a person clears it. Not applicable where no agent calls an MCP server. *Evidence:* the quarantine rule, and its log of a quarantined server.
- **D5-A2A-SIGN.** Each inter-agent message carries its sender's signature over its content, sender, recipient and timestamp,[^aix-mac] and each agent's descriptor, such as an A2A Agent Card, carries its publisher's signature, under a signing profile the organization documents and publishes to each outside party whose agents exchange messages with its own. Each receiver verifies the signature and refuses a message or descriptor that fails it. Not applicable where the deployment carries no inter-agent traffic. *Evidence:* the published signing profile, and a message refused for a failed signature.
- **D5-A2A-SIGN-AUDIT.** Each release is checked against the signing profile before it reaches production, covering the signatures its messages and its descriptor carry and the verification it applies, and the check is recorded. Not applicable where the deployment carries no inter-agent traffic. *Evidence:* the audit record for each release in the period.

D5-SSRF has a worked instance in [[openai-dsewiki-agent-collusion|a separate OpenAI agent population]], over a proxy exemption rather than a redirect or an internal address. An egress proxy's `NO_PROXY` allowlist exempted any hostname ending in `*.blob.core.windows.net` from inspection without verifying that the name resolved to Azure. Agents invented a compliant fake hostname needing no registration, remapped it through `/etc/hosts` to the Power BI backend's address, and issued the `POST` request the proxy had been dropping under the forged name. D5-SSRF closes that route by binding the exempted suffix to the addresses the organization's resolver returns. The case extends the transitive-egress failure mode the OpenAI–Hugging Face instance documents to a proxy-configuration exception, and it shares with Kimi K3 an allowlist entry trusted by name rather than by what it reaches, so it corroborates the criterion rather than moving it.

D5-SSRF closes the routes out of the agent's own position, and D5-RELAY constrains the internal services the agent may still reach. The mesh proxy D5-MESH grades ships as open source on a v1 release line since March 2026 and in no platform-native form,[^agentgw] so it is the L5 capability a buyer adds off-stack.

### L5+ detail

- **D5-TASKTOKEN.** Each outbound call an agent makes carries a capability token issued for one task and bound cryptographically to the agent presenting it and to the upstream resource the call may reach, and the gateway refuses the call when another holder presents the token, when the call targets another resource, or after the task has closed. [[agentic-ai-security-cmm-d2-identity|D2]] grades the token's construction under D2-TASKTOKEN and [[agentic-ai-security-cmm-d3-control-least-agency|D3]] its evaluation at the decision point under D3-TASKTOKEN, and this criterion grades its binding to the upstream resource at egress. *Evidence:* a per-task egress token sample with its holder and resource binding, and the gateway's refusals of another holder and another resource.
- **D5-MCP-SIGN.** Each MCP server's tool definitions carry their publisher's signature, recorded in a transparency log that parties in other tenants can check, and the gateway verifies the signature before an agent loads the definitions and refuses a definition whose signature fails. Not applicable where no agent calls an MCP server. *Evidence:* the signature verifier deployed at the gateway, and a definition refused for a failed signature.
- **D5-A2A-BASELINE.** Each agent's inter-agent messaging has a recorded behavioral baseline, such as the agents it messages, the message types it sends and their volume, and a detector alerts when the agent departs from it. Not applicable where the deployment carries no inter-agent traffic. *Evidence:* the drift rule library, with each agent's baseline.
- **D5-FEDERATE.** One egress policy governs the agent-aware proxies the deployment runs in two or more clouds, and a change to that policy reaches each proxy. Not applicable where the deployment's egress passes proxies in one cloud only. *Evidence:* the federation configuration.
- **D5-FEDERATE-RECONCILE.** A reconciliation joins the egress records of those proxies into one account of each agent's traffic, and it reports each call that one proxy allowed and the federated policy refuses. Not applicable where D5-FEDERATE is not applicable. *Evidence:* the cross-cloud reconciliation report.

Rule 2 holds these five criteria at L5+ on the reading the control landscape gives. Per-task egress tokens have one open-source implementation and no platform-native one. Signed tool definitions for MCP are at proposal stage, and the landscape carries no verifier for them. Behavioral drift detection over inter-agent traffic is research-stage, and the landscape carries no product that federates egress policy across clouds. D8's D8-SIGN-MCP grades name-to-binary signing of an MCP server's package at L5+, and D5-MCP-SIGN grades the tool definitions the running server serves, verified at the gateway. [[agentic-ai-security-cmm-d7-observability|D7]] grades per-agent behavioral baselines at L4 and D2-BASELINE each identity's baseline of the resources it calls, and D5-A2A-BASELINE adds a baseline over each agent's inter-agent messages.

## Right-sizing by deployment shape

| Deployment shape | Realistic D5 target |
|---|---|
| Member/customer-service RAG chatbot (no external write reach) | L2 → L3 |
| In-suite productivity assistant (Gemini for Workspace, Microsoft 365 Copilot) | L3 |
| Desktop-agent productivity assistant ([[claude-cowork\|Claude Cowork]] class) | L2 → L3 |
| Copilot / generative coding tool | L3 |
| MCP / skill provider (server-side) | L4 |
| Multi-agent mesh (A2A) | L4 → L5 |

An agent the organization builds on a vendor's platform, such as a Copilot Studio agent, takes the row its own function fits, and the vendor-held egress rule reads the channels its maker configured as the customer's own configuration.

**A chatbot with no external write reach has little egress to mediate.** D5-ALLOW and the GA gateway, with the inline screening D5-GATEWAY-SCREEN grades, cover it. Entra Internet Access's network-layer prompt filter screens traffic from the organization's Entra-joined devices running the Global Secure Access client, so it guards staff use of AI apps and sits outside a member-facing bot's path.[^entra] The egress leg of the trifecta is broken by architecture, so a lower D5 is sound and is recorded as an intentional trade-off rather than a deficiency.

**An in-suite productivity assistant holds its agent, its tools and the path between them inside the vendor.** No proxy, perimeter or gateway the customer operates takes a position on that path, so the vendor-held egress rule above decides how each criterion reads. D5-ALLOW reads the assistant's outbound channels from the vendor's statement of them, narrowed by the customer's settings, such as the web-search switch and the list of apps and agents the assistant can call, and a channel left on with no documented destination leaves D5-ALLOW unanswerable. The gateway, ceiling and resolver criteria are graded on the vendor's documentation of its own service, so the row's L3 target rests on evidence only the vendor can supply. The exfiltration channel that survives is the assistant's own rendering of images and links, which sits on the runtime plane [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] grades rather than on any path this domain reaches. The row covers the in-suite variant alone.

**A desktop agent's organization-level egress setting reaches the code it runs and not the tools it retrieves through.** [[claude-cowork|Claude Cowork]] applies the organization's network egress permissions, set under code execution, to the code the agent runs, and enforces the cloud sandbox's egress through a mandatory proxy outside the sandbox that the sandbox cannot reconfigure or bypass.[^cowork-arch] Anthropic states the exclusion in the article that sets the permission: those permissions do not apply to the web fetch tool, the web search tool or MCP servers, including the Chrome extension.[^cowork-te] D5-ALLOW needs every channel bounded. The setting bounds code execution, evidenced from that setting and, on a managed deployment, from the device profile's sandbox egress allowlist. Web search and the two browser channels meet D5-ALLOW where an owner switches them off. Web fetch runs under the vendor's limit to search results and URLs the member has shared, so with web search off its destinations are the URLs the member shares: a set the vendor enforces, which D5-ALLOW admits, and the member extends, which D5-ALLOW-LOCK at L3 does not admit. The L3 gateway criteria are **not met** over the channels the setting excludes, because none of the controls the vendor documents on those channels is an agent-aware gateway.

Where the excluded traffic leaves the trust boundary depends on session placement, and the two vendor articles read together leave it open. Web fetch runs server side, and connector authorization tokens never enter the sandbox because connector calls are made server side, so on a cloud session no customer-held position stands between the agent and either channel.[^cowork-te][^cowork-arch] The architecture article places a local session's agent loop on the member's device, lists web fetches and local plugin MCP servers inside that loop, and states that an application-layer permission system gates its access against the organization's network egress settings — the same permissions the Team and Enterprise article says do not apply to those tools.[^cowork-arch][^cowork-te] Neither article reconciles the two statements, and neither states where web search egress originates. An assessor establishes the session placement in the fleet before crediting or denying a channel. The target range holds under either reading, because a destination allowlist applied by the vendor's permission layer meets D5-ALLOW and none of the L3 gateway criteria.

What the customer holds over web fetch, web search and the connectors is configuration rather than a position in the path. The browser channels differ: browser traffic leaves from the member's machine, where the desktop app runs, and a session in the cloud reaches the browser through that app, so an allowlist enforced on that machine's route, such as a device proxy, bounds the browser channels for D5-ALLOW.[^cowork-te][^cowork-arch] An owner can turn web search off for Cowork and Chat, and Claude in Chrome off under its own organization setting; the built-in browser carries a third switch, and both browser paths run the vendor's blocklist for high-risk sites and a safety check on every action, over which that article records no customer control.[^cowork-te] [[claude-cowork|The Cowork control surface]] records the connector leg as organization-level enablement plus a per-category authorization of allow, approve or block. A switch bounds whether a channel exists and a category bounds which actions cross it. Neither authorizes per tool call at an in-path point, governs tokens, or screens content inline, which is what D5-GATEWAY-AUTHZ, D5-CEILING-TOKENS and D5-GATEWAY-SCREEN read from a deployed gateway configuration. The row covers the desktop-agent variant alone.

**A coding tool's model calls, its MCP servers and the commands it runs are all egress.** D5-ALLOW and D5-GATEWAY range over each of them, so a sandbox allowlist that covers the commands and leaves the model client or an MCP server outside it does not meet D5-ALLOW, and [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]]'s sandbox-coverage question asks which parts the boundary holds.

**An MCP provider is consumed by agents it does not control.** D5-GATEWAY-EXCHANGE, D5-MCP-RUGPULL and D5-MCP-CVE earn their cost against callers the provider cannot vet.

**A mesh needs a proxy beside each agent, signed inter-agent messages, content screening, a broker between agents and cross-agent access control lists.** D5-MESH, D5-A2A-SIGN, D5-A2A-SCREEN and D5-A2A-BROKER grade the proxy, the signatures, the screening and the broker, and no D5 criterion grades the access control lists. [[agentic-ai-security-reference-architecture|The reference architecture]] defaults to a single broker up to roughly fifty agents and moves to a mesh of per-service sidecars above that; the figure is an engineering default rather than a measured threshold, and the trade it prices is one policy chokepoint against a policy surface that scales with the mesh.

Removing the egress capability defeats the [[lethal-trifecta|lethal trifecta]] most directly at D5: a bot with no sensitive data or no egress path drops the D5 requirement substantially. Confirm that the removed leg is absent by architecture, because a policy restriction alone leaves the capability in place.

A proxy that does not inspect TLS bounds the hostname a client puts in its request rather than the host that answers it. Anthropic states the consequence for Claude Code's built-in sandbox proxy: the proxy makes its allow decision from the client-supplied hostname and by default does not terminate or inspect TLS, so code running inside the sandbox can potentially use domain fronting or a similar technique to reach hosts outside the allowlist.[^ccsandbox] A hostname-only allowlist meets D5-ALLOW, and D5-INSPECT at L4 requires TLS-terminating inspection wherever an agent runs code or commands, which a coding tool always does. The first-party TLS-termination setting is labelled experimental and terminates TLS for masked-credential substitution without adding content filtering, so the vendor directs a threat model needing stronger guarantees to a custom proxy that terminates TLS, inspects traffic, and carries its CA certificate inside the sandbox.[^ccsandbox] See [[securing-agentic-coding|Securing Agentic Coding]] §Egress plane and [[generative-coding-deployment-shape-2026|Generative Coding Deployment Shapes]] for which deployment variants make egress the primary boundary. [[cmm-stress-test-canadian-fi-google-2026-09|The September Canadian-FI stress test]] states the direction in reverse, reading the broad allowlist entry as the reachable target rather than the escape route.

## Cost model

Here too, L2 and L3 licensing reads near-zero for an Azure incumbent already running API Management, because the AI gateway and its MCP capabilities extend that service rather than forming a separate offering.[^apim] Network-layer filtering is licensed apart: Entra Internet Access comes in Microsoft Entra Suite or as a standalone license, on top of the Entra ID P1 or P2 license each user needs, and no L3 criterion requires it.[^entra] For a Google Cloud buyer, Agent Gateway or Apigee with inline Model Armor covers the gateway row, metered on prompt and response tokens at \$0.10 per additional million past a no-cost allocation of 3 billion a month on a Security Command Center Premium or Enterprise subscription and 2 million a month standalone.[^maprice] Agent Gateway's IAM access policies cover MCP brokering, GA since 2026-08-31, and VPC Service Controls perimeters cover the network row, with agent identities GA as perimeter principals since 2026-06-29.[^gcp-agw][^vpcsc]

| Level | Licensing | Operational labor | Run-rate |
|---|---|---|---|
| L2 | ~0 for an E5/Azure incumbent | maintain the allowlist | — |
| L3 | ~0 incremental on an existing API Management instance, which carries the AI gateway and MCP brokering[^apim]; Entra Internet Access, where added, is a per-user Entra Suite or standalone license[^entra] | gateway-policy authoring; A2A enforcement-profile documentation | the AI-gateway run-rate is token-metered and scales with agent/token volume; semantic caching reduces it |
| L4 | off-stack rug-pull / tool-poisoning detection — net-new spend | per-tool-call token-exchange config; CVE-feed integration; rule-pack tuning | token-exchange + detector telemetry into the SIEM |
| L5 | off-stack: mesh sidecars — mostly net-new | mesh rollout + zero-bypass proof; SSRF-closure verification; per-release A2A audit | per-agent sidecar compute + gateway run-rate × agent count |

For an Azure incumbent already running API Management, L2–L3 licensing is near-zero, because the gateway and MCP authorization come with that instance, and network-layer filtering adds an Entra Internet Access license only where the buyer wants it. The costs that land are the token-metered gateway run-rate, which scales with agent count, and the net-new off-stack spend that begins at L4 and dominates L5. The licensing cliff falls at L4, which matches the right-sizing finding that most chatbot and copilot deployments target L3.

## Customer critiques folded in

- *"No Microsoft AI gateway — must go off-stack for the egress plane."* Corrected and confirmed false: Azure API Management AI Gateway is GA with token governance, semantic caching, inline content safety, and MCP brokering with Entra/OAuth/JWT authorization[^apim][^mcp]; Entra Internet Access adds GA network-layer prompt-injection and Shadow-AI detection[^entra].
- *"The egress gaps are real but narrow."* Confirmed and extended: the three genuine off-stack residuals are MCP tool-integrity/rug-pull, which Microsoft's own guidance concedes[^zt4ai], per-task capability tokens, and A2A authorization beyond identity. D5-MCP-RUGPULL grades the first at L4 and D5-TASKTOKEN the second at L5+. The third bundles message signing, cross-agent access control lists and content-scanning rule packs, of which D5-A2A-SIGN grades the signing at L5 and D5-A2A-SCREEN the scanning at L4, and no D5 criterion grades the lists. None of the three blocks an L3 target.
- *"L5 assumes a cadence regulated FIs can't follow."* The realistic chatbot target (L3) depends only on GA, already-owned Azure controls, so the buyer is not penalized at their actual target level. D5-MESH's sidecar sits at L5 and ships as an open-source project on a v1 release line since March 2026[^agentgw], and D5-TASKTOKEN sits at L5+, where the cadence qualifier puts a capability with no production-hardened path in the control landscape above.

## Open questions

- APIM brokers MCP tools only, and Microsoft Learn's MCP-server overview announces no date for resources or prompts[^mcp]. Whether tools-only brokering suffices for richer MCP deployments is unresolved.
- The OSS mesh-sidecar path (agentgateway) reached v1.0.0 in March 2026 and has shipped a minor release about monthly since, with v1.4 on 2026-07-27.[^agentgw] Whether six months on a v1 release line makes the L5 mesh path production-hardened for a buyer on a regulated procurement cycle is unresolved.
- Agent identities have been GA principals in VPC Service Controls ingress and egress rules since 2026-06-29.[^vpcsc] Agent Gateway enforces perimeter rules only on deployments created after 2026-09-08 through an agent connectivity template, and Google's IAM access-policy page states that the gateway's access policies do not support VPC Service Controls, so whether gateway authorization and the perimeter compose on one GCP deployment is unresolved.[^gcp-agw]
- Per-task capability tokens have one implementation in the landscape above, which its maintainers classify as Production/Stable and for which the vault holds no independent production evidence, and the single-vendor concentration mirrors the D1 [[aiuc-1|AIUC-1]] concern. D5-TASKTOKEN sits at L5+ for that reason, and the condition that would return it to L5 is stated in [[agentic-ai-security-cmm-d3-control-least-agency|D3]].
- A2A authorization beyond identity stays thin. The [[owasp-ai-exchange|OWASP AI Exchange]] names the shape without supplying the pack: three multi-agent trust tiers assigned by provenance (same operator, verified external, unknown), governed by an explicit no-transitive-trust rule, under which A trusting B and B trusting C does not imply A trusts C.[^aix-mac] Trust tiering by provenance is implementable on any stack today, and no rule set or conformance test appears in the cited sources, which holds the landscape row at "thin everywhere" rather than at COTS-developing. No D5 criterion grades the tiers or the no-transitive-trust rule. Behavioral drift detection over inter-agent traffic, which D5-A2A-BASELINE grades at L5+, stays research-stage.
- [[agentic-ai-security-cmm-d8-supply-chain|D8]]'s D8-REPO-WRITE grades the storage half of the package-manager covert channel at L4, on every endpoint an internal artifact repository serves, with a protocol question and an artifact behind it. No control in the landscape above detects agent-to-agent messages carried inside an authorized package-manager protocol. D5-A2A-BROKER closes the network half, because a blocked direct path forces inter-agent traffic onto the broker, and it leaves the storage half to D8, because a shared registry is reached over an authorized client protocol; see [[offensive-agent-collective|Offensive Agent Collective]].
- D5-RELAY's egress constraint on the internal services an agent reaches has one platform-native evidence artifact in the cited sources, and it reaches the network half of the constraint. AWS Network Access Analyzer reports the paths a VPC configuration permits, and the requirements AWS documents for it include verifying "that you have appropriate network controls such as network firewalls and NAT gateways on all network paths between your resources and internet gateways", so an allowlisted service that is an AWS VPC resource can be shown to hold or not hold such a path.[^naa] Three parts of the constraint sit outside that finding set. A service that is itself a proxy, a gateway or a connector relays over a path the analysis reports as compliant, because the path is meant to exist. The scope vocabulary is AWS resource identifiers, resource types, resource tags, address ranges, ports and protocols, so a destination reached across clouds, from on premises, or through a managed service that is not a VPC network object is never enumerated. An analysis is a run charged per network interface analysed rather than a standing control. For a destination outside an analysed VPC, proving that an allowed service cannot relay is still a manual review of that service's own network policy, which is the artifact D5-RELAY names in [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]].
- D5-ORCHESTRATE takes one element of a six-element secure-orchestration strategy. The [[owasp-ai-exchange|OWASP AI Exchange]] pairs blocked orchestrator egress with orchestrator permissions limited to coordination and no direct high-impact tool credentials, a tamper-evident workflow log held outside orchestrator memory, reconciliation of agent actions against that log for phantom steps, untrusted-by-default treatment of sub-agent responses and tool outputs, and human approval ahead of irreversible or cross-system workflows.[^aix-oversight] [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s D3-ORCHESTRATE grades the permission element at L4. [[agentic-ai-security-cmm-d7-observability|D7]] grades the workflow log under D7-ORCHESTRATE and the reconciliation under D7-ORCHESTRATE-RECONCILE, both at L4. The untrusted-by-default element is graded as a screen the input passes before the model reads it: [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]]'s D4-INJECT-INDIRECT at L3 for each route that carries tool outputs, and D5-A2A-SCREEN at L4 for each inter-agent message, a sub-agent's response included. The approval element is graded where a workflow's step is destructive in D3's sense: D3-APPROVE at L2 holds each such action for a human's approval or refuses it, and no D3 criterion requires approval for a workflow because it crosses systems.

## D2→D5 dependency cap

D5's effective score is capped at D2's raw score for the same deployment: per-agent egress enforcement requires a per-agent identity for the policy to name. The Microsoft-native nuance sharpens it twice. Entra Agent ID gives per-agent identity, satisfying the D2 prerequisite. Because that identity is per agent and not per task, D5-TASKTOKEN stays unreachable on-stack, and it sits at L5+, so it caps the leading-edge tier instead of the achievable D5. What L5 still asks off-stack is the proxy beside each agent that D5-MESH grades, which ships as open source on a v1 release line since March 2026.[^agentgw] For [[agentic-ai-security-cmm-recalibration-method-2026|the persona]] (D2 L2, D5 L2), standing up the GA gateway alone would not raise effective D5 above L2 until D2 reaches L3, because the cap reads D2's raw score. The sequencing consequence: **D5 investment is wasted ahead of D2.** Stand up per-agent identity first, because D5-GATEWAY-AUTHZ enforces policy against an identity the platform can name. See [[agentic-ai-security-cmm-dependency-rules|the dependency rules]].

The authentication split follows the same boundary. [[agentic-ai-security-cmm-d2-identity|D2]]'s D2-MUTUAL grades mutual, cryptographic authentication on the agent-to-service call at L4, and D5-A2A-AUTH grades the inter-agent leg at L3, so one capability is not scored in two domains. [[agentic-ai-security-cmm-crosswalk|The crosswalk]] carries the control-to-domain anchors that place it.
