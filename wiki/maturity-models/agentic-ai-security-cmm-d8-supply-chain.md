# Agentic AI Security CMM — D8 Engineering and Supply Assurance

## Domain decision and boundary

D8 grades the engineering and supply controls for one agent deployment before it enters use and as its components change. The deployment includes the agents and the components they actually use. A customer that enables an assistant in a hosted suite still assesses its configuration, integrations, supplier assurance, tests, and release decision. Model-file checks apply where the organization loads model files. Producer criteria apply where it trains or fine-tunes a model for the agent; publication criteria apply where it supplies a component to outside consumers. [[agentic-ai-security-cmm-2026|The CMM core]] defines the five cumulative levels, and [[agentic-ai-security-cmm-measurement-protocol|the Assessor's Handbook]] records the evidence and determination.

D8 owns design review, first-party implementation checks, assembled-system tests, and the release decision. [[agentic-ai-security-cmm-d1-governance|D1]] supplies risk authority and accepts bounded residual risk. [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] grades controls while an agent runs. [[agentic-ai-security-cmm-d7-observability|D7]] grades production detection and recurring evaluation. A D8 test can exercise a D4 or D7 control, but one passing release test does not show continuous operation. D8-RELEASE records a D1-authorized exception and enforces the release path; it does not grant that exception. A supplier-held development or model step requires relevant supplier evidence. Missing evidence for a material existing step is unanswerable. Customer-controlled configuration and integration remain assessable even when the platform is hosted.

A component is a model the agent calls, its hosting service, its harness or platform, an ability, an AI framework library, an acquired dataset, or security-relevant configuration. An ability is a skill, plugin, connector, local or remote MCP server, external agent, or tool adapter the agent can invoke or load. An acquired dataset is a bounded collection imported or licensed for the deployment's retrieval, training, fine-tuning, or evaluation. A live connector that only queries an existing enterprise corpus does not acquire a dataset; an imported copy does. An individual user request or an incidental fetched page is not an acquired dataset. An information asset in D8-DOCS is a document or experiment record the organization writes, not every file the agent reads.

A version identifies the component revision that ran, not just a name such as `latest`. The inventory records when a hosted service publishes no released versions. If its supplier will not name the model or version it selected, D8-VERSION remains unanswerable for that model. A release is any promotion that changes the assessed deployment: a built artifact, workflow revision, managed configuration, platform publication, or vendor-console change. A build criterion applies only when a build produces an artifact. The release decision still applies to a hosted suite's customer enablement or configuration change.

The customer is the organization that operates or enables the assessed deployment. A supplier is an external provider or an internal team that provides a component across an organizational boundary. The customer tests its own configuration and integration; supplier records support controls inside a hosted service that the customer cannot inspect. Evidence inherited from a common build, supplier assessment, or managed fleet must name a scope, version, and date that cover the deployment. Each criterion must pass across its full applicable population, including manual and emergency paths. A missing component, failed check, or undocumented exception defeats a claim of full coverage.

The supplier assessment identifies model-file sources whose integrity assurance is insufficient for direct loading. These are the less trusted sources in D8-MODEL-INSPECT and D8-MODEL-PROBE. A missing source assessment cannot make either criterion inapplicable.

## Failure paths

A dependency, model file, tool definition, instruction pack, or copied configuration can carry hostile behavior into an agent. A valid signature identifies an origin but does not establish that the code or prompt is safe; the release decision therefore considers design, implementation, and assembled-system test results as well as integrity. A shared artifact repository can also become a write channel between agents or runs. The [OWASP AI Exchange supply-chain control](https://owaspai.org/go/supplychainmanage/) covers component records, acquisition, verification, and drift. [NIST's AI-focused Secure Software Development Framework profile](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218A.pdf) addresses model and AI component provenance. The criteria below are this model's assessable synthesis, not clauses imported from either source.

## Level progression

| Level | Observable outcome |
|---|---|
| L1 | A characterized deployment has a known gap in its foundational engineering or supply records or controls. |
| L2 | The customer inventories deployed components and versions, keeps supplier or model-team descriptions of each model's intended use, tested behavior, and known limits, records sources for imported or licensed datasets, and limits access to its design and experiment records. |
| L3 | Repeatable engineering checks cover material designs, first-party changes, supplied components, and applicable prompt or harness changes before use. |
| L4 | The customer tests the assembled deployment before promotion and checks component integrity, build provenance, advisories, and the exact release version. |
| L5 | Scheduled reconciliation, release gates, published-component vulnerability feeds, and finding deadlines keep component assurance current. |

A known failure of any applicable L2 criterion establishes the D8 L1 state. If no L2 failure is known but an applicable L2 fact remains unresolved, report D8 as unanswerable outside the level scale until the evidence resolves it. Supplier ownership does not establish a failure or make the fact inapplicable.

## Criterion catalogue

A pass requires every stated facet. A negative test must reach the actual install, load, promotion, or approval path. “Verified” means a check outside the agent compares the item with an approved signature, attestation, or hash and refuses a mismatch. A finding above a blocking threshold can proceed only through a bounded exception granted by the D1 risk authority. For a supplier-held part, inspect a supplier record that names the relevant product and practice, or record why the material step remains unanswerable. [NIST SSDF](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf) grounds the design, code review, test, and release sequence; [OWASP AI Exchange testing guidance](https://owaspai.org/docs/5_testing/#agentic-ai-security-testing) identifies agent-specific paths to exercise.

### L2 detail

- **D8-DATASET.** For each dataset imported or licensed for the deployment, the customer records its provider or original source and any filtering, labelling, or augmentation that supplier or customer records disclose. If the dataset lists content by reference, such as URLs, the customer records a hash of the content at each reference when it acquires the dataset. A record with no content source, or referenced content with no acquisition-time hash, fails. Not applicable where the deployment uses no imported or licensed dataset. *Evidence:* each dataset's source and documented processing, plus hashes of referenced content, reconciled with the component inventory.
- **D8-DOCS.** The customer lists its own agent design and development documents in an information-asset register. The register also covers its model design and experiment records when it trains, fine-tunes, or evaluates a model for the agent. For an in-suite assistant, customer-written configuration designs count. Each entry names the document store and owner; an omitted store fails. Not applicable where the customer writes none of these records. *Evidence:* register entries reconciled with the stores for agent, model, experiment, and configuration-design records.
- **D8-DOCS-ACCESS.** Each documentation store listed under D8-DOCS restricts reading to the people and roles its owner names as needing it, and the store's access list matches those names. A store that every employee, or any address on the network, can read fails the criterion. Not applicable where D8-DOCS is not applicable. *Evidence:* the access list of each store, set against the roles its owner names.
- **D8-INVENTORY.** The customer inventories every component each assessed agent uses. For each one, it records its source and maintainer, the date it or its current version entered the deployment, and its version where the supplier publishes one. For each component stored as a file or container image, it records a cryptographic hash. A field can live in a linked lock file, image record, or device inventory. A missing component or required field, or a version that differs from the one running, fails. If the supplier does not reveal a model version, record it as undisclosed for D8-VERSION; a hosted service with no released versions needs no version field. *Evidence:* the inventory and linked records matched to effective agent configuration on the assessment date.
- **D8-MODEL-CARD.** For each model an agent calls, the customer keeps a document from its supplier that identifies the model or family and describes its intended use, tested behavior, and known limits. A model card or an evaluation report can provide these facts. For a model it produces, the customer's own model-team document qualifies. The document must be dated or versioned to match the model version in D8-VERSION. A transparency note or service description that names no model, or a document for another version, fails. If the supplier names no model, the criterion is unanswerable for that model. *Evidence:* each saved document matched by date or version to the model in use.
- **D8-VERSION.** For each model the agent calls, the customer records the exact version that ran during each run or bounded period in the prior twelve months, or since the agent entered scope. It does the same for harnesses or platforms, abilities, and AI framework libraries whose suppliers release versions. A version range or supplier-controlled name such as `latest` does not establish which version ran. A run log or dated supplier record must map that name to the exact version used. A model identifier without a date qualifies if the supplier documents that it always names the same release. A period with no exact-version record fails. If a supplier will not name the model or version it selected for an in-suite assistant, that model is unanswerable. *Evidence:* exact-version history from run logs, change records, device inventories, or scoped supplier notices, reconciled with configuration-change dates.
- **D8-PROMPT-SECRETS.** Before use, the customer inspects each system prompt it controls as the agent will receive it. A credential or key in that effective prompt fails. The customer also records a threat-model-linked disclosure decision for sensitive database names, roles, or permission details in the prompt; an untreated sensitive detail fails. For a supplier-held prompt, obtain a supplier assertion that covers secret absence and sensitivity treatment for the assessed service and route. A customer leak test can prove disclosure but cannot prove that an inaccessible prompt contains no secret. Without scoped supplier evidence, that facet is unanswerable. *Evidence:* inspected effective prompts or scoped supplier assertions, reviews, sensitivity decisions, and any leak-test results.

### L3 detail

- **D8-DESIGN.** Before a material deployment release or configuration change, the engineering owner updates its architecture and threat model for the agent's assets, trust boundaries, untrusted inputs, actions, and suppliers. A reviewer checks the changed design and records a control, design change, or D1-authorized risk decision for each material failure path. An added tool, authority, input, data path, or supplier boundary with no treatment fails. Supplier design records cover supplier-held parts; the customer reviews the integration it controls. *Evidence:* versioned architecture, change-linked threat model, security requirements, review, and risk-treatment records.
- **D8-HARNESS.** *Coding fleet.* The fleet owner places every harness-configurable coding agent under managed settings on every device or runner that hosts it. User and project settings cannot override those settings. An uncovered device or runner, or a local override that takes effect, fails. Not applicable where no harness-configurable coding agent runs. *Evidence:* full device and runner list, managed-setting assignments, and effective settings checked for each configuration class and exception.
- **D8-HARNESS-EXTEND.** *Coding fleet.* The fleet owner records each managed list setting that the coding harness still lets user or project settings extend, and which entries those local settings may add. An extendable list omitted from the record fails. Not applicable where no harness-configurable coding agent runs, or where no local setting can extend a managed list. *Evidence:* the owner's record compared with the harness documentation of lists that merge across settings scopes.
- **D8-HARNESS-LOCK.** *Coding fleet.* The fleet owner enables every vendor-provided managed lock that prevents user or project settings from changing permission rules, hooks, MCP servers, and plugins or skills. An available lock left unset fails. Not applicable where no harness-configurable coding agent runs, or where the harness offers no such lock. *Evidence:* effective managed lock values compared with the locks the harness documents.
- **D8-HARNESS-RESTORE.** *Coding fleet.* If a device or runner's managed settings file changes, fleet management restores the published version on a stated interval, or the next run starts from an image that carries it. A changed file that remains in use beyond that interval or next run fails. Not applicable where no harness-configurable coding agent runs, or where no person or process can change the managed file. *Evidence:* restore settings and a restore log or test.
- **D8-HARNESS-REVIEW.** *Coding fleet.* The fleet owner enforces review before any change to the coding agent's configuration tree takes effect. The tree includes managed and project settings, hooks, MCP server definitions, subagents, skills, and loaded instruction files. A developer's unreviewed local change fails. A project setting that takes effect during the pull request run proposing it also fails. Not applicable where no harness-configurable coding agent runs. *Evidence:* the full configuration change history and enforced review path, with review times and effective revisions sampled across change routes and bypass attempts.
- **D8-IMPLEMENT.** Before merge or release, the customer checks each change it controls in the agent's code, orchestration, tool integration, policy, data preparation, or security-relevant configuration against the design risks. A human reviewer and blocking static analysis check all executable code, including code an agent generated. An unchecked change or a blocking finding shipped without D1-authorized disposition fails. For supplier-controlled code, use scoped supplier development evidence; customer-editable configuration remains in customer scope. *Evidence:* changed revisions, human and scanner results, held findings, dispositions, and the link from checked to shipped revision.
- **D8-INSTRUCT-BASELINE.** Each instruction file the assessed agent loads has a reviewed baseline, and each new version is reviewed before use. For a customer-controlled mutable file, a hash check at session start and after each change must hold the session or alert on a mismatch. For a file in an immutable artifact, the runtime verifies the artifact's hash against the approved release at load, and the running agent cannot write it. Scoped supplier records must establish the same baseline and load check for a supplier-held file; unavailable evidence is unanswerable. A later load of a changed file without a baseline check fails. Not applicable only when no instruction file loads on the assessed route. *Evidence:* each loaded file's baseline and load path, the customer check or scoped supplier record, and a mismatch record or test for a mutable file.
- **D8-ABILITY-SCAN.** Each ability that installs code or instructions on a system the organization runs, such as a skill, a plugin, a local MCP server or a harness extension, passes a scan for malicious code and instructions before it installs, and again at each new version. A positive finding is cleared or receives a D1-authorized bounded disposition before installation; an ability installed without a scan or disposition for its version fails. Not applicable where no ability installs on a system the organization runs. *Evidence:* the scan result and disposition for each such ability and version, dated before its install.
- **D8-ABILITY-SOURCE.** Each ability an agent uses comes from a source the organization approved for that ability, and the approval names the ability, its publisher and the source it installs from or is reached at, such as a marketplace entry, a registry namespace or a server's URL. A configuration that restricts the agents to the approved entries meets the criterion as the approval record. An approval of a class that admits abilities nobody reviewed, such as a setting that admits every agent a vendor builds or every plugin of a public marketplace, fails the criterion for each ability it admits. Not applicable where no agent uses an ability. *Evidence:* the approval record or the enforced configuration, set against the abilities each agent uses.
- **D8-AIBOM.** For each agent version the customer assembles or publishes, its release pipeline generates an AI bill of materials (AI-BOM) in a standard machine-readable format. The bill names the release's models, hosting services, harness or platform, abilities, AI framework libraries, acquired datasets, and security-relevant configuration. It records disclosed versions and cryptographic hashes for files or images the customer stores, and marks a supplier-undisclosed version as such for D8-VERSION. A coding fleet assembles an agent version when it packages or promotes the harness with managed settings and any admitted abilities as one versioned deployment. An image SBOM without the model and abilities, or a manually assembled release without a pipeline-generated AI-BOM, fails. Not applicable to a hosted-suite configuration-only promotion with no customer-assembled agent version; D8-INVENTORY still applies. *Evidence:* the release AI-BOM with its format and version, compared with the approved inventory and effective configuration, with available supplier bills linked.
- **D8-DEPS-INSTALL.** A package an agent installs during a run, or adds to the assessed deployment through an agent-authored install command or manifest, must resolve through a customer-controlled registry. Before serving it, the registry checks its name, publisher, and age and refuses disallowed packages. A registry that only blocks known malware, or an install path that bypasses the registry, fails. Agent advice that does not enter the deployment is outside scope. Not applicable where the deployment has no agent-initiated or agent-authored package install path. *Evidence:* applicable build and runtime install paths, registry policy, package-manager settings, and a refused install test.
- **D8-DEPS-LOCK.** For every package install used to build, set up, or run the assessed agent, the customer uses a lock or requirements file with an exact version and hash for each package. The installer refuses a mismatch. An install by package name or version range fails, including a global harness install at a range. Not applicable where the customer installs no package for the agent. *Evidence:* each applicable install command and lock or requirements file, plus a mismatch refusal record or test.
- **D8-DEPS-SCAN.** Each pipeline that builds or releases an agent scans every package and image the release installs or runs against a vulnerability database, including a harness its setup step installs and the images its sidecars and tools run. A finding at or above the organization's blocking threshold holds the run unless D1 grants a bounded exception; lesser findings enter the vulnerability queue. A package or image the release installs outside any scan fails the criterion. Not applicable where the organization builds and installs nothing for an agent. *Evidence:* the scan configuration, threshold, run results, held-run or exception record, and queued findings, set against every package and image the release installs or runs.
- **D8-MODEL-INSPECT.** Each model file from a less trusted source that the organization loads for an agent passes, before its first load, an architecture inspection that lists its layers without loading it and records any unknown, custom, or dynamically executed component. The owner clears or gives a D1-authorized bounded disposition to a material finding before first load. A file loaded before inspection or while a material finding lacks disposition fails. Not applicable where the organization loads no model file from a less trusted source. *Evidence:* the inspection and finding-disposition records for each such file, dated before its first load.
- **D8-MODEL-PROBE.** Each model file from a less trusted source that the organization loads for an agent is first run in an isolated environment on validation inputs or randomized probes while its resource use, system calls, and network activity are monitored. The owner clears or gives a D1-authorized bounded disposition to suspicious behavior before first production load. A probe without monitoring or a load with an unresolved material finding fails. Not applicable where the organization loads no model file from a less trusted source. *Evidence:* the probe outcomes, finding dispositions, and isolation and monitoring configuration for each file.
- **D8-MODEL-SCAN.** Before the customer first loads a model file for an agent, it records a check of the file's format, any signature it carries, and its checksum. It also scans for serialized patterns and opcodes that could run operating-system commands, subprocesses, or file access. A load policy that admits only formats that execute no code at load, such as Safetensors, replaces that executable-pattern scan but leaves the other checks. A production, pipeline, or notebook load without the checks, or with an unresolved material finding, fails. Not applicable where the customer loads no model file because the supplier hosts every model. *Evidence:* pre-load check and disposition records for each file, plus the enforced format policy where it replaces the scan.
- **D8-SIGN.** Each artifact the organization builds for a release is signed: an image, a package, a policy bundle, a chart, a managed solution file, or a revision of a workflow, skill or plugin its consumers install. A release that ships an unsigned artifact fails the criterion. Not applicable where the organization builds no artifact for a release, as for an in-suite assistant or an agent a maker publishes in place on a platform. *Evidence:* the signature or attestation of each artifact of the latest release, with the key or identity that verifies it.
- **D8-SUPPLIER.** The customer assesses each external provider or internal supplying team for the component it provides to the deployment. The assessment covers relevant development protection, testing, vulnerability disclosure, incident notice, and audit cooperation. For an external provider that processes deployment data, record the actual terms for permitted use, retention, deletion, and subcontracted processing on the assessed service route. Each answer cites evidence or a gap and decision, and the assessment sets a reassessment period. Unsupported questionnaire answers or inferred data-use promises fail. If the supplier publishes a bill of materials, match it to the supplied version; record unavailable lineage as a gap. *Evidence:* supplier assessments or internal-control reviews, cited records, applicable processing terms, and available bills of materials.
- **D8-PROMPT-PROBE.** Before a material prompt or model change reaches production, the customer probes each affected agent for disclosure of protected functionality, internal rules, filtering criteria, and permission or user-role details. The deployment's sensitivity decision identifies which details need protection. Each probe names the disclosure or action that would be unacceptable on the production route. An omitted applicable risk class or failed probe without disposition fails; disclosure of a rule classified as public does not fail by itself. *Evidence:* sensitivity-linked probe-to-risk map, versioned runs on the production route, expected and observed outcomes, and dispositions.

### L4 detail

- **D8-AIBOM-RUNTIME.** For each agent with a release AI-BOM under D8-AIBOM, the customer compares the components running at deployment and on a stated schedule with that approved bill. The comparison includes the service and configuration identifiers the customer can see and scoped supplier change records for supplier-held components. Record every difference. A runtime inventory with no approved release bill to compare against fails. Not applicable only where D8-AIBOM is not applicable. *Evidence:* runtime component records, approved release AI-BOM, scoped supplier changes, reconciliation runs, and findings.
- **D8-BUILD.** Each artifact a build produces for a release carries build provenance at SLSA Build L2 or higher: a provenance statement the build platform generates and signs, naming the source revision, build definition, and platform. The release owner authenticates the statement's signer and matches the artifact hash in the statement to the released artifact. An artifact built with no platform-generated provenance, or with a statement the build's own steps write or the release owner does not authenticate, fails. Not applicable where no build produces an artifact for a release. *Evidence:* the verified provenance statement and matching artifact hash for each artifact of the latest release, with the build platform and its SLSA level.
- **D8-DISCLOSE.** The customer names an advisory source for every type of component its agents use and routes those notices to a triage queue. For each advisory affecting a component in use, it records a fix by its severity deadline or applies D8-DISCLOSE-CONTAIN. A supplier's fix notice qualifies only if it covers the assessed service route, deployment or tenant class, named version where applicable, and affected period. An unnamed intake source, or an affecting advisory closed after its deadline without containment, fails. *Evidence:* sources by component type, severity deadlines, and the prior twelve months of affecting advisories with scoped fix evidence and closure dates.
- **D8-DISCLOSE-CONTAIN.** Before an affecting advisory passes its severity deadline without a fix, the customer records an active compensating control, owner, start, and end condition. A restricted tool, narrower network access, increased monitoring, or disabled function qualifies when it reduces the exposure. A free-text acceptance with no active treatment fails. *Evidence:* containment procedure, overdue advisory list, and dated control records.
- **D8-LINEAGE.** For each model the organization produces for an assessed agent, the producer updates a standard-format lineage record at every new model version. It names the base model, version, and hash, or states that training began from scratch. It identifies each training and fine-tuning dataset by version, checksum, source, and augmentation, and records the training code revision, libraries, environment, and owning team. The producer stores weights and configuration parameters apart from training, test, and fine-tuning data and limits read and write grants to roles that need them. A missing record, omitted applicable base model or dataset, shared store, or unneeded grant fails. Not applicable where no assessed agent calls a model the organization produces. *Evidence:* current model lineage, weight-store location and policy, and identities and roles with read or write grants.
- **D8-REPO-WRITE.** For each identity an agent can use, the repository owner limits writes at every internal artifact-repository endpoint to locations assigned to that agent's release. One run cannot alter content another run trusts; an approved immutable promotion can move content. A legacy or unauthenticated endpoint that bypasses the limit fails. Not applicable where no agent-held identity can write to an internal artifact repository. *Evidence:* agent identities, repository endpoint permissions, promotion records, and a denied-write test where used.
- **D8-RETIRE.** On a stated cadence, the customer reviews every agent component for deprecation or lack of maintenance, using a stated inactivity rule. It retires or replaces each affected component, or records an exception with an end date. An end-of-support component omitted from the review fails. *Evidence:* review cadence, inactivity rule, latest reviewed component list, and action or exception for each affected component.
- **D8-VERIFY.** Before a component installs, loads, or deploys on an organization-run system, a check outside the agent verifies its approved identity and integrity and refuses a missing or mismatched hash, signature, or attestation. A check that merely logs failure fails. For locally run MCP servers, verify author origin where an author signature is available. Not applicable where no component enters an organization-run system. *Evidence:* admission settings, approval record, and refused-component test.
- **D8-VERIFY-BUNDLE.** Verification of each model the organization loads for an agent covers every file the actual loader can use to initialize it, including weights, tokenizer, vocabulary files, configuration, and inference code. The owner reconciles the loader's file set with a signing manifest or approved list that names each required file with its hash, then verifies every listed file. A check of weights alone or a manifest that omits a loadable file fails. Not applicable where the organization loads no model file for an agent. *Evidence:* the loader file set, reconciled signing manifest or approved file-hash list, and verifier results for each file.
- **D8-VERIFY-INSTRUCT.** On a system the customer runs, a check outside the agent verifies every loaded instruction file against a hash tied to an approved origin and refuses the load on mismatch. For a supplier-published file, the origin is its supplier signature. For a customer-written file, it is a signed revision or a hash recorded in an approved release. A free-standing hash with no signed revision or release behind it fails; so does a check that only alerts. This adds origin-backed refusal to the reviewed baseline in D8-INSTRUCT-BASELINE. Not applicable where no instruction file loads on a customer-run system, as with an in-suite assistant. *Evidence:* loaded-file list, approved signatures or release hashes, verification configuration, and a refused-load record or test.
- **D8-VEX.** For each component published outside, the organization publishes an exploitability statement in a VEX format, such as CSAF, OpenVEX or CycloneDX's, for each vulnerability that affects the component, stating whether the vulnerability is exploitable in it. A published component with an affecting vulnerability and no statement fails the criterion. Not applicable where the organization publishes no component outside it. *Evidence:* the published statements, set against the vulnerabilities affecting each published component.
- **D8-MODEL-PIN.** Each production agent selects a fixed model version. A supplier-controlled name that can begin pointing to a different version without the customer's release decision fails, even if the new version is logged afterward. A model identifier without a date qualifies when the supplier documents that it always names the same release. For a supplier-held model choice, supplier evidence must show that the assessed service and route hold one version or require a customer release decision before a change. A known supplier change without that decision fails; unavailable material evidence is unanswerable. *Evidence:* production configuration, scoped supplier version and change assurance, and customer release records.
- **D8-TEST.** Before each release, the customer tests the assembled agent deployment against its material design risks and security requirements. Tests cover conventional application flaws and relevant agent paths, such as untrusted retrieved content reaching a write-capable tool, direct calls against tool authorization, or cross-agent delegation. The record identifies exact model, prompt, tool, data, policy, and configuration versions, plus expected and observed outcomes, coverage limits, findings, and retests. Repeat tests for variable model behavior and record the observed success rate. Component-only tests, a single-turn test for a multi-step risk, an unexplained omitted material path, or a finding closed without retest fails. Supplier tests cover inaccessible internals; the customer tests visible integration. *Evidence:* threat-to-test map, cases, raw results, version manifest, and retests.
- **D8-RELEASE.** For each production release or material configuration promotion, the customer records a security decision for the exact version it will deploy. The decision links D8-DESIGN, D8-IMPLEMENT, and D8-TEST results, applies the blocking threshold, lists unresolved findings and limits, and records any bounded D1-authorized exception. The promotion path refuses a missing decision or a different version. A manual, emergency, or vendor-console bypass fails; a signature alone does not satisfy the decision. In a hosted suite, the customer's enablement or configuration promotion is the decision point. *Evidence:* decision, approver, version or artifact hash, linked results, exception, and refusal test.

### L5 detail

- **D8-A2A-SIGN-TEST.** Before each release that carries Agent2Agent traffic, test the Agent Cards the deployment publishes or consumes against its approved signing profile. A consuming client rejects a card with a missing, altered, or untrusted signature before using its endpoint or capabilities; a published card is tested with a conforming receiver. A signature check described only in configuration fails. Not applicable where the deployment carries no Agent2Agent traffic. *Evidence:* release-linked test record, signing profile, signed Agent Cards, trust anchors, and receiver rejection results.
- **D8-AIBOM-DRIFT.** For each agent with a release AI-BOM, the customer states which runtime-to-release differences it tolerates and the longest each may remain. It closes a difference within that limit or opens a finding with an owner. An overdue difference without an owned finding fails. Not applicable only where D8-AIBOM is not applicable. *Evidence:* drift tolerance and time limits, reconciliation history, and dated closures or owned findings.
- **D8-BUILD-HARDENED.** Each organization-built release artifact carries SLSA Build L3 provenance from an isolated builder whose signing material is unavailable to the build steps. An ordinary attestation without builder isolation fails. Not applicable where no build produces a release artifact. *Evidence:* signed provenance, builder assurance, and, where feasible, an independent matching rebuild.
- **D8-LOOP.** On a stated production schedule, the customer reconciles each agent's approved component inventory with its D8 findings and current deployment. For an agent with D8-AIBOM, it also compares the release and runtime AI-BOMs. Otherwise it compares effective customer configuration and scoped supplier changes with the approved inventory. Every discrepancy becomes a finding with an owner. An on-request-only run, an omitted applicable input, or an ownerless discrepancy fails. *Evidence:* configured inputs and schedule, run history, and owned findings.
- **D8-LOOP-SLA.** The customer publishes a D8 finding-response deadline to deployment owners. Each finding from reconciliation, scanning, assessment, verification, or an advisory must lead to a control change or recorded decision within that deadline. Check every finding in the quarter before the assessment. A closure without either outcome, or one past the deadline, fails. *Evidence:* published SLA and the quarter's findings, each linked to its dated control change or decision.
- **D8-VERIFY-GATE.** For an agent with an approved release AI-BOM, the customer makes every production promotion route, including manual and emergency routes, refuse an artifact that fails verification or a component set that differs from that bill. A gate on only the main pipeline fails. Not applicable only where D8-AIBOM is not applicable. *Evidence:* admission policy for each route and a refused-promotion test.
- **D8-VEX-FEED.** For each component the organization publishes to outside consumers, serve its D8-VEX statements in a machine-readable feed with vulnerability identifiers and update them within a published period. A static document that consumers cannot poll or an affecting vulnerability omitted past the deadline fails. Not applicable where no component is published outside the organization. *Evidence:* feed endpoint, statement match, publication dates, and deadline.
- **D8-WEIGHTS.** For each produced model whose weights D8-LINEAGE stores under separate, least-privilege access, monitor the integrity of its weights and configuration parameters continuously and use approved hashes or signatures to detect unauthorized changes, as [[nist-sp-800-218a|NIST SP 800-218A]] `PS.1.3` recommends. A monitoring gap or a weight change that bypasses the integrity check fails. Not applicable where no agent in scope calls a produced model. *Evidence:* weight-store integrity monitoring, its run history and alerts, and the hash or signature verification configuration with a detected-change test or incident record.

## Prerequisites and blockers

D8-RELEASE needs D1's named risk authority and D8-DESIGN, D8-IMPLEMENT, and D8-TEST results for the exact version it promotes. A missing supplier test report is an evidence gap or unanswerable facet. It does not remove the supplier-held part from assessment. D8-AIBOM-RUNTIME and D8-VERIFY-GATE need a release AI-BOM that names the actual component set. D8-LOOP instead uses approved inventory, effective configuration, and supplier changes where that AI-BOM is not applicable. A deployment with a weak component inventory cannot claim that a runtime comparison found every drift. [[agentic-ai-security-cmm-d3-control-least-agency|D3]] authorizes an agent's actions, [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] confines them at run time, [[agentic-ai-security-cmm-d5-egress-network|D5]] enforces live egress and Agent Card verification, and [[agentic-ai-security-cmm-d7-observability|D7]] monitors them. D8 verifies the proposed release and acquired parts before they enter those paths. Missing prerequisites are named against the criterion and target they block.

## Deployment-shape differences

| Shape | Material D8 difference |
|---|---|
| Hosted assistant, such as Gemini Enterprise | The customer can show connected stores, connector authorization, and tested configuration. A federated connector that searches a source in place imports no dataset. An ingested corpus copied into the app index does. Google supplies model internals. |
| Organization-built RAG agent | The customer inventories the assembled agent. An acquired retrieval corpus reaches D8-DATASET; the release AI-BOM and integration tests cover the running model and tools. |
| Coding agent fleet, such as Claude Code | The fleet owner can show installed harness versions, effective managed, user, and project settings, approved skills and MCP servers, and package gates on each device or runner. |
| Model producer or external component publisher | A produced model reaches lineage and weight controls. VEX and its feed apply to components the organization publishes outside. |

[Claude Code's settings documentation](https://code.claude.com/docs/en/settings) distinguishes managed, user, and project scopes. A repository the coding agent reads is an input, not an imported dataset solely because the agent reads it. [Gemini Enterprise's connector documentation](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/introduction-to-connectors-and-data-stores) distinguishes queries against a source in place from ingestion that copies content into an index. If the app does not expose its selected model version, D8-VERSION needs scoped Google evidence.

A supplier's claim does not prove a customer integration. The release test must cross the customer's actual trust boundaries even when the model or platform internals are inaccessible. Conversely, the customer does not need to claim access to a supplier's weights or source code to use supplier assurance as evidence. Record the exact evidence class and its limitation in the criterion result.

## Implementation and effort drivers

The largest implementation work is the component inventory and a release path that can name the version it tested and deployed. Package locks, registry checks, model-file scans, signatures, and provenance each close a different entry path. A release decision links them to the security tests and open findings. A vendor-managed suite shifts effort toward supplier evidence, customer configuration review, and tests of visible integration and enablement. A coding fleet shifts it toward managed settings and local installation control. Produced models add lineage, protected weight storage, and supplier obligations to their consumers.

Operating cost comes from advisory triage, repeated scans, supplier reassessment, runtime-to-release reconciliation, and exceptions that need an owner and end condition. Risk-based targets can stop short of L5 for a low-impact consumer deployment; L5 remains achievable where its applicable controls have real implementations and evidence. D8-VEX-FEED is producer-specific, so a model consumer with no externally published component does not need to invent a feed. External working-group participation, universal supplier-BOM federation, and independent reproducible builds are not scored conditions.

## Sources and material limits

[NIST SSDF](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf) supplies software design, review, test, and release practices; its [AI profile](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218A.pdf) addresses AI-specific assets and provenance. The [OWASP AI Exchange supply-chain](https://owaspai.org/go/supplychainmanage/), [secure development](https://owaspai.org/docs/1_general_controls/#sec-dev-program), and [agentic testing](https://owaspai.org/docs/5_testing/#agentic-ai-security-testing) sections inform the component and release checks. [SLSA build requirements](https://slsa.dev/spec/v1.2/build-requirements) support the provenance levels. These sources do not require the AAI-S CMM's exact level assignments. An AI-BOM, signature, scan, or model document is evidence about one property, not a substitute for the assembled deployment's security test and release decision.

The [A2A specification](https://github.com/a2aproject/A2A/blob/main/docs/specification.md#84-agent-card-signing) defines optional Agent Card signatures. It does not define general message signatures; D8-A2A-SIGN-TEST grades a release test of card verification, while D5 grades runtime enforcement.
