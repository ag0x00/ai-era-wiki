# Agentic AI Security CMM — D8 Engineering and Supply Assurance

## Domain decision and boundary

D8 grades what the engineering and supply owners can establish before a defined agentic deployment or material configuration change enters use, then checks the provenance and continuing integrity of what it consumes. The assessment unit is one deployment, its agents, their models, harnesses, abilities, libraries, data, release artifacts, and suppliers. A consumer of a hosted model remains in scope for supplier assurance, customer configuration, integration testing, and the release decision; model-file checks are conditional on the customer loading model files. A team that trains or fine-tunes a model also grades the producer criteria. A team that publishes a component for external consumers grades the publication criteria. [[agentic-ai-security-cmm-2026|The CMM core]] defines the five cumulative levels, and [[agentic-ai-security-cmm-measurement-protocol|the Assessor's Handbook]] records the evidence and determination.

D8 owns design review, first-party implementation checks, assembled-system tests, and the release decision. [[agentic-ai-security-cmm-d1-governance|D1]] supplies risk authority and accepts bounded residual risk. [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] grades controls while an agent runs. [[agentic-ai-security-cmm-d7-observability|D7]] grades production detection and recurring evaluation. A D8 test can exercise a D4 or D7 control, but one passing release test does not show continuous operation. D8-RELEASE records a D1-authorized exception and enforces the release path; it does not grant that exception. A supplier-held development or model step requires relevant supplier evidence. Missing evidence for a material existing step is unanswerable. Customer-controlled configuration and integration remain assessable even when the platform is hosted.

A component is a model the agent calls, its hosting service, its harness or platform, each ability, AI framework library, acquired dataset, and security-relevant configuration. An ability is a supplied skill, plugin, connector, local or remote MCP server, external agent, or tool adapter. A supplier can be an external provider or an internal team that supplies a component across an organizational boundary. A release includes an image, package, workflow revision, managed configuration, platform publication, or vendor-console promotion that changes the assessed deployment. A build criterion applies when a build produces an artifact; a vendor-console change still enters D8-DESIGN, D8-TEST, and D8-RELEASE. Evidence can be inherited from a common build, supplier assessment, or managed fleet only where its scope, version, and date cover the deployment. Each criterion is met across its full applicable population, including manual and emergency paths. A missing component, failed check, or undocumented exception defeats a claim of full coverage.

The supplier assessment identifies model-file sources whose integrity assurance is insufficient for direct loading. These are the less trusted sources in D8-MODEL-INSPECT and D8-MODEL-PROBE. A missing source assessment cannot make either criterion inapplicable.

## Failure paths

A dependency, model file, tool definition, instruction pack, or copied configuration can carry hostile behavior into an agent. A valid signature identifies an origin but does not establish that the code or prompt is safe; the release decision therefore considers design, implementation, and assembled-system test results as well as integrity. A shared artifact repository can also become a write channel between agents or runs. The [OWASP AI Exchange supply-chain control](https://owaspai.org/go/supplychainmanage/) covers component records, acquisition, verification, and drift. [NIST's AI-focused Secure Software Development Framework profile](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218A.pdf) addresses model and AI component provenance. The criteria below are this model's assessable synthesis, not clauses imported from either source.

## Level progression

| Level | Observable outcome |
|---|---|
| L1 | A characterized deployment has a known gap in its foundational engineering or supply records or controls. |
| L2 | Sources, versions, model cards, acquired-data provenance, and sensitive engineering records are identified and controlled. |
| L3 | Repeatable engineering checks cover material designs, first-party changes, supplied components, and applicable prompt or harness changes before use. |
| L4 | The assembled deployment is tested before promotion; deployed components, build provenance, advisory response, and exact version admission are verified. |
| L5 | Reconciliation, verification gates, supplier-facing feeds where produced, and owned findings have sustained, time-bound outcomes. |

A known failure of any applicable L2 criterion establishes the D8 L1 state. If no L2 failure is known but an applicable L2 fact remains unresolved, report D8 as unanswerable outside the level scale until the evidence resolves it. Supplier ownership does not establish a failure or make the fact inapplicable.

## Criterion catalogue

A pass requires every stated facet. A negative test must reach the actual install, load, promotion, or approval path. “Verified” means a check outside the agent compares the item with an approved signature, attestation, or pinned digest and refuses a mismatch. A finding above a blocking threshold can proceed only through a bounded exception granted by the D1 risk authority. For a supplier-held part, inspect a supplier record that names the relevant product and practice, or record why the material step remains unanswerable. [NIST SSDF](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf) grounds the design, code review, test, and release sequence; [OWASP AI Exchange testing guidance](https://owaspai.org/docs/5_testing/#agentic-ai-security-testing) identifies agent-specific paths to exercise.

### L2 detail

- **D8-DATASET.** For each acquired dataset, a record gives the sources its content came from and each step that transformed it before the organization received it, such as filtering, labelling or augmentation, as the supplier documents them or the organization's own records show. A dataset that holds references to content rather than the content, such as a list of URLs, carries a checksum of each referenced entry, taken when the organization acquired it, because referenced content can change or disappear after the list is published. A record that names the dataset and none of its sources fails the criterion. Not applicable where the deployment holds no acquired dataset. *Evidence:* the provenance record of each acquired dataset, set against the inventory's dataset entries, with the entry checksums of a dataset held by reference.
- **D8-DOCS.** The organization's asset register lists, as information assets, the documentation it writes of each agent's design and development and of each model it trains, fine-tunes or evaluates for an agent, and the record of experiments behind such a model, such as an experiment-tracking server's runs. Customer-written design records for a configured in-suite assistant are included. Each entry names the store that holds the documentation and its owner. A store of such documentation the register omits fails the criterion. Not applicable only where the organization writes no such documentation. *Evidence:* the register entries, set against the stores that hold the deployment's design, development, model and experiment documentation, including configuration-design records.
- **D8-DOCS-ACCESS.** Each documentation store listed under D8-DOCS restricts reading to the people and roles its owner names as needing it, and the store's access list matches those names. A store that every employee, or any address on the network, can read fails the criterion. Not applicable where D8-DOCS is not applicable. *Evidence:* the access list of each store, set against the roles its owner names.
- **D8-INVENTORY.** A record, or the records it names, lists each component of each agent in scope, and each entry gives the component's source, meaning the registry, marketplace, repository or service it comes from, its version, its maintainer, the date it entered the deployment at that version and, for a component the organization holds as a file or an image, its hash or digest. A record the inventory names, such as a lock file or a release's image digest, can carry a field. The inventory matches the components each agent's configuration runs on the assessment date. A component the configuration runs and the inventory omits fails the criterion, and so do an entry missing a field and an entry whose version differs from the one running. A field the supplier does not disclose, such as the version of a model its vendor names none for, is recorded as undisclosed, and D8-VERSION grades the gap. A service its vendor runs without released versions, such as an in-suite assistant's platform or a hosted connector, carries no version field. *Evidence:* the inventory, each entry read field by field and set against the running configuration, the lock files, the image digests or the device inventory.
- **D8-MODEL-CARD.** For each model an agent calls, the organization holds the card its supplier publishes for the model, or for the model family at the version in use, such as a model card or a system card, dated or versioned so that it matches the version D8-VERSION records. A transparency note or a service description that names no model is no card, and a card for another version fails the criterion. For a produced model, the card the organization writes meets it. Where the vendor names no model, the criterion is unanswerable for that model. *Evidence:* the saved card for each model, with its date or version, set against the version in use.
- **D8-VERSION.** The version of each model an agent calls, and of its harness or platform, each ability and each AI framework library where the supplier releases versions of it, is recorded for each period it ran over the twelve months before the assessment starts, or since the agent entered scope where that is more recent. A version range or mutable model alias meets the criterion only where a run record or scoped supplier mapping identifies the resolved version for each run or bounded period; a log of the requested alias alone does not. A dateless identifier can itself name a fixed version when the supplier documents that it is immutable. A period for which no record gives the resolved version fails the criterion. Where the supplier names no version, as for a model an in-suite assistant's vendor chooses and does not name, the criterion is unanswerable for that component. *Evidence:* the resolved version history of each component over the period, from change records, run logs, the device inventory or scoped supplier change notices, set against the dates the configuration changed.
- **D8-PROMPT-SECRETS.** Review each customer-controlled effective system prompt before use. Each effective prompt contains no credential or key; database names, role details, and permission structure receive a documented disclosure-sensitivity decision tied to the deployment's threat model. A credential in a prompt fails, as does a sensitive detail with no treatment decision. For a supplier-held prompt, obtain a scoped supplier assertion covering secret absence and sensitivity treatment for the assessed service and route. A customer leak test can establish a disclosure failure but cannot establish that an inaccessible prompt contains no secret. Without adequate supplier evidence, the supplier-held facet is unanswerable. *Evidence:* inspected customer prompt or scoped supplier assertion, review, and treatment decisions, with customer test results where used.

### L3 detail

- **D8-DESIGN.** Before each material release or configuration change, the engineering owner records assets, trust boundaries, untrusted input paths, agent actions, suppliers, and credible failure paths. A reviewer maps each material risk to a control, design change, or D1-authorized residual-risk decision and rechecks any reused threat model against the release. A new tool, authority, untrusted input, data path, or supplier boundary with no treatment fails. Supplier design evidence covers supplier-held parts; the customer reviews its integration. *Evidence:* versioned architecture, change-linked threat model, security requirements, review, and treatment record.
- **D8-HARNESS.** *Deployment.* Each harness-configurable coding agent of the deployment runs under managed settings on each device or runner that hosts it, and no local scope overrides a managed setting. An agent on a device or runner that carries no managed settings fails the criterion. Not applicable where the deployment runs no harness-configurable coding agent. *Evidence:* the complete device and runner population, its managed-source assignments, and effective settings reconciled by configuration class, with resolved-setting checks on each distinct class and exception.
- **D8-HARNESS-EXTEND.** *Deployment.* A record the organization keeps names each list key in the managed settings that a local scope can still extend, with the entries each local scope may add. A key the harness merges from a local scope and the record omits fails the criterion. Not applicable where the deployment runs no harness-configurable coding agent, or where no local scope can extend a managed list key. *Evidence:* the record, set against the harness's documentation of the keys that merge across scopes.
- **D8-HARNESS-LOCK.** *Deployment.* The managed settings set each managed-only lock the harness offers over permission rules, hooks, MCP servers, and plugins or skills from user or project sources. A lock the harness offers and the settings leave unset fails the criterion. Not applicable where the deployment runs no harness-configurable coding agent, or where the harness offers no managed-only lock. *Evidence:* the lock values in the resolved managed settings, set against the locks the harness documents.
- **D8-HARNESS-RESTORE.** *Deployment.* The managed settings file on each device or runner returns to the published version whenever it differs: the fleet's management restores it at an interval the organization states, or each run starts from an image that carries it. Not applicable where the deployment runs no harness-configurable coding agent, or where no person or process on the device or runner can change the managed file. *Evidence:* the restore mechanism's configuration, with its log of a restore or a test of it.
- **D8-HARNESS-REVIEW.** *Deployment.* Each change to the deployment's harness configuration tree passes a documented review before it takes effect, whether it changes the managed settings or a hook, an MCP server definition, a subagent, a skill or an instruction file the harness loads. A change a developer makes on their own device with no review, or a project settings change that takes effect in the run of the pull request that carries it, fails the criterion. Not applicable where the deployment runs no harness-configurable coding agent. *Evidence:* the complete change history and the enforced review path, with review timestamps and effective revisions sampled across distinct change routes and likely bypasses.
- **D8-IMPLEMENT.** Before merge or release, every organization-controlled change to agent code, orchestration, tool integration, policy enforcement, data preparation, and security-relevant configuration receives a security check matched to its design risks. Human review and blocking static analysis cover executable code, including agent-generated code. A bypassed change, generated code merged without the analysis, or a blocking finding shipped without D1-authorized disposition fails. Supplier-controlled implementation requires supplier development evidence; customer-modifiable configuration stays in customer scope. *Evidence:* change list, scanner and review results, held findings, dispositions, and checked-to-shipped revision link.
- **D8-INSTRUCT-BASELINE.** Each file an agent loads as instructions matches a baseline recorded for its reviewed version, checked when the agent loads it, and a change reaches the agent only as a new reviewed version with a new baseline. Two mechanisms meet the check: a hash baseline verified at session start and after each change, where a mismatch holds the session or raises an alert, or an immutable artifact pinned by digest, such as a container image, which the runtime verifies when it loads it and which the running agent cannot write. A file that an agent or another writer can change and a later load reads with no check against a baseline, such as a rules file one session edits and the next loads unchecked, fails the criterion. *Evidence:* the baseline for each instruction file, with the check that verifies it at load, and for a hash baseline its record of a mismatch or a test of it.
- **D8-ABILITY-SCAN.** Each ability that installs code or instructions on a system the organization runs, such as a skill, a plugin, a local MCP server or a harness extension, passes a scan for malicious code and instructions before it installs, and again at each new version. A positive finding is cleared or receives a D1-authorized bounded disposition before installation; an ability installed without a scan or disposition for its version fails. Not applicable where no ability installs on a system the organization runs. *Evidence:* the scan result and disposition for each such ability and version, dated before its install.
- **D8-ABILITY-SOURCE.** Each ability an agent uses comes from a source the organization approved for that ability, and the approval names the ability, its publisher and the source it installs from or is reached at, such as a marketplace entry, a registry namespace or a server's URL. A configuration that restricts the agents to the approved entries meets the criterion as the approval record. An approval of a class that admits abilities nobody reviewed, such as a setting that admits every agent a vendor builds or every plugin of a public marketplace, fails the criterion for each ability it admits. Not applicable where no agent uses an ability. *Evidence:* the approval record or the enforced configuration, set against the abilities each agent uses.
- **D8-AIBOM.** Each agent version the organization assembles or publishes has a pipeline-generated AI bill of materials in a standard machine-readable format. It covers the release's models, hosting services, harness or platform, abilities, AI framework libraries, acquired datasets, and security-relevant configuration, with disclosed versions and digests for held files. A supplier-held service or component whose version is undisclosed remains named with that status. D8-VERSION grades the unresolved version. An image SBOM that omits model and tools, or a manually assembled release with no pipeline-generated AI-BOM, fails. Not applicable where the organization releases no assembled agent version, including a configuration-only promotion in a hosted suite. D8-INVENTORY still covers that deployment. *Evidence:* release AI-BOM reconciled with the approved component inventory and effective configuration, with supplier bills of materials linked when available.
- **D8-DEPS-INSTALL.** Each package an agent installs at run time, or that enters the assessed deployment through an agent-authored install command or manifest in a governed development workflow, resolves through a registry the organization controls. The registry refuses a package that fails a check of its name, publisher, and age before it serves it, such as a policy that blocks a newly published package or a name resembling an internal or popular package. A registry that blocks only packages already marked malicious fails, as does a path to a public registry that bypasses the organization's registry. Ordinary advice that does not change the assessed deployment is outside this criterion. Not applicable where the deployment has no agent-initiated or agent-authored package install path. *Evidence:* the applicable build and runtime install paths, registry policy, package-manager configurations, and a refused install or test.
- **D8-DEPS-LOCK.** Each install of packages for an agent, in its build, its setup step or its runtime image, installs from a lock file or a requirements file that pins each package to an exact version with its hash, and the install fails on a mismatch, as `npm ci`, a Poetry install from a checked lock file or `pip install --require-hashes` do. An install by name or by version range, such as `npm install -g` at a range, fails the criterion. Not applicable where the organization installs no package for an agent. *Evidence:* the install command and the lock file of each install, with a run that failed on a mismatch or a test.
- **D8-DEPS-SCAN.** Each pipeline that builds or releases an agent scans every package and image the release installs or runs against a vulnerability database, including a harness its setup step installs and the images its sidecars and tools run. A finding at or above the organization's blocking threshold holds the run unless D1 grants a bounded exception; lesser findings enter the vulnerability queue. A package or image the release installs outside any scan fails the criterion. Not applicable where the organization builds and installs nothing for an agent. *Evidence:* the scan configuration, threshold, run results, held-run or exception record, and queued findings, set against every package and image the release installs or runs.
- **D8-MODEL-INSPECT.** Each model file from a less trusted source that the organization loads for an agent passes, before its first load, an architecture inspection that lists its layers without loading it and records any unknown, custom, or dynamically executed component. The owner clears or gives a D1-authorized bounded disposition to a material finding before first load. A file loaded before inspection or while a material finding lacks disposition fails. Not applicable where the organization loads no model file from a less trusted source. *Evidence:* the inspection and finding-disposition records for each such file, dated before its first load.
- **D8-MODEL-PROBE.** Each model file from a less trusted source that the organization loads for an agent is first run in an isolated environment on validation inputs or randomized probes while its resource use, system calls, and network activity are monitored. The owner clears or gives a D1-authorized bounded disposition to suspicious behavior before first production load. A probe without monitoring or a load with an unresolved material finding fails. Not applicable where the organization loads no model file from a less trusted source. *Evidence:* the probe outcomes, finding dispositions, and isolation and monitoring configuration for each file.
- **D8-MODEL-SCAN.** Each model file the organization loads for an agent passes, before its first load, a recorded check that validates its format and any signature it carries, scans it for opcodes and serialized patterns that invoke operating-system commands, subprocesses, or file access, and checks it for corruption against a checksum. An enforced load policy that admits only formats that execute no code at load, such as Safetensors, meets the scan and leaves the format and checksum checks to run. A load with no check or an unresolved material finding, whether in production, a pipeline, or a notebook, fails. Not applicable where the organization loads no model file for an agent, as where the supplier hosts every model an agent calls. *Evidence:* the check and disposition records of each model file, dated before its first load, with the enforced load policy and the formats it admits where the policy replaces the scan.
- **D8-SIGN.** Each artifact the organization builds for a release is signed: an image, a package, a policy bundle, a chart, a managed solution file, or a revision of a workflow, skill or plugin its consumers install. A release that ships an unsigned artifact fails the criterion. Not applicable where the organization builds no artifact for a release, as for an in-suite assistant or an agent a maker publishes in place on a platform. *Evidence:* the signature or attestation of each artifact of the latest release, with the key or identity that verifies it.
- **D8-SUPPLIER.** Assess each external provider or internal team that supplies a model, hosting service, harness, ability, or acquired dataset against relevant security requirements, including development protection, testing, vulnerability disclosure, incident notice, and audit cooperation. Internal-control records can establish an internal team's practice. For an external provider that processes deployment data, record the terms governing permitted data use, retention, deletion, and subcontracted processing for the service and route in use. Each answer cites applicable evidence or a recorded gap and decision, with a reassessment period. A questionnaire with unsupported “yes” answers or an inferred data-use promise fails. Where a supplier publishes a bill of materials, reconcile the supplied version; record absent lineage as an evidence gap. *Evidence:* external assessments or internal-control reviews, cited records, applicable processing terms, and available bill-of-materials links.
- **D8-PROMPT-PROBE.** Before each material prompt or model change reaches production, run leak probes against each affected agent for functionality, internal rules, filtering criteria, and permissions or user roles that the deployment's sensitivity decision identifies as protected. Each case names the disclosure or action that would be unacceptable on the production route. A set omitting an applicable risk class or a failed case with no disposition fails; disclosure of a rule classified as public is not a failure by itself. *Evidence:* sensitivity-linked probe-to-risk map, versioned runs on the assessed route, expected and observed outcomes, and dispositions.

### L4 detail

- **D8-AIBOM-RUNTIME.** At deployment and on a stated schedule, compare each agent's observed runtime components in the D8-AIBOM population with its approved release AI-BOM and record each difference. The comparison includes customer-visible service and configuration identifiers and uses scoped supplier change evidence for supplier-held components. Runtime discovery without a release baseline fails. Not applicable only when D8-AIBOM is not applicable. *Evidence:* runtime component record, release AI-BOM, scoped supplier changes, reconciliation runs, and findings.
- **D8-BUILD.** Each artifact a build produces for a release carries build provenance at SLSA Build L2 or higher: a provenance statement the build platform generates and signs, naming the source revision, build definition, and platform. The release owner authenticates the statement's signer and matches its subject digest to the released artifact. An artifact built with no platform-generated provenance, or with a statement the build's own steps write or the release owner does not authenticate, fails. Not applicable where no build produces an artifact for a release. *Evidence:* the verified provenance statement and subject digest of each artifact of the latest release, with the build platform and its SLSA level.
- **D8-DISCLOSE.** Advisories for each component of each agent reach a queue the organization triages, from a source it names for each type of component, such as the dependency scanner for packages, each harness's and ability's advisory feed, each model provider's notices, and each platform vendor's security bulletins. Each advisory that affects a component the deployment runs is remediated within the deadline the organization sets for its severity, or passes to D8-DISCLOSE-CONTAIN. An advisory the vendor remediates in its own service closes on a fix notice that covers the assessed service route, deployment or tenant class, version where named, and period. A type of component with no named source fails, as does an affecting advisory closed past its deadline with no containment on record. *Evidence:* the intake source named for each component type, deadlines by severity, and each affecting advisory of the prior twelve months with its scoped fix evidence and closure date.
- **D8-DISCLOSE-CONTAIN.** For each affecting advisory that cannot be fixed before its severity-based deadline, record the compensating control, owner, start, and end condition before the deadline. Restricting a tool, narrowing network access, increasing monitoring, or disabling a function can qualify when it reduces the advisory’s exposure. A free-text acceptance with no active treatment fails. *Evidence:* procedure, overdue advisory list, and each dated containment record.
- **D8-LINEAGE.** Each produced model carries a lineage record in a standard format, updated at each new version. The record names its base model with version and hash where it derives from one, or states that it was trained from scratch. It identifies each training and fine-tuning dataset with its version, checksum, sources, and augmentation steps. It also names the training code revision, its libraries and environment, and the team that owns the model. The weights and configuration parameters occupy a store separate from training, testing, and fine-tuning data. Named roles receive only the read or write access their work needs. A missing lineage record, omitted applicable base or dataset, shared data-and-weight store, or unneeded weight-store grant fails. Not applicable where no agent in scope calls a produced model. *Evidence:* the lineage record of each produced model's current version, weight-store location and access policy, and the roles and identities with read or write grants.
- **D8-REPO-WRITE.** For every identity an agent can use and every endpoint of an internal artifact repository, writes are limited to that agent’s own release locations. One run cannot change content another run trusts; a controlled immutable promotion can move approved content. A legacy or unauthenticated write endpoint that bypasses the rule fails. Not applicable where no agent-held identity can write to such a repository. *Evidence:* identities, endpoint ACLs, and promotion records or a denied write test.
- **D8-RETIRE.** A review on a cadence the organization sets reads each component of each agent for deprecation and for its maintenance state, against an inactivity rule the review states, and each component it finds deprecated or unmaintained is retired, replaced or given a recorded exception with an end date. A component past its maintainer's end-of-support date that no review record covers fails the criterion. *Evidence:* the review's cadence and rule, with its latest record listing the components it read and the action taken on each it found.
- **D8-VERIFY.** Before a component installs, loads, or deploys on an organization-run system, a check outside the agent verifies its approved identity and integrity and refuses a missing or mismatched digest, signature, or attestation. A check that merely logs failure fails. For locally run MCP servers, verify author origin where an author signature is available. Not applicable where no component enters an organization-run system. *Evidence:* admission settings, approval record, and refused-component test.
- **D8-VERIFY-BUNDLE.** Verification of each model the organization loads for an agent covers every file the actual loader can use to initialize it, including weights, tokenizer, vocabulary files, configuration, and inference code. The owner reconciles the loader's file set with a signing manifest or pinned list that names each required file with its digest, then verifies every listed file. A check of weights alone or a manifest that omits a loadable file fails. Not applicable where the organization loads no model file for an agent. *Evidence:* the loader file set, reconciled signing manifest or pinned list, and verifier results for each file.
- **D8-VERIFY-INSTRUCT.** Each file an agent loads as instructions, whoever writes it, the object D8-INSTRUCT-BASELINE holds to a baseline, is verified at each load against a digest whose origin is on record: its supplier's signature, for a file a supplier publishes, such as a skill's instructions, or a signed revision or a release's pinned digest, for a file the organization writes, such as a system prompt built into an image deployed by digest or a rules file in a signed commit. A mismatch or a missing signature stops the load. A file checked against a baseline that traces to no signature and no release, or one whose mismatch only raises an alert, fails the criterion. Not applicable where no instruction file loads on a system the organization runs, as for an in-suite assistant. *Evidence:* the verification step with the signatures or digests it checks, set against each file an agent loads as instructions, and a refused load or a test.
- **D8-VEX.** For each component published outside, the organization publishes an exploitability statement in a VEX format, such as CSAF, OpenVEX or CycloneDX's, for each vulnerability that affects the component, stating whether the vulnerability is exploitable in it. A published component with an affecting vulnerability and no statement fails the criterion. Not applicable where the organization publishes no component outside it. *Evidence:* the published statements, set against the vulnerabilities affecting each published component.
- **D8-MODEL-PIN.** Each production agent selects a fixed model version rather than an alias the provider can repoint without the customer's release decision. A dateless model identifier qualifies when the supplier documents that it names an immutable snapshot. An alias whose resolved version is logged but changes without promotion fails. For a supplier-held model choice, provider evidence must establish that the assessed service and route hold a fixed version or require a customer release decision before a change. A known unilateral repoint fails; unavailable material evidence is unanswerable. *Evidence:* production configuration, scoped provider version and change assurance, and customer release records.
- **D8-TEST.** Before release, test the assembled deployment against material design risks and security requirements, including conventional application flaws and relevant agent-specific paths. Selected paths can include untrusted retrieved content reaching a write-capable tool, direct calls against tool authorization, or cross-agent delegation. Records identify model, prompt, tools, data, policy, and configuration versions, expected and observed outcome, coverage limits, findings, and retests. Variable model outcomes include repetitions and observed success rate. Component tests alone, a single-turn probe for a multi-step risk, an omitted material path with no reason, or a “fixed” finding without retest fails. Supplier tests cover inaccessible internals while customer-visible integrations remain in customer scope. *Evidence:* threat-to-test map, cases, raw results, manifest, and retests.
- **D8-RELEASE.** Each production release or material configuration promotion has a recorded security decision bound to the exact deployed version. It checks D8-DESIGN, D8-IMPLEMENT, and D8-TEST, applies the approved blocking threshold, lists unresolved findings and limits, and records any bounded exception from the D1 risk authority. The promotion path refuses a missing decision or unapproved version. A manual, emergency, or vendor-console bypass fails; a signature alone is insufficient. For a managed suite, customer enablement or configuration promotion is the decision point. *Evidence:* decision, approver, version or digest, linked results, exception, and refusal test.

### L5 detail

- **D8-A2A-SIGN-TEST.** Before each release that carries Agent2Agent traffic, test the Agent Cards the deployment publishes or consumes against its approved signing profile. A consuming client rejects a card with a missing, altered, or untrusted signature before using its endpoint or capabilities; a published card is tested with a conforming receiver. A signature check described only in configuration fails. Not applicable where the deployment carries no Agent2Agent traffic. *Evidence:* release-linked test record, signing profile, signed Agent Cards, trust anchors, and receiver rejection results.
- **D8-AIBOM-DRIFT.** For each agent covered by D8-AIBOM, set a tolerance for runtime-to-release AI-BOM differences and how long each can remain. Close each difference within tolerance or raise an owned finding. A difference left open past its limit without a finding fails. Not applicable only when D8-AIBOM is not applicable. *Evidence:* tolerance, reconciliation history, and dated closures or findings.
- **D8-BUILD-HARDENED.** Each organization-built release artifact carries SLSA Build L3 provenance from an isolated builder whose signing material is unavailable to the build steps. An ordinary attestation without builder isolation fails. Not applicable where no build produces a release artifact. *Evidence:* signed provenance, builder assurance, and, where feasible, an independent matching rebuild.
- **D8-LOOP.** A reconciliation runs in production on a schedule the organization sets and joins each agent's component inventory and the deployment's D8 findings. Where D8-AIBOM applies, it also joins the release and runtime AI-BOMs; otherwise it compares the approved inventory with effective customer configuration and scoped supplier changes. Each discrepancy becomes a finding with an owner. A reconciliation run only on request, one that omits an applicable input, or one that records no owner fails. *Evidence:* the reconciliation's inputs, configuration and schedule, run history, and owned findings.
- **D8-LOOP-SLA.** Each D8 finding, from the reconciliation, a scan, an assessment, a verification or an advisory, reaches a change to a control or a recorded decision within an SLA the organization publishes to the deployment's owners, and the record shows the SLA met for each finding over the quarter before the assessment starts. A finding closed with no control change and no decision fails the criterion, and so does one closed past the SLA. *Evidence:* the published SLA, with each finding of the quarter and the control change or decision that closed it, with its date.
- **D8-VERIFY-GATE.** Every production promotion route for an agent covered by D8-AIBOM, including manual and emergency routes, refuses an artifact that fails verification or a component set that differs from the approved AI-BOM. A gate on only the main pipeline fails. Not applicable only when D8-AIBOM is not applicable. *Evidence:* each route's admission policy and a refused promotion test.
- **D8-VEX-FEED.** For each component the organization publishes to outside consumers, serve its D8-VEX statements in a machine-readable feed with vulnerability identifiers and update them within a published period. A static document that consumers cannot poll or an affecting vulnerability omitted past the deadline fails. Not applicable where no component is published outside the organization. *Evidence:* feed endpoint, statement match, publication dates, and deadline.
- **D8-WEIGHTS.** For each produced model whose weights D8-LINEAGE stores under separate, least-privilege access, monitor the integrity of its weights and configuration parameters continuously and use approved hashes or signatures to detect unauthorized changes, as [[nist-sp-800-218a|NIST SP 800-218A]] `PS.1.3` recommends. A monitoring gap or a weight change that bypasses the integrity check fails. Not applicable where no agent in scope calls a produced model. *Evidence:* weight-store integrity monitoring, its run history and alerts, and the hash or signature verification configuration with a detected-change test or incident record.

## Prerequisites and blockers

D8-RELEASE needs D1's named risk authority and D8-DESIGN, D8-IMPLEMENT, and D8-TEST results for the exact version it promotes. A missing supplier test report is an evidence gap or unanswerable facet. It does not remove the supplier-held part from assessment. D8-AIBOM-RUNTIME and D8-VERIFY-GATE need a release AI-BOM that names the actual component set. D8-LOOP instead uses approved inventory, effective configuration, and supplier changes where that AI-BOM is not applicable. A deployment with a weak component inventory cannot claim that a runtime comparison found every drift. [[agentic-ai-security-cmm-d3-control-least-agency|D3]] authorizes an agent's actions, [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] confines them at run time, [[agentic-ai-security-cmm-d5-egress-network|D5]] enforces live egress and Agent Card verification, and [[agentic-ai-security-cmm-d7-observability|D7]] monitors them. D8 verifies the proposed release and acquired parts before they enter those paths. Missing prerequisites are named against the criterion and target they block.

## Deployment-shape differences

| Shape | Material D8 difference |
|---|---|
| Hosted assistant | Supplier development and model evidence must be assessed; customer enablement and configuration promotion remain releases for design, test, and decision checks. |
| Organization-built RAG agent | The corpus acquisition record, model card, tool provenance, integration tests, and release AI-BOM cover the assembled system. |
| Coding agent fleet | Harness settings, locally installed abilities, package installs, repository writes, and generated code must reach their respective gates on every device or runner. |
| Model producer or external component publisher | Lineage and weight checks apply to produced models; VEX and a feed apply only to components published for outside consumers. |

A supplier's claim does not prove a customer integration. The release test must cross the customer's actual trust boundaries even when the model or platform internals are inaccessible. Conversely, the customer does not need to claim access to a supplier's weights or source code to use supplier assurance as evidence. Record the exact evidence class and its limitation in the criterion result.

## Implementation and effort drivers

The largest implementation work is the component inventory and a release path that can name the version it tested and deployed. Package locks, registry checks, model-file scans, signatures, and provenance each close a different entry path. A release decision links them to the security tests and open findings. A vendor-managed suite shifts effort toward supplier evidence, customer configuration review, and tests of visible integration and enablement. A coding fleet shifts it toward managed settings and local installation control. Produced models add lineage, protected weight storage, and supplier obligations to their consumers.

Operating cost comes from advisory triage, repeated scans, supplier reassessment, runtime-to-release reconciliation, and exceptions that need an owner and end condition. Risk-based targets can stop short of L5 for a low-impact consumer deployment; L5 remains achievable where its applicable controls have real implementations and evidence. D8-VEX-FEED is producer-specific, so a model consumer with no externally published component does not need to invent a feed. External working-group participation, universal supplier-BOM federation, and independent reproducible builds are not scored conditions.

## Sources and material limits

[NIST SSDF](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf) supplies software design, review, test, and release practices; its [AI profile](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218A.pdf) addresses AI-specific assets and provenance. The [OWASP AI Exchange supply-chain](https://owaspai.org/go/supplychainmanage/), [secure development](https://owaspai.org/docs/1_general_controls/#sec-dev-program), and [agentic testing](https://owaspai.org/docs/5_testing/#agentic-ai-security-testing) sections inform the component and release checks. [SLSA build requirements](https://slsa.dev/spec/v1.2/build-requirements) support the provenance levels. These sources do not require the AAI-S CMM's exact level assignments. An AI-BOM, signature, scan, or model card is evidence about one property, not a substitute for the assembled deployment's security test and release decision.

The [A2A specification](https://github.com/a2aproject/A2A/blob/main/docs/specification.md#84-agent-card-signing) defines optional Agent Card signatures. It does not define general message signatures; D8-A2A-SIGN-TEST grades a release test of card verification, while D5 grades runtime enforcement.
