# Agentic AI Security CMM — D4 Runtime & Guardrails (Deep Dive)

Companion deep-dive to [[agentic-ai-security-cmm-2026|the CMM]]'s D4 domain, written under the [[agentic-ai-security-cmm-recalibration-method-2026|recalibration method]]. D4 is the [[oversight-layer|Policy Enforcement Point]] at runtime: it enforces what [[agentic-ai-security-cmm-d3-control-least-agency|D3]] decides. The runtime threats it answers map to [[owasp-agentic-ai-threats-mitigations|OWASP Agentic AI Threats and Mitigations]]: Tool Misuse (T2), Intent Breaking and Goal Manipulation (T6), Unexpected RCE and Code Attacks (T11), and Rogue Agents in Multi-Agent Systems (T13), whose playbooks call for execution sandboxing with per-call reset and in-path reasoning-manipulation controls. The recalibration regrades this domain against what ships. The L2/L3 input-and-output controls are cheap and generally available on Azure and AWS, although the AWS prompt-attack filter does not evaluate tool results.[^bedrock] Of the platform-native L4 controls, chain-of-thought auditing ships as an experimental open-source component, and groundedness checking is generally available on AWS and in preview on Azure.

**The cost model rests on one customer's stress test.** The levels and the cost model synthesize the recalibration method against the [[agentic-cmm-regulated-fi-stress-test|regulated-FI stress test]] plus vendor documentation, and the L3 to L5 criteria also cite the [[owasp-ai-exchange|OWASP AI Exchange]] entries footnoted at each. The status column of the control landscape is a May 2026 snapshot; rows re-read since carry their own retrieval dates in the notes.

## Threat coverage

D4 is the primary domain for **ASI01 (Agent Goal Hijack)** and **ASI05 (Unexpected Code Execution)**, and the runtime home of **Class 2 (APT — cross-version eval continuity)**, **Class 3 (collusion — supervisor agents)**, and **Class 4 (model-version regression — continuous red-teaming)**. Its effective score is capped by D3, since a guardrail cannot enforce a decision the policy decision point never makes. See the [[threat-taxonomy-reconciliation|Threat Taxonomy Reconciliation]] matrix and the [[agentic-ai-threat-classes-2026|threat classes]].

The [[agent-escape|agent escape]] threat entry is graded primarily in [[agentic-ai-security-cmm-d3-control-least-agency|D3]], which holds the capability-based access control that decides a call. D4 holds the boundary that bounds the reach of a decision that was wrong, and the [[owasp-ai-exchange|OWASP AI Exchange]] keeps the two layers distinct: infrastructure-layer enforcement can block escape even where jailbreak has succeeded at the reasoning layer.[^aix-escape]

The Exchange cuts the same pair on a different axis. `LEAST MODEL PRIVILEGE` is preventative and `OVERSIGHT` is detective — reactive or gate-based — and the Exchange states that both may apply to the same action tier.[^aix-oversight] A domain boundary drawn on decide-versus-enforce and a control boundary drawn on prevent-versus-detect cross rather than coincide, so a control anchored at D3 can be the detective one and a control anchored here can be the preventative one. `OVERSIGHT` itself is categorised as a runtime control. The Exchange divides it into automated and human oversight, and the automated side carries two mechanisms that sit on different planes. The first recognizes unwanted output and suspicious action sequences in model output, before or after execution. This domain grades the screening of output and the check of each proposed call before it runs, and [[agentic-ai-security-cmm-d7-observability|D7]] grades detection after execution. The second withholds an action until a policy gate returns, and [[agentic-ai-security-cmm-d3-control-least-agency|D3]] grades that. [[agentic-ai-security-cmm-crosswalk|The CMM crosswalk]] sets out the control's split across domains, and [[oversight-layer|the oversight layer]] states the same automated side as detection at the Policy Information Point (PIP) and enforcement at the PEP.[^aix-oversight]

The input/output safety layer (L2/L3) is GA on the Microsoft and AWS stacks and sits largely inside Azure entitlements. On AWS, the prompt-attack filter evaluates user input marked with input tags and does not evaluate tool results,[^bedrock] so its documented scope stops short of the tool-output route that the L3 indirect-injection test uses. Google announces general availability for named Model Armor features and integrations and states no launch stage for the core prompt-and-response screening service,[^ma] and the filter set a template runs is region-gated, so a template in a limited-support region with data-residency compliance enabled loses malicious URL detection, multi-language detection, CSAM support, image support and antivirus scanning.[^maregion] Of the agentic-reasoning layer (L4), one capability has a generally available platform control, on one stack: AWS's Bedrock contextual grounding check.[^awsgrounding] Chain-of-thought auditing ships as an experimental open-source component, Microsoft's Task Adherence check of planned tool calls against user intent and its groundedness detection are preview, and Google states no launch stage for the check grounding API,[^grounding] so an L4 program assembles the layer rather than buying it.

The [[taiwan-ai-agent-government-intrusion|Taiwan AI-agent government intrusion]] is an operational example of the failure class the jailbreak-classifier row grades against. A framing-based jailbreak ("authorized penetration testing") defeated the underlying models' refusals across a four-day, 12-wave campaign.[^taiwan] Holding a refusal against a social-engineering frame that persists for days is the multi-turn framing class a current bypass library holds, which D4-INJECT-BYPASS measures at L5. A GA classifier in the path evidences D4-INJECT-DIRECT and supplies no measurement of that class.

Cyera's Protect phase is a further vendor example of the tool-call interception row above: Cyera states it blocks a risky tool call during execution ([[cyera-agent-guardian-release|Cyera Agent Guardian Release]]). Cyera names the block and gives no efficacy figure, no bypass rate, and no decision mechanism behind that block, so that row's graded status is unchanged.

[[falcon-guardian|CrowdStrike Falcon Guardian]] is a second vendor example on that row and the first placed at the endpoint. CrowdStrike states that Falcon Guardian defines which AI agent types may run on a managed endpoint and blocks the rest, and that it correlates a user prompt to the agent's skill use, tool calls, MCP server invocations and downstream system actions. Analyst coverage of the announcement reports CrowdStrike as claiming 99% detection efficacy against prompt attacks at under 100 ms response latency, across more than 200 known attack techniques.[^nand-fg] The figure measures the product's prompt-layer protection, which is the capability the input-classifier row grades, and it is a single aggregate with no published methodology, technique list or per-language breakdown. D4-INJECT-LANG, D4-INJECT-BYPASS and D4-INJECT-REFRESH require a per-language miss rate, a rate per bypass class against a current bypass library, and refresh receipts, so neither row's graded status changes. CrowdStrike gives no general-availability date, so rule 2 is unmet regardless.

Twenty-one products in the independent runtime-protection category were canvassed in September 2026, and the category supplies no row of this table at the L4 tier. Graded against the five L4 capabilities, chain-of-thought auditing drew no documented implementation, groundedness drew one product naming the concept with no method behind it, and generated-code safety drew one adjacent mechanism: Operant AI's CodeInjectionGuard, launched 2026-04-21, scans commands and packages at run time, a different subject from the static analysis of generated code that the capability names. Trusted/untrusted context boundaries drew one documented mechanism whose product is in early access. Semantic tool-call validation drew eleven products, each a behavioural approximation, a schema- or classifier-level inspection, a limited preview or an undocumented claim, and none implements the capability as written. Seven vendors market agentic runtime security over documentation that describes input and output filtering. No capability the canvass found clears rule 2's two-quarter window: the generally available implementations reached GA inside it, and the rest stands at preview, early access, or undocumented status. The assembled route this domain already describes therefore remains the route, and no row's graded status changes. [[agent-runtime-protection-canvass-2026-09|The canvass]] carries the per-vendor grades.

The [[microsoft-zt4ai|Microsoft ZT4AI]] Apps & Workloads pillar (assume breach) supplies the Microsoft-native runtime controls behind these levels — Prompt Shields, Groundedness Detection, and Task Adherence — crosswalked to D4 in [[standards-review-microsoft-zt4ai-2026-Q2|the 2026-Q2 ZT4AI review]], which records the same GA-versus-preview split.

## Capability-decoupled levels

Stated as capabilities per [[agentic-ai-security-cmm-recalibration-method-2026|rule 1]]; a control counts when it operates in production per rule 2. A control implemented through a product in the organization's approved-vendor pipeline with a documented production date satisfies its criterion on that basis alone, and the production date is the date the control entered the organization's production. A planned date satisfies none, and neither does a product the organization does not yet run in production, whatever the vendor has announced.

- **L1 — Initial.** No runtime guardrails, or only system-prompt instructions. No enforcement boundary.
- **L2 — Developing.** A safety filter screens each prompt, and a content-safety classifier screens every response the model returns, the content it passes to tools included. Both are reachable on generally available filters.
- **L3 — Defined.** Injection classifiers run in path on canonicalized text, over the prompt and every route of untrusted content, and the output classifier's data-class scope is recorded. Code an agent executes runs in a per-task sandbox that covers the whole run, starts before the workspace is read, confines the code, carries no credential and has platform limits.
- **L4 — Managed.** Runtime checks reach the agent's intent and the effect of its calls: an alignment monitor before each tool call, a scan of generated code, a groundedness check on answers, and a rule that narrows the calls a session can make once untrusted content enters it. Each high-impact call passes a dry-run, a cross-family judge and a per-call limit on its parsed impact.
- **L5 — Optimizing.** Every L4 control runs platform-level for every agent. The injection classifiers' miss rates are measured per language and per bypass class and refreshed on record, credential-leak scanning is measured against encoded forms, each guardrail carries an enforced latency and cost budget, and the services agents share are recorded with a decision on each.
- **L5+ — Leading Edge.** A trusted execution environment attests that the guardrails ran, and each bypass class a measurement finds reaches the classifier's supplier and closes in a recorded remediation.

The control landscape states each capability's launch stage, and rule 2 counts a control from the documented date it entered the organization's production. A preview control in production therefore counts toward its criterion, and a buyer that cannot deploy preview features assembles each level from what it can deploy.

Sandbox strength is graded from L3 rather than assumed, and the control's own limits bound what the grade asserts. The [[owasp-ai-exchange|OWASP AI Exchange]] states that container or hypervisor escape undermines containment and that OS-specific behaviour can weaken the same configuration on a different host.[^aix-sandbox] An L3 sandbox therefore asserts containment on the integrity of a boundary the buyer does not test, which is the same evidence problem that the coding-shape paragraphs under [Right-sizing by deployment shape](#right-sizing-by-deployment-shape) raise for scope and start order. The Exchange states that shared inference, credential and policy services create implicit cross-agent channels,[^aix-sandbox] which D4-SHARED grades at L5.

Two adjacent controls fall outside this domain. Exfiltration through legitimately permitted APIs is out of segmentation's reach and is graded in [[agentic-ai-security-cmm-d5-egress-network|D5]], which also takes the API-volume and tool-invocation limits of the Exchange's per-agent quota control, leaving D4 the CPU, memory and wall-clock limits D4-SANDBOX-LIMITS grades. [[agent-sandbox-isolation-landscape|The sandbox and isolation landscape]] compares what each shipping sandbox partitions.

Tool-output sanitization before content enters the agent's context — stripping role-change patterns, validating against schema, labelling trust by source, and scanning for exfiltration-oriented encoding — is specified by the Exchange alongside these controls.[^aix-piioh] That control sits on the tool-call path, which [[agentic-ai-security-cmm-d5-egress-network|D5]] owns. D5-GATEWAY-SCREEN grades at L3 an inline screen, on the gateway every call passes, for prompt injection in the responses and tool results an agent receives, so a gateway that strips role-change patterns from a tool result evidences its inbound half. D5-CONTRACT validates the responses of a supplied model or AI service against a pinned schema, and no D5 criterion validates the schema of other tool results, labels trust by source or scans for exfiltration-oriented encoding. Those three stay ungraded, with an open domain assignment, and no D4 level grades them.

Recitation detection is a further output-side mechanism the Exchange specifies and these level definitions do not grade. It matches output against an indexed set of the training data to catch the model reproducing training content verbatim, and the Exchange states its reach as limited to what is indexed, where it may miss shorter and paraphrased disclosures.[^aix-soh] The index covers pretraining and fine-tuning data and is a development-time artifact of the party that trained or fine-tuned the model: a deployment consuming a third-party model cannot index the pretraining set, and one that fine-tunes can index only its own fine-tuning set, so a level graded against the full check would grade the model provider rather than the buyer. The control stays ungraded, owned upstream of the assessed organization, beside the tool-output sanitization case above.

Ensemble deviation detection is a third such mechanism, and the Exchange files it as a runtime implementation of a development-time decision. `MODEL ENSEMBLE` deploys a model as several models trained on a randomly split training set, so that an output deviating from its peers can be ignored as possible evidence of a poisoned training set. The Exchange states that its effectiveness falls as the poisoned share of the dataset rises.[^aix-modelensemble] The detection runs at inference and the decision that makes it possible — how the training set is split and how many models are trained — is taken by whoever trains the model, so a deployment consuming a third-party model has no instance of it. It stays ungraded with recitation detection, owned upstream. D4-VALIDATE-JUDGE draws on the same diversity argument for a different purpose: a judge from a different model family is independent of the model it checks, and an ensemble's members are independent of one another; both hold only as far as the shared training corpus lets them.

## Assessor detail per level

L1 describes where a deployment starts and carries no criterion, so a deployment that does not meet every L2 criterion scores L1. It scores 0 under the measurement protocol's rubric only where no evidence of the L1 baseline exists, meaning the assessment holds no record and no interview answer about the domain for that deployment. The levels from L2 to L5+ each carry a criteria list below, each list stating what its own level adds.

Grading is cumulative: Level N requires every Level N–1 control plus the new criteria at Level N ([[agentic-ai-security-cmm-2026|the CMM]]), so a level is met only where every level below it is met.

Each criterion takes one of four verdicts. **Met** and **not met** are read from the evidence the criterion names, whoever operates the control. The assessment records the evidence's assurance class beside the verdict and names the artifact behind it, its issuer and its date, per [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]]:

- **Tested**: the customer or the assessor exercised the control and recorded what it did.
- **Inspected**: vendor tooling the customer can reach, or a record the organization keeps, such as an inventory or a plan, shows the control's state in the deployment.
- **Attested**: the vendor states the control in a document the customer holds, and the document's own scope names the control.

**Not applicable** is recorded where the deployment holds no instance of what the criterion governs, and the reduced scope is recorded as an intentional trade-off in the [[agentic-ai-security-cmm-dependency-rules|effective-score]] strategic-rationale field. **Unanswerable** is recorded where the instance exists, the customer can run no test and keeps no record of the control's state, and the vendor supplies neither inspectable output nor an attestation that names the control. An unanswerable criterion never counts as met: its level stays open, and every level above it stays open under cumulative grading. The assessment names what would close it. A criterion that can be not applicable states that condition alongside the criterion. Each level's list below holds criteria only, and a paragraph after a list states no criterion: it carries maturity, market or provenance commentary, or the boundary between this domain and another.

**D4 grades one deployment at a time.** A deployment is the unit the assessment scope names: one agent application, or one agent platform a vendor provides together with the agents the organization runs on it. Evidence of a control counts only for the deployments the control covers. The D3→D4 cap reads the D3 score of the same deployment, so an assessment grades D4 on the scope it graded [[agentic-ai-security-cmm-d3-control-least-agency|D3]] on, and D3 takes [[agentic-ai-security-cmm-d2-identity|D2]]'s unit. Four terms fix what the criteria range over:

- **An agent** is one deployed configuration: its code, instructions, tools and grants as the deployment runs them. Replicas of one configuration are one agent, and two configurations are two agents even where they share code.
- **The agents in scope** are those the deployment runs in production, per rule 2. An agent outside production enters scope once it holds a production credential or reaches production data. Evidence from a pilot outside scope counts for no criterion, and the gap report can cite it as the planned route to a level. A deployment with no agent in scope, such as a pilot that holds no production credential and reaches no production data, takes no D4 result, and the assessment records it as outside scope.
- **An agent's model calls** are every inference call it makes to a model, itself or through an orchestration step, under every autonomy mode the deployment permits. A model that a tool or a service calls for the agent, such as a document-extraction service a tool sends a file to, is part of that tool, and what it returns reaches the agent as a tool result. A model that the agent's own flow calls to write content the agent sends on, such as a maker platform's prompt action, is the exception: that call is one of the agent's model calls, and its output is the agent's response.
- **An agent's executions** are the commands it runs and the code it writes and runs, under every autonomy mode the deployment permits. An agent that executes neither holds no instance of the sandbox criteria, which are then not applicable to it.

A criterion that names every agent, prompt, response, route or execution is met only where it holds for each one. No percentage threshold applies, because the deployment's configuration enumerates its agents, their routes and their tools, and one agent outside the rule is the failure D4 grades. An agent whose configuration the organization cannot produce, such as a workstation that has stopped reporting to device management, does not meet a criterion that ranges over it. The deployment's verdict is the weakest among its agents: not met where any agent fails the criterion, then unanswerable where any agent's verdict is unanswerable, and not applicable only where the criterion is not applicable to every agent. The assessment names the scope it graded, and where a narrower scope would change an agent's result, such as one repository of a shared CI workflow, it reports that agent beside the deployment's result.

**Grading words.** The criteria use these terms in one sense each:

- **Prompt**: a request the person an agent acts for sends it, such as a chat message or a task description, as the model receives it. A run that no person starts, such as one an inbound message or a schedule triggers, receives no prompt.
- **Untrusted content**: content an agent takes in from a party outside the organization, or from a source the organization does not control, such as a claimant's document, an inbound mail, a web page or a third-party tool's output, as [[agentic-ai-security-cmm-d5-egress-network|D5]] defines it. A **route** is one path by which content other than the prompt reaches the model's context, such as one retrieval index, one tool, one connector or one inbound channel, and a route carries untrusted content where any content it can deliver is untrusted.
- **Response**: what a model call returns, both the text a person reads and the content the model passes to a tool, such as a drafted message, a post or a command. A configuration that sets a classifier on a model's output, or a vendor document stating that the vendor screens an assistant's responses, shows the text a person reads in the classifier's scope, and shows the content the model passes to a tool only where the configuration or the document names that content, such as a query the model sends to a search service or code it passes to an interpreter.
- **Answer**: text an agent gives a person, a review or a comment it posts included.
- **Prompt attack**: an instruction placed in content to override the agent's instructions or its safety behaviour. A **direct** attack arrives in a prompt, such as a jailbreak, and an **indirect** attack arrives in untrusted content.
- **Safety filter**: a classifier that screens content for harmful-content categories, such as hate, violence, sexual content and self-harm, or for prompt attacks, and blocks, redacts or flags what it matches. A **content-safety classifier** screens for harmful-content categories, and an **injection classifier** screens for prompt attacks.
- **In path**: a classifier runs in path where the content cannot reach its destination until the classifier returns, and a match blocks or holds it. A classifier that reads a copy, or runs after delivery, runs out of band.
- **Canonicalize**: apply the four steps D4-INJECT-CANON names, so that text differing only in encoding, invisible characters, case or confusable characters reaches the classifier in one form.
- **Exposure-restricted data**: the class the Exchange's `SENSITIVE OUTPUT HANDLING` covers, such as personal data, confidential identifiers, passwords and tokens,[^aix-soh] together with the classes the organization's classification scheme restricts and system prompts, which `OVERSIGHT` counts as a special category of sensitive data.[^aix-oversight]
- **Sandbox**: the isolation boundary that the code or commands an agent executes run inside, such as a container, a microVM or an operating-system sandbox around a code-execution or shell tool, whoever operates it. A boundary that hosts only the agent's own process, and runs no code the agent writes and no command it chooses, is the agent's runtime. [[agentic-ai-security-cmm-d7-observability|D7]] uses the same definition. Where the code runs inside more than one such boundary, such as a command sandbox inside a per-job virtual machine, a criterion is met where any one of them meets it.
- **Workspace**: the files and version-control state an agent's run works on, such as a checked-out repository, that a party other than the organization's administrators can change, such as through a pull request.
- **The agent's configuration**: the settings, permission rules, hooks and MCP server definitions the harness reads to decide what the agent may do or to start processes for it. An instruction file that an agent edits and a later run loads is agent memory in D7's sense, which [[agentic-ai-security-cmm-d6-data-rag|D6]] and D7 grade.
- **Task** and **session**: [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s sense, one unit of work an agent was started for and one run of an agent from its start to its end.
- **High-impact call**: a call that can carry out a destructive action, as D3 defines one, the organization's own additional classes included.
- **Guardrail**: each safety filter, injection classifier, alignment monitor, judge, code scan and groundedness check the deployment runs on its agents' model calls.
- **Current bypass library**: a set of prompt attacks grouped by bypass class, such as encodings, invisible characters, confusable characters, other languages and multi-turn framing, whose latest revision the organization records and that was revised within the refresh period the organization sets for it.
- **Tested**: a test counts where it ran in production, or in another environment on the model, guardrail configuration, sandbox configuration and code that production runs, and its record names the environment and the revisions. A demonstration the organization runs and the assessor observes is a test.

**Names and precedence.** Each criterion carries a stable name, D4 and a mnemonic for what the criterion requires, and the name leads the criterion in bold. The level is an attribute recorded beside the name, so a criterion that changes level keeps its name. Members of a family share its first mnemonic, as D4-SANDBOX and D4-SANDBOX-CLEAN do, and each member is a separate criterion because a deployment can hold one without the other and an assessor collects different evidence for each. [[agentic-ai-security-cmm-2026|The CMM]]'s D4 levels restate each criterion under the same name, and [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]]'s D4 questions and artifacts cite each one by that name, in plain text. A level's statement above summarizes its list, and where the two read differently the list governs.

**Vendor-run guardrails.** A vendor runs a guardrail where the vendor's service applies the classifier or hosts the sandbox and the customer holds no configuration of it, as with an in-suite assistant's classifiers, a model provider's own filtering or a maker platform's code interpreter. The criteria stand for those guardrails and are graded on the evidence the vendor produces, because the prompts, responses and code they govern exist whoever screens them: vendor operation is no ground for a not-applicable verdict. A vendor document whose own scope names the product and the control evidences it as attested, and a record of the control's result that the customer can search, such as an audit field recording a detection, evidences it as inspected. A statement that the vendor may screen its service, naming no category, threshold or action, attests no control. A statement that names the control but says the vendor may apply it, or that limits it to scenarios the statement does not name, attests the control only for the scenarios the statement names. Where the vendor documents neither, the criterion is read from a test the customer runs, such as a crafted document placed in the tenant or code run in the vendor's interpreter to probe its boundary, and it is unanswerable for the agent where no such test can be run. An agent the organization builds on a vendor's platform, such as a Copilot Studio agent, runs the guardrails its maker's settings select, such as its moderation level, so those settings are the customer's own configuration, and the platform's operation under them is graded on the evidence the vendor produces.

**Not applicable across a level.** A level at which every criterion is not applicable for the deployment is not reached, and neither is any level above it, because a not-applicable verdict records that the deployment holds nothing for a criterion to govern and records no control. D4-OUTPUT reads every response an agent's model returns, so every deployment in scope holds an instance at L2 and takes a D4 result.

**Conditions the rubric adds.** [[agentic-ai-security-cmm-measurement-protocol|The measurement protocol]]'s rubric adds two conditions to score 3 that no domain's criteria state: operational ID tagging of the domain's findings, and the live observation it requires, a trace, a policy decision and, where D3-APPROVE-GATE applies, a gate fire. A deployment that meets every D4 L3 criterion without them scores 2 under the rubric, and the assessment records which condition held it there.

### L2 detail

- **D4-INPUT.** A safety filter screens each prompt an agent receives before the model reads it, and it blocks, redacts or flags what its configuration matches. The filter can be the model provider's default or one the organization configures, and it screens the prompt on every path to each of the agent's model calls, so a code path that sends a prompt to the model without it fails the criterion. Not applicable where no agent receives a prompt. *Evidence:* the filter's configuration at the running version, with the setting or code that applies it to each of the agent's model calls, or for a filter the vendor runs, the vendor document naming it or a record of its result.
- **D4-OUTPUT.** A content-safety classifier screens every response each agent's model returns before the response reaches its destination, both the replies a person reads and the content the model passes to a tool, such as a message it drafts, a post or a comment, and it blocks or redacts what its configuration matches. A classifier that screens the replies and leaves tool-call content unscreened fails the criterion. *Evidence:* the classifier's configuration, or the vendor document naming it, showing replies and tool-call content in its scope, or a test in which it blocked each.

The two L2 criteria screen the prompt and every response. Untrusted content that enters through a retrieval or a tool result is D4-INJECT-INDIRECT's at L3, so L2 grades no screen of it. The Microsoft and AWS filters ship generally available, and on AWS the prompt-attack filter evaluates user input marked with input tags and does not evaluate tool results.[^bedrock]

### L3 detail

- **D4-INJECT-DIRECT.** An injection classifier runs in path on each prompt every agent receives and detects direct prompt attacks, and a detected attack is blocked or held before the model acts on it. Not applicable where no agent receives a prompt. *Evidence:* the classifier's configuration and its place on the request path, with a direct attack it blocked, or for a classifier the vendor runs, the vendor document naming it for prompts or a record of a detection.
- **D4-INJECT-INDIRECT.** Each route that carries untrusted content to an agent's model, such as a retrieval, a tool result, a fetched page or an inbound message that starts a run, passes an injection classifier in path that detects indirect prompt attacks before the model reads the content, and a detected attack is blocked or held. The criterion is read route by route, from a test that presented an attack through the route itself[^aix-testing] or from a detection the classifier recorded on content that arrived through it, because a vendor's statement that a classifier has an indirect mode shows that the capability exists, and only a test or a recorded detection shows that the deployment's route reaches it. A route that no classifier screens, or one with neither a test nor a recorded detection, fails the criterion. A message from another agent is inter-agent traffic, which [[agentic-ai-security-cmm-d5-egress-network|D5]]'s D5-A2A-SCREEN grades. Not applicable where no route carries untrusted content to any agent's model. *Evidence:* the list of routes that carry untrusted content to each agent's model, and for each route a test record of an attack presented through it or a detection the classifier recorded on content from it.
- **D4-INJECT-CANON.** Before an injection classifier reads a prompt or the content of a route, the content is canonicalized in four steps: Unicode normalization such as NFKC, zero-width and other invisible characters removed, locale-independent case folding, and confusable characters mapped to their UTS #39 skeleton with mixed-script runs flagged.[^aix-piioh] A step left out, or a prompt or route whose classifier reads raw content, fails the criterion, and so does a prompt or route on which D4-INJECT-DIRECT or D4-INJECT-INDIRECT requires a classifier and none runs. For a classifier the vendor runs, the vendor's statement of the canonicalization it applies evidences the criterion, and where the vendor states none, a test does: an attack the classifier blocks, presented again in each variant form the four steps address, is blocked each time. Not applicable where D4-INJECT-DIRECT and D4-INJECT-INDIRECT are both not applicable. *Evidence:* the canonicalization code or configuration at the running version, set against each prompt path and route the classifier screens, or for a vendor classifier its stated canonicalization or the variant test record.
- **D4-OUTPUT-SCOPE.** A dated record the organization keeps names the classes the output classifier detects, its content-safety categories apart from its exposure-restricted data classes, and states, for each exposure-restricted data class an agent's model can reach, system prompts included, and for other technical detail about the system, whether the classifier detects it. The record matches the classifier's configuration or, for a classifier the vendor runs, the vendor's statement of its categories. A record that omits an exposure-restricted data class the model can reach fails the criterion, because content safety and exposure-restricted data are separate detections.[^aix-soh] *Evidence:* the dated scope record, set against the classifier's configuration or the vendor's statement.
- **D4-SANDBOX.** Every command and every piece of code an agent executes runs inside a sandbox, and so does everything else the agent's run does on the host where it runs: its tools that read or write files or open connections there, and the processes its harness starts for the run, such as MCP servers and hooks. The coverage holds under every autonomy mode the deployment permits, so a mode that runs commands outside the sandbox, such as a sandbox bypass, fails the criterion for every agent that can run in it, and a command the sandbox blocks does not then run outside it, such as through a retry the permission check allows. Not applicable where no agent executes code or commands. *Evidence:* the sandbox's scope as its configuration or the vendor's documentation states it, set against each tool of the agent and each process its run starts, with the autonomy modes the deployment permits and the setting that governs a blocked command's retry.
- **D4-SANDBOX-FIRST.** Each agent's sandbox is in place before the agent's run reads configuration from its workspace that can start a process or set one's environment, such as a settings file, a hook, an MCP server definition or a version-control configuration, or the run reads no such configuration from the workspace. A sandbox built from workspace-supplied settings, or one that starts after a workspace-supplied hook or subprocess has run, fails the criterion. Where the harness's vendor documents no ordering, the criterion is read from a test the customer runs, in which a workspace-supplied hook or setting records where it ran, and it is unanswerable only where no such test can be run. Not applicable where D4-SANDBOX is not applicable, or where no agent's run reads configuration from a workspace. *Evidence:* the vendor's statement of the order in which the harness reads workspace configuration and starts the sandbox, or the test record.
- **D4-SANDBOX-CONFINE.** Each sandbox refuses the code inside it four kinds of access: starting a process outside the sandbox, reaching files on the host outside the workspace beyond the read-only system files the code needs to run, changing the agent's configuration, and interacting with the host, such as through its devices, its display and input, a container or virtualization control socket, or its other processes.[^aix-sandbox] A sandbox that refuses three of the four fails the criterion. Not applicable where no agent executes code or commands. *Evidence:* the sandbox's profile, with a staging demonstration of each refusal.
- **D4-SANDBOX-MAC.** The kernel or the hypervisor applies a mandatory access control profile to the processes in each sandbox, one they cannot change, such as a seccomp filter, an AppArmor or SELinux profile or macOS Seatbelt, and the processes hold no kernel capability or privilege-escalation path they do not need, such as raw sockets, setuid binaries or passwordless sudo.[^aix-sandbox] Not applicable where no agent executes code or commands. *Evidence:* the profile and the capability set the platform reports for the processes of a running sandbox.
- **D4-SANDBOX-CREDS.** No credential the agent's run uses is readable from inside a sandbox, whether a model-provider key, a token for a tool, an MCP server or a code host, or a cloud credential, short-lived tokens included. The credentials sit outside the sandbox, in a credential store or a proxy that attaches them to calls, and neither the sandbox's environment nor its filesystem carries one.[^aix-sandbox] Not applicable where no agent executes code or commands. *Evidence:* the environment and the mounts of a sandboxed process, showing no credential, with the store or the proxy that holds each.
- **D4-SANDBOX-CLEAN.** Each sandbox serves one task: the platform creates it for the task and, when the task completes or is stopped, destroys it with its transient state, its cached data and any credential material inside it, so no later task reads them.[^aix-sandbox] A sandbox that one task leaves for the next, or one a forced stop leaves standing, fails the criterion. Not applicable where no agent executes code or commands. *Evidence:* the platform's lifecycle configuration, with its documented or observed teardown on completion and on a forced stop.
- **D4-SANDBOX-LIMITS.** The platform that runs each sandbox sets and enforces its CPU, memory and wall-clock limits, and a limit the agent's own code keeps, such as a harness's turn count or a recursion limit, counts for none of them.[^aix-sandbox] Not applicable where no agent executes code or commands. *Evidence:* the limit configuration for each sandbox, with the component that enforces each limit.

The Microsoft classifier carries a GA grade for both kinds of attack, with Prompt Shields' indirect mode screening documents.[^ps] The AWS classifier carries a GA grade for user input marked with input tags and does not evaluate tool results,[^bedrock] so on AWS the tool-result route needs a detector the filter's documented scope does not supply. Google states no launch stage for Model Armor's core screening service.[^ma] The classifiers ship at differing launch stages, and canonicalization, the scope record and the sandbox are configuration, so an assessor grades this level off the deployment, and a product's status page decides none of it.

The Exchange states that the canonicalization steps are separate: normalization leaves case unchanged (`NFKC("İGNORE")` is unchanged) and leaves confusables in place (Cyrillic `а`, U+0430, survives NFKC), and a locale-sensitive lowercase on a Turkish-locale host maps ASCII `I` to dotless `ı` and breaks a blocklist match.[^aix-piioh] The Exchange also directs that input handling apply as early as possible, such as when data is retrieved from an API, which is why D4-INJECT-CANON reads every route the classifier screens. A classifier graded GA does not answer whether the text reaching it was canonicalized first, so the criterion is read off configuration.

D4-OUTPUT-SCOPE records the scope and grades no detection. The Exchange specifies the detection of exposure-restricted data as a final safeguard before output reaches a user or a downstream system, applicable where the model was trained on, fine-tuned with or given such data, the data may be reflected in output, output can reach an unauthorized actor, and misuse or manipulation of model behaviour is a concern.[^aix-soh] The detection is graded where the content leaves: [[agentic-ai-security-cmm-d5-egress-network|D5]]'s D5-GATEWAY-SCREEN screens the organization's restricted data classes in what an agent sends, at D5 L3, and D4-OUTPUT-LEAK measures credential scanning against encoded forms at L5. [[agentic-ai-security-cmm-d6-data-rag|D6]]'s D6-LABEL-GATE keeps items of the classes a policy names out of answers at D6 L4, a gate that reads each item's class and detects nothing in the answer.

The sandbox criteria draw on the Exchange's sandboxing control, which runs each live agent in a bounded environment.[^aix-sandbox] They read the boundary around the code an agent executes, because a boundary that runs no code the agent writes and no command it chooses holds only the agent's own process, whose tool calls [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s policy governs, and D4-SHARED at L5 reads what agents share across their boundaries. The Exchange directs that tool credentials for MCP servers and APIs be stored outside the sandbox in a controlled credential store,[^aix-sandbox] and D4-SANDBOX-CREDS extends the rule to every credential the run uses, model-provider keys and short-lived tokens included. Two of the control's execution-isolation items carry no D4 criterion: the separate namespaces a container or an operating-system sandbox forms its boundary from, which the grading word "sandbox" does not specify, and a read-only root with ephemeral writable layers, whose discard at termination D4-SANDBOX-CLEAN grades and whose read-only root no D4 criterion requires. Playbook 3 of OWASP Agentic AI Threats and Mitigations resets the sandbox after each tool execution, and a sandbox reset per call meets D4-SANDBOX-CLEAN, which asks for one per task. D4-SANDBOX and D4-SANDBOX-FIRST carry the two coverage questions the coding-shape paragraphs under [Right-sizing by deployment shape](#right-sizing-by-deployment-shape) describe: what the boundary contains, and when it begins.

[[agentic-ai-security-cmm-d3-control-least-agency|D3]] grades the interception of each tool call: D3-MEDIATE requires every call to reach a decision point, and D3-MEDIATE-SYNC holds the call there until a permit returns. The D4 criteria grade the classifiers and the sandbox, whichever component runs them, so a lifecycle hook that runs an injection classifier on each tool result evidences D4-INJECT-INDIRECT for that route, and a hook that runs a formatter evidences no D4 criterion. The tool-call interception row in the control landscape lists decision points of the kind D3-MEDIATE grades. D3-MEDIATE-OUTSIDE bars the agent's own tool calls from writing the scope its policy comes from, and D4-SANDBOX-CONFINE bars the code in the sandbox from changing the agent's configuration, so one write-deny over the harness's settings files can evidence both. [[agentic-ai-security-cmm-d2-identity|D2]]'s D2-NOCRED keeps stored credentials out of everything the agent's process can read and admits a short-lived token issued at run time, while D4-SANDBOX-CREDS keeps every credential the run uses, short-lived tokens included, out of the sandbox the agent's code runs in.

The injection criteria meet two other domains' screens. [[agentic-ai-security-cmm-d5-egress-network|D5]]'s D5-GATEWAY-SCREEN screens the responses and tool results an agent receives on the gateway every call passes, where D4-INJECT-INDIRECT screens each route on the model's request path, so a component that does both evidences both. [[agentic-ai-security-cmm-d6-data-rag|D6]]'s D6-SCAN-INJECT scans each item for instructions addressed to a model as it enters a corpus, at D6 L3, and D4-INJECT-INDIRECT screens retrieved content in path as it enters the context. [[agentic-ai-security-cmm-d7-observability|D7]]'s D7-FORWARD-ESCAPE reads the escape indicators of the sandbox D4 grades, on the same definition of a sandbox.

### L4 detail

- **D4-ALIGN.** An alignment monitor outside the agent checks each tool call the agent's model proposes against the task the agent was started for, before the call runs, reading the agent's stated reasoning or plan where the model exposes one, and a call it finds misaligned with the task is blocked or held for a person. A monitor that reads calls after they run, or reads a sample of them, runs out of band and fails the criterion. Not applicable where no agent holds a tool. *Evidence:* the monitor's configuration and its place before tool execution, with a call it held or blocked, on a production run or in a test.
- **D4-CODESCAN.** Static analysis scans the code each agent generates before that code runs outside a sandbox or is merged, and a finding at or above a severity the organization sets holds the code until a person clears it. A scan whose findings do not hold the code, or one that covers part of the code an agent generates, fails the criterion. Not applicable where no agent generates code. *Evidence:* the scanner's configuration with its blocking severity and the code it covers, and a finding that held agent-generated code.
- **D4-GROUND.** A groundedness check scores each answer an agent gives a person against the content retrieved or supplied for it, before the answer reaches the person, and an answer below the threshold the organization sets is blocked, corrected or shown to the person as unsupported. A check run on a sample of answers after delivery fails the criterion. Not applicable where no agent answers a person from retrieved or supplied content. *Evidence:* the check's configuration with its threshold, and the scores for a sample of answers.
- **D4-CONTEXT.** Once untrusted content has entered a session's context, a rule outside the model decides which tool calls the session can still make, and it blocks or holds each call that sends content outside the organization, and each further call its policy names, until the task ends or a person clears the session. A boundary held only by message roles, delimiters or an instruction to treat such content as data fails the criterion. Not applicable where no route carries untrusted content to any agent's model. *Evidence:* the rule with the calls it names, and a call it held after untrusted content entered a session.
- **D4-VALIDATE-DRYRUN.** Before a high-impact call runs, a dry-run of the tool computes the change the call would make, for each tool that can report a change without making it, such as through a plan or preview mode, and the proposed change is recorded with the call.[^aix-oversight] Not applicable where no tool an agent can call for a high-impact action can report its change without making it. *Evidence:* dry-run records for a sample of high-impact calls, each with the proposed change and the call it preceded.
- **D4-VALIDATE-JUDGE.** Before a high-impact call runs, a judge model from a different model family than the agent's compares the intent the user stated with the call's proposed parameters, and a mismatch blocks the call or holds it for a person.[^aix-oversight] A judge whose model family the deployment does not record fails the criterion, because independence is the property it grades. Not applicable where no agent can make a high-impact call. *Evidence:* judge findings for a sample of high-impact calls, each naming the judge's model family and the agent's.
- **D4-VALIDATE-IMPACT.** Before a high-impact call runs, deterministic rules outside the model evaluate its parsed impact, the change it would make as its dry-run or its parsed arguments state it, such as the records it would delete or the amount it would move, against a per-call limit, and a call past the limit is refused or held for a person.[^aix-oversight] Not applicable where no agent can make a high-impact call. *Evidence:* the rules with their per-call limits, and a call they refused or held.

AlignmentCheck, the chain-of-thought auditor, ships as an experimental open-source component.[^pg2] Microsoft's Task Adherence, which compares planned tool calls with user intent, and its Groundedness Detection are preview,[^ta][^ground] and groundedness is generally available only on AWS, whose contextual grounding check has been GA since 2024-07-10.[^awsgrounding] Rule 2 counts a preview or open-source control from the documented date it entered the organization's production, so a defensible L4 today is assembled from preview, open-source and generally available components. Rule 2 also keeps a level from naming a capability whose only implementations are young products, and each L4 criterion can be built from components generally available for longer: a model of another family as the judge, a policy engine for the impact limit and the session rule, a tool's own plan or dry-run mode, a static analyzer, and AWS's grounding check. The criteria therefore stay at L4, on the reading [[agentic-ai-security-cmm-d7-observability|D7]] gives D7-BASELINE.

The semantic-validation criteria have one named preview component and no complete implementation. Microsoft's Task Adherence, in preview, compares planned tool calls with the user's intent and returns a signal for blocking or human review;[^ta] Microsoft documents no model family for it, so it evidences D4-VALIDATE-JUDGE only where the deployment records one. Proposed state change has no named implementation, so a deployment assembles it and evidences D4-VALIDATE-DRYRUN and D4-VALIDATE-IMPACT from its own pipeline. Every L4 control is evidenced from the deployment, and a vendor's status page dates a product and evidences no deployment.

The Exchange's simulate-before-execute strategy also makes human approval mandatory for configured high-blast-radius operations even when the automated checks pass, and sets the impact limits across the session as well as per call.[^aix-oversight] [[agentic-ai-security-cmm-d3-control-least-agency|D3]] grades both. D3-TIER-DESTRUCT places each destructive action at confirm or block, D3-TIER-ENFORCE holds the decision point to the recorded tier and D3-APPROVE-GATE holds a confirm-tier action until a person approves it, so no clean result from the checks above lowers a tier or stands in for the approver. [[agentic-ai-security-cmm-d9-operations|D9]]'s D9-HIGHRISK-RECORD, at D9 L3, grades the record of each high-risk approval. D3-LEDGER limits what a session's executed writes add up to, and D4-VALIDATE-IMPACT limits the parsed impact of each call, so a per-session count of payments evidences D3-LEDGER and evaluates no parsed impact.

Read-only tool restriction after risky web access or after a judge failure, held until task end or human clearance, is an optional mechanism the Exchange names beside the validation controls, and the runtime counterpart to the dynamic narrowing on risk elevation that [[least-agency-principle|least agency]] carries as an implementation pattern.[^aix-oversight] D4-CONTEXT grades narrowing once untrusted content enters a session, with outbound sends as its floor. D3 grades two further forms: D3-TRIFECTA at L4 moves external-communication actions to confirm or block once a session holding private data has taken in untrusted content and can reach an external path, and D3-ADAPT at L5 withdraws grants on a D7 anomaly score. Narrowing write and sensitive-read tools stays at the policy's discretion, and narrowing after a judge failure has no criterion.

The Exchange's `INPUT SEGREGATION` marks untrusted content in the prompt and instructs the model to ignore instructions inside it, and it states that segregation reduces the likelihood that the model follows them.[^aix-inputseg] D4-CONTEXT grades the rule that holds where the marking fails. The rule needs to know which routes carry untrusted content, a trust label at the grain of a route and a session, and labelling each piece of content by source, which the Exchange lists under tool-output sanitization, stays ungraded.

D3-TASKSCOPE denies a call to a tool outside the task's scope, which a deterministic policy decides, and D4-ALIGN judges whether a call inside that scope serves the task. Agent Anomaly Detection on the Gemini Enterprise Agent Platform reads reasoning traces asynchronously,[^gaad] so it evidences no D4-ALIGN verdict, and D7 grades detection of that kind. Code that runs only inside a sandbox that meets the L3 sandbox criteria, and is never merged, is outside D4-CODESCAN's trigger. D4-GROUND grades the check between an answer and its sources. [[agentic-ai-security-cmm-d6-data-rag|D6]] grades no groundedness check, and its criteria grade the corpus the answer is checked against: its entitlements, its provenance and its integrity.

### L5 detail

- **D4-PLATFORM.** Each L4 control runs on every agent in scope that it applies to, through a component the agent's owner cannot switch off or configure away, on every channel that starts the agent's runs, an agent that serves only internal users included. An agent excluded from an L4 control that applies to it fails the criterion. *Evidence:* the coverage report of each L4 control across the agents in scope, with zero opt-outs, and the setting that stops an owner turning each off.
- **D4-INJECT-LANG.** The miss rate of each injection classifier is measured for each language the deployment's prompts and untrusted content arrive in, against prompt attacks in that language, and reported per language, because the Exchange states that detection accuracy differs across languages and directs that each detector's miss rate be evaluated per supported language.[^aix-piioh] An aggregate rate across languages, or a language the measurement leaves out, fails the criterion. Not applicable where D4-INJECT-DIRECT and D4-INJECT-INDIRECT are both not applicable. *Evidence:* the evaluation log by language, with each language's test set and date.
- **D4-INJECT-BYPASS.** The miss rate of each injection classifier is measured against a current bypass library and reported for each bypass class the library holds. A measurement against a suite with no bypass classes, or against a library past its refresh period, fails the criterion. Not applicable where D4-INJECT-DIRECT and D4-INJECT-INDIRECT are both not applicable. *Evidence:* the evaluation log by bypass class, with the library's revision and date.
- **D4-INJECT-REFRESH.** Each injection classifier is refreshed against new attack techniques on a cadence its operator states, and each refresh leaves a receipt naming the classifier's version and date, because the Exchange directs that detection techniques and patterns be kept updated from external sources.[^aix-piioh] For a classifier the vendor runs, the vendor's release record of each version evidences the criterion. Not applicable where D4-INJECT-DIRECT and D4-INJECT-INDIRECT are both not applicable. *Evidence:* the refresh receipts for each classifier over the period, with the stated cadence.
- **D4-OUTPUT-LEAK.** A scan on each agent's output path detects credentials in the agent's responses before they leave, and a test measures its detection against encoded forms, such as base64 and hexadecimal, beside literal ones, with the rate recorded per form. A scan measured against literal credentials alone fails the criterion. Not applicable where no credential can reach any agent's context. *Evidence:* the scanner's configuration on the output path, with the test results per encoded form.
- **D4-BUDGET.** Each guardrail carries a latency budget and a cost budget in the configuration of the component that runs it, and that component enforces both: it cuts off a guardrail call past its latency budget and stops a guardrail's spending past its cost budget, and it hands each call a breach leaves unscreened to the fail mode [[agentic-ai-security-cmm-d9-operations|D9]] L3 tests. A budget that is measured and never enforced fails the criterion. *Evidence:* the budget configuration for each guardrail, with a breach record showing the enforcement.
- **D4-SHARED.** A record the organization keeps enumerates each service that two or more agents in scope share, such as a model endpoint, a credential or credential store, or a policy decision point, and states for each whether it is partitioned per agent or accepted as a cross-agent channel, with the residual risk and the person who accepted it. A service is partitioned per agent where each agent reaches its own instance of it, or where the service keeps each agent's data and grants apart, such as a vault that holds each agent's credential under an access policy naming that agent. A shared service the record omits fails the criterion. Not applicable where the deployment runs a single agent. *Evidence:* the shared-service register, set against each agent's configuration, with the decision on each service.

The Exchange lists attackers' attempts to obfuscate output among the limitations of output detection and gives base64-encoding a token as the example,[^aix-soh] which D4-OUTPUT-LEAK measures. [[agentic-ai-security-cmm-d5-egress-network|D5]]'s D5-GATEWAY-SCREEN screens the organization's restricted data classes in what an agent sends, at D5 L3, and D4-OUTPUT-LEAK grades the measurement of credential detection against encoded forms wherever the scan runs, so a gateway screen measured against encoded forms evidences both.

[[agentic-ai-security-cmm-d9-operations|D9]]'s D9-GUARD-LATENCY, D9-GUARD-COST and D9-GUARD-FAILMODE, at D9 L3, track each guardrail's latency and cost for each agent and test its fail mode, and D4-BUDGET grades the per-guardrail budget and its enforcement, so one breach test that exercises the fail mode can evidence D9-GUARD-FAILMODE and D4-BUDGET.

The Exchange names shared inference, credential and policy services as implicit cross-agent channels and directs isolating shared inference where feasible;[^aix-sandbox] the enumeration and the written acceptance are this model's requirement. D4-SHARED ranges over agents, as the Exchange's bounded environment does, so replicas of one agent share nothing D4-SHARED records.

### L5+ detail

- **D4-ATTEST.** A trusted execution environment attests, for each of the agents' model calls, that each guardrail on the call ran inside the enclave, and the attestation verifies to the hardware vendor's root. *Evidence:* the attestation chain, with its verification record.
- **D4-INJECT-REMEDIATE.** Each bypass class that D4-INJECT-BYPASS finds an injection classifier missing is reported to the classifier's supplier, and the record shows the supplier's acknowledgement and the release that remediated the class, or, for a classifier the organization builds, its own remediation. Not applicable where D4-INJECT-BYPASS records no class the classifier misses. *Evidence:* the bypass-class results, each missed class with its report, acknowledgement and remediation date.

Rule 2 holds D4-ATTEST at L5+: attestation that guardrails executed in an enclave has reference pilots only. D4-INJECT-REMEDIATE closes the loop the L5 measurement opens and rests on each supplier's acknowledgement. [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s D3-QUARANTINE grades the privileged/quarantined split at D3 L5+, for each workload that holds all three trifecta legs, and D4 grades no second instance of it; D3's control landscape carries one vendor implementation, marked experimental by its vendor in September 2026.

| In-suite productivity assistant (Gemini for Workspace, Microsoft 365 Copilot) | L3 | The injection path is the product's own retrieval surface. D4-INJECT-INDIRECT is met per route on a recorded detection or a crafted-document test, and D4-INJECT-CANON is read from a variant test |
| Desktop-agent productivity assistant ([[claude-cowork\|Claude Cowork]] class) | L3 | Code runs in a hypervisor VM while the agent loop's file operations, local MCP servers and computer use run on the device, so a local session that runs code fails D4-SANDBOX |
| Copilot / assistant (RAG + light tools) | L3 → L4 | Add D4-GROUND for answers drawn from retrieval and the semantic-validation criteria on high-impact calls; D4-ALIGN earns its cost once tools can write |
| Generative coding harness (writes files, runs shell) | L3 → L4 | D4-INPUT and D4-OUTPUT still screen the harness's model calls. The sandbox family and D4-CODESCAN carry L3 and L4, and the range tracks what the program assembles. Coverage note below |
| MCP / skill provider (real tool reach) | L4 | D4-ALIGN, the semantic-validation criteria and the sandbox family become first-order |
| Multi-agent mesh | L4 → L5 | D4-PLATFORM, D4-SHARED and D4-OUTPUT-LEAK across every agent |

An agent the organization builds on a vendor's platform, such as a Copilot Studio agent, takes the row its own function fits, and the vendor-run guardrails rule reads the guardrails its maker's settings select as the customer's own configuration.

**The screening on both assistant shapes is evidenced from published vendor material, and on Microsoft 365 Copilot from the tenant's own audit record as well.** Microsoft states that it operates jailbreak classifiers on behalf of customers and that a triggered classifier exposes signals in the Defender portal and in Purview audit logging.[^mscopilotdefense] The Microsoft Purview interaction audit record carries that signal at the grain D4-INJECT-INDIRECT reads: `XPIADetected` is a boolean on each resource the assistant reached, denoting a cross-prompt injection attack detected in that resource, and a jailbreak flag sits on the prompt message.[^mscopilotaudit] A record with the flag set is an inspected detection on the route its resource came through, and placing a crafted document in the tenant and observing the flag raises the same signal to tested, so D4-INJECT-INDIRECT is met for each route that holds either. Records whose flags are all false show the field and no detection. D4-INJECT-DIRECT rests on the article and the jailbreak flag. D4-OUTPUT rests on the article's egress row for the replies a person reads.[^mscopilotdefense] The queries the assistant generates for web search and for the agents it calls, and any other content it passes to a tool, are read from a test the customer runs, because neither the article nor Microsoft's data, privacy and security page for the assistant names that content in the content-safety classifiers' scope.[^m365privacy] Google documents six layers over Gemini in Workspace — prompt-injection content classifiers, security thought reinforcement, markdown sanitization with URL redaction, a user confirmation framework, end-user mitigation notices and model resilience — and the pages read name no audit event recording a detection, so there D4-INJECT-DIRECT rests on attested evidence and D4-INJECT-INDIRECT on a crafted-document test the customer runs.[^ggeminiipi] Anthropic states that classifiers scan all untrusted content entering the context and flag potential injections before they affect behavior, and that in automatic-approval mode each action is reviewed for safety before it runs; the same document states that the chance of an attack remains non-zero.[^coworksafe] The desktop agent's D4-INJECT-INDIRECT likewise rests on a test the customer runs through each route. D4-INJECT-CANON is read from a variant test on both in-suite products: Microsoft documents sanitizing hidden Unicode instructions in pasted prompts and states none of the normalization, case-folding or confusable handling the criterion asks for, and the customer reads no configuration behind it.[^mscopilotdefense]

**A desktop agent's documented sandbox covers code execution, and D4-SANDBOX reads the rest of the run.** A local session runs shell commands and generated code in the VM, while its agent loop, with file reads and writes in connected folders, web fetches and local MCP servers, runs natively on the device behind an application-layer permission system.[^coworkarch] Anthropic states that computer use runs with no sandbox between Claude and the screen.[^coworksafe] D4-SANDBOX requires the file tools and the processes of a run that executes code to sit inside a sandbox, as the code does, so a local session that runs code does not meet it, whatever the VM contains. A session with code execution off holds no instance of the sandbox criteria, and its file operations fall under [[agentic-ai-security-cmm-d3-control-least-agency|D3]]'s tool policy.

The [[lethal-trifecta|lethal-trifecta]] test lowers the required level. An agent that reaches no private data, or that holds no exfiltration path, makes a poor high-impact injection target, so the alignment monitor and credential-leak scanning cover only risk the deployment shape has already removed. A lower D4 score is then recorded as an intentional trade-off.

The core page assigns the generative coding shape the same L3-to-L4 target range for this domain, and raises only [[agentic-ai-security-cmm-d8-supply-chain|D8]] to a flat L4, where the dependency channel stays external ([[cmm-known-limitations|CMM Known Limitations]] item 20).

**An assessment of the coding shape reads what "sandboxed" covers from D4-SANDBOX's coverage rule.** The load-bearing D4 control for an agentic coding harness is an OS boundary. A harness sandbox that covers shell subprocesses leaves in-process file tools, MCP servers and hooks on the host, the asymmetry through which the [[claude-code-github-action-credential-exposure|June 2026 CI credential exfiltration]] ran while the shell boundary held, and D4-SANDBOX is not met while any of them runs outside a sandbox. Whole-process wrappers such as [[anthropic-sandbox-runtime|`@anthropic-ai/sandbox-runtime`]] close it without requiring containers, at beta-research-preview grade, and a credential the harness then holds inside the wrapper falls to D4-SANDBOX-CREDS. A hosted CI runner's per-job virtual machine also holds the whole run, so on such a runner the harness in the June 2026 case meets D4-SANDBOX under the nested-boundary rule and fails D4-SANDBOX-CREDS, because its file-read tool reached the model-provider key inside that machine. Authoring-time instruments such as the [[security-guidance-plugin|Security Guidance plugin]] warn without blocking and therefore carry no D4 level on their own. [[securing-agentic-coding|Securing Agentic Coding]] holds the full catalog with availability grades.

Scope is one of two coverage questions, and D4-SANDBOX-FIRST grades the second: when the boundary begins. A sandbox established after the harness has read workspace-supplied configuration is absent for that window, whatever it contains afterwards. The [[gemini-cli-workspace-trust-rce|Gemini CLI Workspace-Trust RCE]] is one case on the record, where headless Gemini CLI executed from an attacker-supplied `.gemini/` tree before its sandbox initialized, at CVSS 10.0, with the isolation control correctly implemented and never in the path. [[gitspawn-coding-agent-git-config-rce|GitSpawn Coding-Agent Git-Config RCE]] is another, across seven coding agents: the git subprocess each spawns to gather repository context ran a command named in the repository's own git configuration on the host, outside the sandbox and unseen by the permission model ([Manifold Security, 2026-09-01](https://www.manifold.security/blog/ai-coding-agents-git-hijack)). [[claude-code|Claude Code]] is one of the seven: in both of its findings the command ran before the workspace-trust prompt was accepted, and one was unpatched at publication. Claude Code's documentation states the ordering for repository content. A `claude -p` or Agent SDK run in a folder never trusted uses the repository's settings-file hooks, `env` block and `apiKeyHelper` and connects its `.mcp.json` servers without asking,[^cc-trust] and MCP servers and command hooks run unconstrained on the host, outside the per-command sandbox,[^cc-sbxenv] so an assessor reads that harness's D4-SANDBOX-FIRST verdict from its documentation, and [[claude-code-control-sheet|Claude Code Control Sheet]] names the flags that keep repository content out of such a run. For the other harnesses this wiki tracks, no vendor documentation it holds states the ordering, so an assessor reads D4-SANDBOX-FIRST from a test the customer runs, in which a workspace-supplied hook records where it ran, and records it as **unanswerable** only where no such test can be run. A documented sandbox scope does not answer the ordering question.

## Cost model

An E5 or Azure incumbent already holds Prompt Shields, Content Safety and Foundry sandboxing, and the licensing column below prices that buyer. A Google Cloud buyer meets the input and output classification rows on Model Armor and the groundedness row on the check grounding API, and Google states no launch stage for either, while GKE Agent Sandbox leads the sandbox row. Google publishes a rate for Model Armor alone: 3 billion tokens a month at no cost on a Security Command Center Premium or Enterprise subscription, whose minimum annual fee is \$15,000, then 2 million tokens a month standalone and \$0.10 per additional million,[^maprice] so the Google buyer reads this licensing column against a subscription or a standalone purchase where the E5 buyer reads it against an entitlement.

| Level | Licensing | Operational labor | Run-rate |
|---|---|---|---|
| L2 | ~0 for an E5/Azure incumbent (Prompt Shields, Content Safety are Azure entitlements) | enable defaults | per-call content-safety transaction cost (low) |
| L3 | ~0 incremental (indirect-PI mode and sandbox are platform features) | route inventory and indirect-injection tests; sandbox configuration and coverage | classifier calls scale with traffic; sandbox compute scales with concurrently sandboxed work |
| L4 | mostly ~0 on entitlements, but the load-bearing controls are preview/OSS | the real spend: integrating and tuning CoT-audit and groundedness, false-positive triage, context-boundary engineering | per-call cost roughly doubles (input + output + grounding + CoT passes); latency-budget engineering |
| L5 | some off-stack (bypass-class eval tooling; egress response-leak scanning overlaps D5) | continuous multi-language eval; classifier-refresh ops; guardrail budget enforcement | guardrail inference at every surface × every agent; agent log volume hits the SIEM bill here too |

Licensing is near-zero through L3 and largely zero through L4 for an E5 incumbent, because Prompt Shields, Content Safety and Foundry sandboxing need no new licence. Defender's runtime protection for agents is the exception: since 2026-07-01 Microsoft requires an Agent 365 licence for agent threat detection and real-time protection, and Agent 365 is an add-on to E5 that Microsoft 365 E7 includes.[^agent365] An E5 buyer who wants the native tool-call interception in the control landscape buys that licence. The rest of the spend is guardrail-tuning labor and per-call inference run-rate (each added guardrail pass is another model call), which is why D4 scores well at low cost for this buyer.

The Exchange states that sandbox overhead scales with concurrent agents, each of which it runs in its own sandbox.[^aix-sandbox] The L3 criteria place every command and piece of code an agent executes in a sandbox that serves one task, so the overhead follows the sandboxes open at once, and the run-rate tracks the rate of tasks that execute code. A mesh deployment that runs every agent confined for the length of a session pays the sandbox floor for the whole fleet. Cost the L3 line against the deployment's own confinement scope.

## Customer critiques folded in

The stress test rated D4 the persona's strongest domain (raw ~L2–L3, lifting to L3), because the defaults are on and entitled: Prompt Shields (direct + indirect) is GA, and it credited groundedness with the lift to L3. Two corrections apply. The level definitions above place groundedness at L4, so it lifts nothing at L3. **Groundedness Detection is also public preview and English-only**[^ground]. The language limit is moot for a US English member bot, but where a regulated buyer cannot deploy preview features, the L4 groundedness criterion rests on a preview control on Azure. Two further critiques addressed:

- *"L4 looks GA but isn't."* The control landscape states each L4 control's shipping status, and rule 2 counts a control from the date it entered the organization's production, so nothing in the model directs a regulated buyer to deploy a preview control to hit L4.
- *"Cost was invisible."* Licensing is near-zero for E5 apart from the Agent 365 licence that Defender's agent protection needs; the real cost is per-call inference run-rate and tuning labor.

## Open questions

- CoT / alignment auditing has not reached GA, and two September 2026 sources bear on the reliability of what it reads. OpenAI's GPT-6 Astra system card (2026-09-03) states that the model *"shows a substantial decrease in chain-of-thought monitorability compared to previous models"* ([OpenAI Deployment Safety Hub](https://deploymentsafety.openai.com/gpt-6-astra)), and a contemporaneous evasion paper reports 25-33% monitor evasion rates across monitorability benchmarks under deliberate plan injection ([arXiv:2609.15989](https://arxiv.org/abs/2609.15989), 2026-09-14). AlignmentCheck carries the "still experimental" grade its May 2025 paper gave it,[^pg2] and Task Adherence stays preview, so D4-ALIGN continues to grade the capability rather than a GA product. See [[chain-of-thought-monitorability|Chain-of-Thought Monitorability]].
- Microsoft's groundedness detection supports English content only. The API accepts other languages, with accuracy and quality optimized for English,[^ground] so a non-English member base runs it outside its supported scope, with no verified multilingual GA date.
- The check grounding API answers the Google groundedness row: it returns an overall support score of 0 to 1 with per-claim scores and citations, and Google documents it for filtering responses at inference time and states no launch stage for it.[^grounding] On AWS, the Bedrock contextual grounding check has been GA since 2024-07-10 and is not supported for conversational question answering or chatbots,[^awsgrounding] and Automated Reasoning checks, which validate a response against policy rules, are GA in six US and EU regions for English (US) only.[^ar] A buyer whose procurement requires a supported-product commitment cannot read the Google row as entitled, and whether these level definitions treat an unstated launch stage the way they treat preview is an open calibration question.
- Defender real-time protection for Agent 365 tooling servers reached GA on 2026-07-27, which is inside rule 2's two-quarter window, and agent threat detection stays in public preview. No D4 criterion names either product, and rule 2 counts each from the date it entered the organization's production.
- **One output-side minimization target falls outside every data class the levels name.** `DISCRETE` is anchored at [[agentic-ai-security-cmm-d1-governance|D1]] as a classification and publication control, and the third of the three examples it gives is minimizing technical details in model output ([`/go/discrete/`](https://owaspai.org/go/discrete/)).[^aix-discrete] D4-OUTPUT-SCOPE requires the output classifier's data-class scope to be recorded, and the two classes it names are content safety and the exposure-restricted data `SENSITIVE OUTPUT HANDLING` covers, which the Exchange illustrates with personal data, confidential identifiers, passwords, and tokens.[^aix-soh] `OVERSIGHT` adds system prompts to sensitive data as a special category, because an attacker can use one to circumvent the injection protection it carries,[^aix-oversight] so one kind of system detail already falls in the second class. Other technical detail about the system falls in neither. The enforcement point for it is this domain's output path, and no level here claims the class, because the Exchange gives the example with no mechanism, artifact, or threshold and a criterion would grade an assertion. D4-OUTPUT-SCOPE's record states whether that detail is inside the classifier's scope, and the control's anchor stays at D1, where its method sits.

## D3→D4 dependency cap

D4's effective score is capped at D3's raw score, because runtime enforcement acts only on decisions the control layer makes, so strong guardrails over a weak PDP add little. For the persona, the stress test names D4 the strongest domain at raw L2–L3, a range it also gives D7, while D3 sits at L1–L2, so effective D4 is pulled to roughly L1–L2. The headline "strongest domain" reports the raw score; the dependency-resolved score is lower. The cheapest move is therefore to firm up [[agentic-ai-security-cmm-d3-control-least-agency|D3]] before buying more guardrails. Report D4 as raw plus effective. See [[agentic-ai-security-cmm-dependency-rules|the dependency rules]].
