# Agentic AI Security CMM — D3 Control and Least Agency

## Domain decision and boundary

D3 determines whether each action an agent can invoke is authorized by a decision point the model cannot rewrite, held until that decision returns, and executed only within the approved task and delegation scope. It grades the deployed agents and all their tool, connector, command, function, MCP, and inter-agent calls, including calls through an orchestrator and the most permissive autonomy mode enabled. An action is one operation on a target. A write changes state outside the agent, including a send. [[agentic-ai-security-cmm-2026|The CMM]] defines the five cumulative levels. [[agentic-ai-security-cmm-measurement-protocol|The measurement protocol]] states the evidence method.

The decision point may be a policy engine, gateway, interceptor, or runtime permission system. It must be outside the model context even if it runs inside the same service. D3 grades its decision and enforcement path. [[agentic-ai-security-cmm-d1-governance|D1]] owns the deployment's risk approval and decision authority. [[agentic-ai-security-cmm-d2-identity|D2]] supplies and governs the agent identity and task-bound credentials. [[agentic-ai-security-cmm-d7-observability|D7]] grades telemetry, approval coverage, and denied out-of-scope event records. [[agentic-ai-security-cmm-d9-operations|D9]] operates the approval queue and incident response. A human approval is a decision for one action before execution. A standing allow rule is authorization policy, not a human approval. [[hitl|Human-in-the-Loop (HITL) for Agentic AI]] distinguishes that gate from a confirmation screen without enforcement.

A vendor-fixed agent remains in scope. Its product-specific tool list and administrator enablement settings establish the callable surface. If the vendor neither exposes nor attests the built-in tool list, the list-dependent criteria are unanswerable. A blank console is not proof of an empty tool set. A customer-built agent on a vendor platform uses the customer's configured list plus scoped platform evidence for enforcement. An agent with no callable action contributes no tool-call instance. The handbook records the corresponding applicability decision.

For a decision point inside a vendor runtime, customer configuration can establish isolation from model context, but verification still depends on the vendor's enforcement code. [[cmm-known-limitations|CMM Known Limitations]] records that evidence limit.

The stateful criteria use three terms consistently:

- A **task** is one unit of work started by a human request or an event.
- A **session** is one run of an agent from start to end and may span tasks. Restarting a component does not create a new security session when the task and authority continue.
- A **delegation hop** passes a task to an agent with a different configuration or identity. A child process using the parent's identity and grants remains in the parent's run.

## Failure paths

A prompt may instruct an agent to ignore a rule held only in context. A shell expansion can turn an apparently permitted command into a different executed action. A log-only decision point can observe a forbidden action without preventing it. Individually permitted writes can exceed a session limit, and a delegate can inherit more authority than its caller. Approval can be replayed for different parameters. The [OWASP AI Exchange least-model-privilege control](https://owaspai.org/go/leastmodelprivilege/) and [agentic testing guidance](https://owaspai.org/go/testing/) anchor these paths; the particular CMM gates remain this wiki's synthesis.

## L1–L5 progression

| Level | Observable authorization outcome |
|---|---|
| L1 — Initial | Tool use and human confirmation are local to the agent's operation, without a complete policy record. |
| L2 — Developing | The callable surface is bounded and destructive actions wait for a person or are refused. |
| L3 — Defined | Every call reaches a locked, outside-model decision and follows the tier and decision-rights record; high-risk routes and uncertain external writes have defined handling. |
| L4 — Managed | Task, session, delegation, elevation, and separation-of-duties state constrain permitted actions over time. |
| L5 — Optimizing | Approval binding, adaptive response, release checks, policy integrity, and security-consequential action order are tested and sustained. |

Levels are cumulative. A higher-level control cannot compensate for a missing lower-level decision or mediation path. The assessor records missing and opaque evidence separately and reports target blockers without converting them into a numeric cap.

## Criterion catalogue

The four action tiers used below are auto (runs), notify (runs and informs a named person), confirm (waits for an authorized person), and block (refused). “Destructive” includes deletion, unrestorable overwrite, bulk write, value transfer, access-right change, and external communication. An organization's classification can add classes. A decision test counts when run in production or against the same policy revision, enforcement code, and configuration that production runs.

### L2 detail

- **D3-ALLOW.** Each agent's tools are enumerated in an allowlist, and a component outside the model refuses a call to a tool the list does not hold, or holds the call until a human approves it. For a tool that runs arbitrary commands or requests, such as a shell or an HTTP client, the list also enumerates the commands or destinations the agent runs without a human's approval, and an entry that admits every command or destination enumerates nothing, so an agent holding one does not meet the criterion. The allowlist holds under every autonomy mode the deployment permits, and a mode that suppresses it, such as a bypass or unattended flag, fails the criterion for every agent that can run in that mode. *Evidence:* each agent's allowlist as the enforcing component reads it at the production version, with the autonomy modes the deployment permits and a call outside the list refused under the most permissive of them.
- **D3-APPROVE.** Each destructive action an agent can invoke waits for a human's approval before it runs, or a component outside the model refuses it. The approval can be informal, such as an in-session confirmation by the human the agent acts for, or a draft the agent prepares that leaves only when the user sends it, provided the action cannot run until the person acts. Coverage is complete: a destructive action the agent reaches without approval or refusal, through any tool, rule or autonomy mode, fails the criterion. Not applicable where no agent in the deployment can invoke a destructive action. *Evidence:* the approval step or the refusal governing each destructive action each agent can invoke, as configured in production, and one record of each step operating.

### L3 detail

- **D3-APPROVE-GATE.** A confirm-tier action does not run until an approver acts. The gate holds the action outside the model, the agent cannot proceed without a verified approval signal, and a denial, an expiry or an unreachable approval path leaves the action unrun. An instruction to the model to ask first fails the criterion, and so does a notice sent while the action proceeds. Not applicable where no action sits in the confirm tier and the deployment runs no human approval path that its tier record omits. *Evidence:* the gate's configuration with the approval records for a sample of confirm-tier actions, and a gate fire observed live or on the record.
- **D3-DENY.** The policy's default for a call no rule permits is deny: the call does not run, or it waits for a human approval under D3-APPROVE-GATE, and it never runs because no rule matched it. A policy whose default is permit fails the criterion, and so does a default that places an unlisted connector or tool in a class the agent can call. *Evidence:* the policy's default and its handling of an unmatched call, at the running revision.
- **D3-MEDIATE.** Every tool call every agent makes reaches a decision point before it runs, whether the agent makes the call itself or through an orchestration step, and under every autonomy mode the deployment permits. A tool whose calls bypass the decision point, or a mode in which the point is not consulted, fails the criterion. *Evidence:* the inventory of each agent's tools reconciled against the decision point's configuration and its decision log, showing the calls of each tool reaching it.
- **D3-MEDIATE-EXACT.** The decision point decides on the action in the form the executor carries it out, so a rule over a shell command reads the command as the shell will run it, and a rule over a path reads the path as the filesystem resolves it ([[guard-canonicalization-gap|Guard Canonicalization Gap]]). A rule that matches the raw text of a command before the shell expands, unquotes and splits it is advisory, and so is a prefix rule that admits a compound command beginning with an allowed one, and either fails the criterion. Not applicable where no agent holds a tool whose executor transforms its input, such as a shell, a file tool that takes a path, or a tool server that rewrites its arguments. *Evidence:* the rules compared with what the executor receives, and a compound or expanded command refused.
- **D3-MEDIATE-FAILCLOSED.** The enforcement point denies the call when the decision point is unreachable, times out or returns an error, and when its own policy source is absent or malformed. An enforcement point that proceeds without a decision, or that falls back to a policy wider than the one that failed to load, fails the criterion. *Evidence:* the configured failure behaviour with the record of a test that exercised it, or for an in-process decision point the behaviour the vendor documents for the running version when the policy source is absent or malformed.
- **D3-MEDIATE-OUTSIDE.** The decision point sits outside the model context: no instruction or content that reaches the model, such as a prompt, a retrieved document, a tool output or a file in the agent's workspace, changes the decision it returns or the policy it evaluates, because a restriction held only in the model's context is not enforced against an injected instruction. The agent's own tool calls cannot write the scope the policy comes from. Where the decision point exposes an interface of its own, such as a gateway, a proxy or a sidecar, a crafted call sent to that interface from the position the agent's tool-execution code holds, bypassing the model, is denied. Where the decision point runs inside the runtime that hosts the model and exposes no interface of its own, that test is not applicable, and the criterion is graded from the deployed configuration: the policy as a production instance of the runtime resolved it, the scope it came from, the write-deny holding the agent out of that scope, and a deny observed under the most permissive autonomy mode the deployment permits. The assessment then records the runtime's version beside that evidence, and that one vendor's code both runs the model and enforces the policy. *Evidence:* the direct-invocation test with its decision-log entry, or for an in-process decision point the substitute set [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]] names, with the policy's source scope.
- **D3-MEDIATE-SYNC.** No tool call runs until the decision point returns its decision, and a call runs only on a permit. A call the enforcement point sends for a decision and then runs without waiting fails the criterion, and so does a call that runs whatever the decision says, as in a log-only mode. *Evidence:* the enforcement code or configuration for each tool, showing the call held until the decision returns, and a trace in which the decision precedes the call.
- **D3-POLICY-LOCK.** The decision point's policy changes only through its own administration: neither the agent nor the principal it acts for can widen it. A policy that takes rules from a scope the agent's run or its principal can edit, such as a project settings file a pull request can change for its own run or a user settings file on a developer's own machine, fails the criterion, and so does an "allow always" answer that writes a permanent allow rule. A just-in-time grant the policy issues for one task changes no scope, and D3-ELEVATE grades it. Not applicable where no agent in the deployment holds a tool. *Evidence:* each scope the running policy takes rules from, with the principals able to change each.
- **D3-RIGHTS.** Every action class each agent can invoke has a row in a decision-rights matrix ([[decision-rights|Decision Rights for AI Agents]]) giving its decision right, approver, justification and time bound, and the decision path applies the row at call time. A class with no row is denied, an approval goes to the approver the row names and is accepted only from a holder of that role, a right outside its time bound is refused, and each rule that applies a row cites it. An approval that any holder of the session can give, with no check of the approver against the row, fails the criterion. *Evidence:* the matrix with the rule or workflow step that applies each row, and one approval routed to the approver its row names.
- **D3-TIER.** Every action each agent can invoke carries a tier, auto, notify, confirm or block, recorded before the action is available in production. A record in the organization's own vocabulary meets the criterion where it maps each of its values onto one of the four, and a value maps to notify only where a named person receives the notification. An allowlist whose unlisted calls are refused is such a record, with its entries at auto and every other call at block. A tier can hold no action, so a record that places nothing in confirm describes a deployment with no approval queue. *Evidence:* the dated tier record for each agent, covering each action it can invoke.
- **D3-TIER-DESTRUCT.** Every destructive action carries the confirm or the block tier, so none runs at auto or notify. Not applicable where no agent in the deployment can invoke a destructive action. *Evidence:* the destructive-action classification, which lists each agent's destructive actions with the tier each carries.
- **D3-TIER-ENFORCE.** The decision point returns each action's recorded tier as its decision: it permits an auto action, permits a notify action and informs the named person, holds a confirm action for approval, and denies a block action whoever asks. A tier applied outside the decision point, such as a pause in an agent's own code, fails the criterion for that tier, and so does a running policy that disagrees with the tier record. *Evidence:* the policy rules for each tier compared with the tier record, and a decision-log entry for each tier the record uses.
- **D3-HIGHRISK.** Before agents can invoke write actions, the organization defines and ranks high-risk action categories using irreversibility, data classification, external-party reach, and financial threshold, then maps each category to its authorization route and names which categories are critical. Leaving out one dimension or letting the requester choose an easier route fails. For an irreversible action where delay is useful, a documented cooling-off period and emergency route may supplement the authorization rule. Each emergency use records its reason and authorization; delay is not a universal scored gate. Not applicable where agents can invoke no write action. *Evidence:* category and routing rules with sampled decisions and any recorded emergency exception.
- **D3-HIGHRISK-SOD.** Each action classified as critical requires approvals from at least two people in different named roles before execution. The routing policy fixes the roles; neither the agent nor requester selects an approver. Not applicable where no callable action is classified as critical. *Evidence:* routing policy and a sample of critical-action approvals.
- **D3-WRITE-RECONCILE.** For each external write that could be applied twice, a gateway or equivalent trusted mediator binds a request identifier to the approved task and action instance before its first send and records the outcome. A duplicate proposal for that approval cannot obtain a fresh identifier while the outcome is unknown. An unknown outcome, including a timeout, blocks another send until the mediator confirms the provider's state by that identifier or a named reconciliation owner resolves it. A retry is permitted only when the first write is confirmed absent or the provider guarantees duplicate suppression for that identifier. A named owner handles compensation for an applied or partial write. A model-supplied identifier, blind retry after an unknown result, or missing reconciliation owner fails. Not applicable where no agent can initiate such an external write. *Evidence:* identifier and outcome records, provider lookup or reconciliation procedure, named compensation owner, and tests that refuse a duplicate with a fresh identifier and hold a timeout retry until resolved.

### L4 detail

- **D3-CHAIN.** The decision point validates the whole delegation chain behind each delegated call, from the first hop to the presenting agent, and rejects an action outside the scope the chain binds even where the presenting credential is valid. No agent in the chain validates only its own link, and a credential issued for one step of the chain fails when presented at another. Not applicable where no agent delegates a task to another agent. *Evidence:* the chain-validation rule, and a splice test in which a credential from one step was presented at another and refused.
- **D3-CHAIN-DEPTH.** The policy sets a maximum delegation depth, and the decision point refuses a delegation past it, by denying the call or by granting no delegation tool to an agent at the last permitted depth. A limit held only in the delegating agent's own code fails the criterion. Not applicable where no agent delegates a task to another agent. *Evidence:* the configured depth, with a delegation refused past it or the grants showing no delegation tool at the last permitted depth.
- **D3-CHAIN-SUBSET.** For each delegated task, the decision point intersects the downstream agent's standing grants with a task authorization fixed by the initiating principal or a trusted component outside the model context. A delegator may request a specialist action through a coordination grant without holding the specialist's direct-action grant. Each further delegation can narrow, but cannot widen, the task authorization; an action outside it is denied even when the downstream identity holds a wider standing grant. Not applicable where no agent delegates a task to another agent. *Evidence:* the approved task authorization and each hop's allowed scope, with a call using a specialist's wider standing grant denied.
- **D3-ELEVATE.** A grant beyond an agent's standing allowlist is issued just in time for one task, carries an expiry the decision point enforces, and lapses at the expiry or when the task ends, whichever comes first. An elevation that becomes standing, such as an approval answer that writes a permanent allow rule, fails the criterion. Not applicable where no agent can gain a grant beyond its standing allowlist. *Evidence:* the elevation mechanism's configuration, and the expiry log for a sample of elevations.
- **D3-LEDGER.** The decision path keeps a ledger, outside the model, of the write actions each session has executed, and denies a call that would carry a write class past the per-session limit the policy sets for it, as a count or a value, so individually permitted steps cannot add up past that limit. A limit that a restart resets while the session continues fails the criterion. Not applicable where no agent can invoke a write action. *Evidence:* the per-session limit for each write class, and a call the ledger denied.
- **D3-NOREPLAY.** An authorization issued to one agent is refused when any other agent presents it, the agent it delegates to included, so no authorization carries across a delegation hop, and the downstream agent receives an authorization of its own for the delegated task ([[owasp-ai-exchange|OWASP AI Exchange]], [`/go/agenticaioverview/`](https://owaspai.org/go/agenticaioverview/)). Not applicable where the deployment runs a single agent. *Evidence:* the record of a replay test in which another agent and a delegatee each presented the authorization and were refused.
- **D3-ORCHESTRATE.** An orchestrator holds coordination grants only: it can start, instruct and receive results from the agents it delegates to, and holds no grant to a destructive, confirm-tier or external-communication action, each of which runs through the agent the orchestrator delegates it to. Not applicable where no agent delegates a task to another agent. *Evidence:* the orchestrator's grants compared with the tier record.
- **D3-PROMOTE.** Each agent holds a recorded autonomy stage in a scheme the organization defines, such as Intern, Junior, Senior, and Principal, and moves up a stage only on promotion criteria the organization documents for that stage. Each change of stage is recorded against those criteria, and an agent with no recorded stage, or a promotion with no criteria behind it, fails the criterion. *Evidence:* the promotion rubric with each agent's current stage, and the record of each promotion in the period.
- **D3-SOD.** Every change an agent proposes to a production system's code, configuration, infrastructure or access policy passes three distinct principals: the one who proposes it, the one who approves it and the one who deploys it. The agent holds no role but proposer, and a pipeline in which the approver's merge is itself the deployment, or in which the proposer can approve or deploy, fails the criterion. Not applicable where no agent in the deployment proposes such a change. *Evidence:* the pipeline's role assignments and protections, and a sample of agent-proposed changes showing three distinct principals.
- **D3-TASKSCOPE.** Every tool invocation is authorized against the invoking agent's current task scope and role as well as against the tool's tier, so a call to a tool the agent holds is denied while the agent performs a task outside that tool's scope. The task scope is set when the task starts, outside the model, by the principal or the component that starts the task, and the agent cannot widen it during the task. *Evidence:* the policy input carrying the task scope and role, and a denied out-of-scope call.
- **D3-TRIFECTA.** A lethal-trifecta breaker runs at every decision. When a session holds private data, has taken in untrusted content and can reach an external-communications path, the decision point lowers the agent's autonomy automatically, moving its external-communication actions to confirm or block until the task ends or a person clears the session ([[lethal-trifecta|Lethal Trifecta]]). The external-communications leg is read transitively across every dependency the agent can call, and the agent's own network policy alone does not settle it. Not applicable where no agent can hold all three legs, the third read the same way. *Evidence:* the breaker's configuration with its transitive reading of the external leg, and a downgrade it recorded.

### L5 detail

- **D3-ADAPT.** The decision point reads each agent's production anomaly signal from D7 at call time. When the signal crosses the policy's threshold, it raises the affected action tiers and withdraws the specified grants. Both changes reverse when the signal clears or an authorized person resolves it. A dashboard alert with no policy response, or a response in one direction only, fails. *Evidence:* the signal input and policy rule, with test or production records of tier increase, grant withdrawal, and recovery.
- **D3-APPROVE-TOKEN.** Each human approval yields a token for that one request, cryptographically binding the approver's identity, the exact action parameters approved and an expiry, and the enforcement point rejects execution where a parameter deviates from the approved value or the token has expired. An approval held in a record or a workflow without that binding fails the criterion. Not applicable where no action any agent can invoke routes to a human approval. *Evidence:* an approval-token sample showing the three bound fields, and an execution refused for a deviating parameter.
- **D3-LEDGER-SEQUENCE.** For write paths where order or timing changes the security outcome, the decision point checks the session's executed history and denies a write that lacks a required predecessor, follows a forbidden predecessor, or falls outside its authorized window. It uses a session identity the agent cannot replace to erase history. The organization analyzes its write paths for consequential order and timing; a rule for every harmless sequence is unnecessary. Not applicable where agents can invoke no write action or a recorded analysis of all write paths establishes no security-consequential ordering condition. *Evidence:* the path analysis, running temporal rules, trustworthy session-binding configuration, and a denied out-of-order or out-of-window write where applicable.
- **D3-POLICY-COMPILE.** Every policy release is parsed, compiled, or validated by the policy language's tooling before it reaches production; a failed check blocks release. This checks structural validity, while D3-POLICY-SEMANTIC checks the policy's security properties. *Evidence:* validation output and release gate records for each policy release in the period.
- **D3-POLICY-DRIFT.** The policy each decision point runs is compared with the last reviewed release at each policy load and on a recorded schedule, and a difference raises an alert that a person resolves. A deployment that cannot show which revision its decision points run fails the criterion. *Evidence:* the drift check's configuration and its results over the period, with each alert and its resolution.
- **D3-POLICY-SEMANTIC.** Before each release of the deployment's credential and tool-call policies, including applicable MCP calls, decision tests or policy analysis check effective authorization behavior on the relevant action paths. They detect contradictory effects, unreachable rules, and unintended shadowing where these could change an access decision. Each finding is resolved or explicitly authorized by the policy owner; an unresolved defect blocks release. A compile pass alone fails, as does a generic check with no relationship to the deployment's hazards. Formal proof is one method, not a condition. *Evidence:* the decision tests or analysis report, finding dispositions, and protected release-gate records for each release.
- **D3-POLICY-REVIEW.** Every release of the decision point's policy is reviewed before it reaches production by a person other than its author, and the review is recorded. *Evidence:* the review record for each release in the period.
- **D3-SOD-CRYPTO.** The separation D3-SOD requires is enforced cryptographically: the approval and the deployment of each change are signed with keys that only their role holders hold, and the deploying key cannot produce a valid approval, so no single key both approves and deploys. Not applicable where D3-SOD is not applicable. *Evidence:* the key assignment per role, and a deployment refused because the deploying key signed its approval.

## Prerequisites and blockers

D3's action list depends on an actual tool and mode inventory. D2 supplies the agent identity and task binding used by per-agent rules and replay refusal. For a human-started task, D2-DELEGATE bounds the business action through every specialist: a coordinator's permission to request a specialist action is no grant to exceed the human's authority. D3-TASKSCOPE requires a task scope set by a principal or trusted component outside the model; agent text cannot enlarge it. A session ledger or temporal rule needs a session identifier that the agent cannot reset to escape the limit or sequence. D3-WRITE-RECONCILE also needs an external provider state lookup or an owner who can settle an uncertain write. D7 owns anomaly detection and delivery of a score for D3-ADAPT, while D9 owns approval-queue operation and D7 measures its coverage. The handbook records a failed criterion and its prerequisite owner as a target blocker.

## Deployment-shape differences

A read-only retrieval assistant may have no destructive action or write-ledger instance, but any callable tool still needs the relevant lower-level mediation. An in-suite assistant requires scoped vendor evidence for its built-in tools and enforcement path; opaque behavior remains unanswerable. A coding agent's shell, file, and repository actions make canonicalization, autonomy-mode bypass, and review/deploy separation material. A multi-agent workflow adds chain depth, subset, replay, and orchestrator constraints. A high-impact external writer makes high-risk routing, uncertain-outcome reconciliation, approval binding, and consequential action order relevant.

## Implementation and effort drivers

The first cost is enumerating the real callable surface, including indirect calls and permissive modes. Policy enforcement adds latency and a fail-closed outage path, so availability design must carry that cost. Later work maintains action tiers, approval roles, task context, bounded elevation, ledger state, and change review. Semantic policy analysis is a release check, distinct from syntax validation. It needs checks tied to the deployment's actual hazards and a release gate that rejects unresolved defects. Sequence checks need a trusted session boundary and event history. These controls can use native platform features, a gateway, or organization-operated code if the evidence demonstrates the outcome.

## Sources and limits

[OWASP least model privilege](https://owaspai.org/go/leastmodelprivilege/), [oversight](https://owaspai.org/go/oversight/), and [agentic security testing](https://owaspai.org/go/testing/) support the authorization and independent-test boundaries. OWASP calls for both coordination-only orchestrators and downstream grants that remain a subset of upstream grants. Applied literally, those rules conflict when a coordinator invokes a specialist. D3 tests non-expansion against authorization for the original task, while the coordinator retains only a delegation grant. [Cedar Analysis](https://aws.amazon.com/blogs/opensource/introducing-cedar-analysis-open-source-tools-for-verifying-authorization-policies/) is an implemented route to semantic policy checks, but syntax validation alone does not establish D3-POLICY-SEMANTIC. [AWS AgentCore temporal policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal.html) demonstrate history-dependent decisions. Their 24-hour maximum window, same-account and Region condition, and caller-supplied session identifier bound what they prove for D3-LEDGER-SEQUENCE. The model does not certify that an agent's action is prudent simply because the action was permitted.
