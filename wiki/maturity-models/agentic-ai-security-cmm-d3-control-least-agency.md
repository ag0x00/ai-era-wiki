# Agentic AI Security CMM — D3 Control & Least-Agency (Deep Dive)

Companion deep-dive to [[agentic-ai-security-cmm-2026|the CMM]]'s D3 domain, written under the [[agentic-ai-security-cmm-recalibration-method-2026|recalibration method]]. D3 is the decide plane: the [[oversight-layer|Policy Decision Point]] (PDP) outside the model context that authorizes agent actions. D4 is the runtime plane that enforces those decisions. The control landscape names the platform-native PDP options that ship today. Formal policy analysis already ships as open source, so the leading-edge tier grades running it over every release of the policies that govern MCP tool calls. Every criterion carries a name, D3 and a mnemonic such as D3-MEDIATE, and §Assessor detail per level states each one with the evidence it names.

> [!gap] Single-customer grounding
> Levels and cost model synthesize the recalibration method against the [[agentic-cmm-regulated-fi-stress-test|regulated-FI stress test]] plus vendor documentation. The L3–L5 criteria also cite the [[owasp-ai-exchange|OWASP AI Exchange]] entries footnoted at each. The status column of the control landscape is a May 2026 snapshot; rows re-read since carry their own retrieval dates in the notes.

## Threat coverage

D3 is the primary domain for **ASI02 (Tool Misuse)** and **ASI08 (Cascading Failures)**, and carries **Class 1 (insider, via dual control)** and **Class 3 (collusion, via tiered approval gates)**. Its policy decision point caps runtime-guardrail effectiveness (D4): a guardrail can only enforce a decision the PDP makes. The other Class 3 control, monitor isolation, belongs to the Observability plane, and the [[agentic-ai-threat-classes-2026|threat classes]] propose it as a [[agentic-ai-security-cmm-d7-observability|D7]] L4+ evidence item. See the [[threat-taxonomy-reconciliation|Threat Taxonomy Reconciliation]] matrix.

D3 is also the primary domain for the [[agent-escape|agent escape]] threat entry. The [[owasp-ai-exchange|OWASP AI Exchange]] places escape prevention at the infrastructure policy-enforcement layer, through capability-based access control that restricts tool sets, data sources, and action space independently of LLM reasoning, and pairs it with oversight monitoring for session-level jailbreak drift.[^aix-escape] D4 enforces the decision the PDP returns, and [[agent-sandboxing|sandboxing]] bounds what a wrong decision can reach.

The Class 3 coverage claim needs a bound the [[openai-hugging-face-agent-incident|OpenAI–Hugging Face agent incident]] supplies. Neither named control reached the collusion that occurred there.[^bhusa] Tiered approval gates were not bypassed, because no gate was triggered: writing a file to a package repository the workload is authorized to use is not an action class an approval tier covers. Monitor isolation held in the sense the control means it — the evaluation runs were mutually blind by construction — and the agents built a channel through a shared writable dependency anyway. **D3 grades what an agent may do, and both controls assume the coordination risk lives in the action set; in the attested case it lived in a medium two agents could both reach.** The complementary control is per-workload write scoping on shared caches and registries. [[agentic-ai-security-cmm-d8-supply-chain|D8]]'s D8-REPO-WRITE grades it at L4 for internal artifact repositories, and [[agentic-ai-security-cmm-d5-egress-network|D5]]'s D5-A2A-BROKER takes the network half of the same channel. See Open questions below.

Five capabilities survive the product churn: a PDP mediating every tool call outside the model context, least-agency tiering, per-task scoped authorization with binding, human-approval gates, and auto-downgrade on anomaly. The product names perish, and the tooling map holds them.

The Exchange's agentic authorization framework runs to seven parts, and the levels below grade four of them.[^aix-leastmodelpriv] Agents hold no permissions until granted, and each grant is scoped to a task, a time window, and a resource set, expiring when the task completes, times out, or is cancelled. Evaluation happens at API gateways, service meshes, or tool-execution proxies, through a dedicated policy decision point that returns permit or deny and withholds the policy logic behind it; that decision point and its enforcement point both sit outside the agent execution context, since an agent can reason around a policy expressed in a system prompt. The enumeration names three locations, and none is the runtime that hosts the model, so D3-MEDIATE-OUTSIDE at L3 admits a placement the Exchange does not list. It reads the requirement as the two things the Exchange states around it: that authorisation must not live in prompts the agent can reason around, and that the control is an interceptor in the data path validating an action before it reaches a tool.[^aix-leastmodelpriv] An assessor taking the enumeration itself as the criterion reaches a different verdict on the same deployment, and D3-MEDIATE-OUTSIDE names the evidence that carries this one.

Each grant binds a context chain — human principal, verified agent identity, tool and operation, target resource classification — and re-authorisation is required when scope expands, a read elevates to a write, a trust domain is crossed, or work is delegated downstream. The [[taiwan-ai-agent-government-intrusion|Taiwan AI-Agent Government Intrusion]] shows the cost of a trust boundary crossed without re-authorization: 84 of the 85 accounts the agent framework cracked authenticated to a department's internal information system through an SSO bridge that trusted the office-automation session with no additional authentication.[^taiwan] For dynamic task decomposition the Exchange prefers task-bound capability tokens, narrowable across delegation and subset-only when one agent delegates to another, with ABAC layered over them for time, data classification, input trust, and task stage.

The remaining three parts are graded in part in this domain or in another. Context-aware access control — infrastructure signals feeding graduated tiers, autonomous in low-risk context and gated in elevated-risk context — is graded in part by D3-ADAPT at L5 below, which reads D7 anomaly scores where the Exchange lists five signal classes. Agent identity verification, which the framework carries as unique cryptographic per-instance identity with mutual authentication and an active-agent registry, is graded at [[agentic-ai-security-cmm-d2-identity|D2]] and anchored there in [[agentic-ai-security-cmm-crosswalk|the crosswalk]]. Dynamic permission scoping — automatic narrowing the moment untrusted external content enters the flow — is graded in part by D3-TRIFECTA at L4, which narrows only once the session also holds private data and can reach an external party. Its unconditional form is implementation pattern 7 on [[least-agency-principle|least agency]], and [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] grades it at L4 for outbound sends: D4-CONTEXT holds each call that sends content outside the organization once untrusted content enters a session, and leaves write and sensitive-read tools to the session rule's own policy.

The [[microsoft-zt4ai|Microsoft ZT4AI]] least-privilege principle grounds the D3 deny-by-default level in its least-action design guidance ("start with no permitted actions by default"), crosswalked to D3 in [[standards-review-microsoft-zt4ai-2026-Q2|the 2026-Q2 ZT4AI review]].

Two open-source vulnerability-discovery harnesses ship a per-agent tool allowlist as a product default. [[vvah|VVAH]] runs a tool sandbox with no Bash and executes no code, and [[deepsec|deepsec]] gives its agents read-only tools, per the LLM-generated capability matrix and per-tool summaries in Semgrep's July 2026 survey of nine such harnesses.[^semgrep] The same survey separates three harnesses that reason completely statically from two that compile and execute binaries to validate a finding, which Semgrep calls a new hybrid analysis much closer to how human vulnerability research looks. Execution is the capability the narrowing removes, and a tool set without execution cannot produce the finding class that requires execution. The level definitions below grade the narrowing and say nothing about the workload's output, which is where the consequence of the narrowing lands. [[oss-ai-vuln-discovery-harness-landscape|The open-source harness landscape]] carries the comparison, and [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] grades the sandbox the executing harnesses run in.

Cyera states its Protect phase blocks a risky tool call during execution; the release names no policy language, no deny-by-default configuration, and no risk tier behind that block, so the release adds no entry to the table above ([[cyera-agent-guardian-release|Cyera Agent Guardian Release]]). Cyera states its Govern phase watches high autonomy as a risk signal, and the release names no permission-narrowing or capability-attenuation mechanism this domain's tooling map would carry.

## Capability-decoupled levels

Stated as capabilities per [[agentic-ai-security-cmm-recalibration-method-2026|rule 1]]; a control counts when it operates in production per rule 2. A control implemented through a product in the organization's approved-vendor pipeline with a documented production date satisfies its criterion on that basis alone, and the production date is the date the control entered the organization's production. A planned date satisfies none, and neither does a product the organization does not yet run in production, whatever the vendor has announced.

- **L1 — Initial.** No tool-call policy; agents can call any tool.
- **L2 — Developing.** Each agent's tools are enumerated in an allowlist, and a human approves each destructive action before it runs.
- **L3 — Defined.** A decision point outside the model context decides every tool call before it runs, denying by default and failing closed, against a documented tier for every action and a decision-rights matrix, and a confirm-tier action waits for its approver.
- **L4 — Managed.** The decision point decides on state as well as on the action: the task's scope, the session's cumulative writes, the delegation chain and a continuous lethal-trifecta reading. Autonomy is promoted by stage, elevation expires, the duties around an agent-proposed change stay separate, and an orchestrator holds coordination grants only.
- **L5 — Optimizing.** Cryptography carries each approval and the separation of duties, anomaly scores move an agent's tiers, and every policy release is compiled, reviewed and held against drift.
- **L5+ — Leading Edge.** Capability tokens carry each task's grant and narrow at each hop, trifecta-positive workloads run a privileged/quarantined split, formal analysis proves each policy release, and the policy decides on the order of a session's actions.

The platform-native decision points, AWS AgentCore Policy and the Microsoft Agent Governance Toolkit, are named in the control landscape and the L3 commentary, never in a criterion. D3-TASKSCOPE sits at L4 because authorizing a call against the current task needs session or task state, which the action-class decision graded at L3 does not carry. The three levels above L3 stay distinct on mechanism: L4 checks a task scope set outside the model and an aggregate over the actions a session has executed, L5 binds a human approval into a token the agent cannot mint for itself, and L5+ binds the scope into a capability the agent cannot assert, then decides on the order of the executed actions, which neither a task scope nor an aggregate carries. Cedar Analysis has shipped as open source since June 2025,[^cedaranalysis] so D3-POLICY-FORMAL grades running such analysis over every policy release, those governing MCP tool calls included. AWS AgentCore Policy has offered temporal policies since 2026-08-06,[^dogwood] and rule 2 holds them at L5+ until they clear the two-quarter window.

**Per-task holder-bound capability tokens sit at L5+.** The tooling map above records no platform-native product for the capability. Its one implementation is an open-source primitive, [[tenuo-warrant|Tenuo Warrant]], which its maintainers have classified as Production/Stable since release 0.2.0 of 2026-06-22,[^tenuo-pypi] and for which the vault's August 2026 reading found no independent enterprise-deployment evidence. [[agentic-ai-security-cmm-recalibration-method-2026|Rule 2]] places such a capability in L5+ until a production-hardened implementation path exists, and it states the reading that satisfies a level criterion: a product in the organization's approved-vendor pipeline with a documented production date. A primitive with no production deployment on record outside the organization that wrote it supplies neither the path nor the date. Rule 2 exists to keep the levels reachable for a buyer whose adoption cadence is externally constrained, and that buyer's reading is the graded one, so no program records a trade-off for declining the primitive. [[agentic-ai-security-cmm-d4-runtime-guardrails|D4]] reads the qualifier the same way twice. A September canvass of twenty-one runtime-protection vendors found no implementation clearing the two-quarter window and moved no graded status, and neither Defender's real-time protection for Agent 365 tooling servers, generally available since 2026-07-27 and inside the window, nor its agent threat detection, still in preview, carries a D4 L5 criterion until production-hardened. [[agentic-ai-security-cmm-d2-identity|D2]] grades the capability at L5+ and [[agentic-ai-security-cmm-d5-egress-network|D5]] holds it there on the same reading, so one level answers for all three domains. The capability returns to L5 when a platform ships it, or when the open-source primitive carries production evidence from an organization that did not write it.

**A high D3 score asserts that actions are permitted, and asserts nothing about whether they are wise.** The Exchange states the bound on its own control: authorisation and policy enforcement define what is permitted, agents can cause harm entirely inside their granted scope, and prompt injection landing before a delegation is established or misuse of legitimately delegated authority both survive a correct policy engine.[^aix-leastmodelpriv] Two operational costs travel with the levels above. Per-action evaluation adds latency to every tool call, and the behaviour D3-MEDIATE-FAILCLOSED requires converts a policy-engine outage into an agent outage, an availability trade the Exchange asks each deployment to make explicitly.[^aix-leastmodelpriv] Novel action sequences resist complete pre-specification, which leaves short token lifetimes, revocation within a stated latency tolerance, and delegation attenuation carrying the residue that policy authoring cannot.

## Assessor detail per level

L1 describes where a deployment starts and carries no criterion, so a deployment that does not meet every L2 criterion scores L1. It scores 0 under the measurement protocol's rubric only where no evidence of the L1 baseline exists, meaning the assessment holds no record and no interview answer about the domain for that deployment. The levels from L2 to L5+ each carry a criteria list below, each list stating what its own level adds.

Grading is cumulative: Level N requires every Level N–1 control plus the new criteria at Level N ([[agentic-ai-security-cmm-2026|the CMM]]), so a level is met only where every level below it is met.

Each criterion takes one of four verdicts. **Met** and **not met** are read from the evidence the criterion names, whoever operates the control. The assessment records the evidence's assurance class beside the verdict and names the artifact behind it, its issuer and its date, per [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]]:

- **Tested**: the customer or the assessor exercised the control and recorded what it did.
- **Inspected**: vendor tooling the customer can reach, or a record the organization keeps, such as an inventory or a plan, shows the control's state in the deployment.
- **Attested**: the vendor states the control in a document the customer holds, and the document's own scope names the control.

**Not applicable** is recorded where the deployment holds no instance of what the criterion governs, and the reduced scope is recorded as an intentional trade-off in the [[agentic-ai-security-cmm-dependency-rules|effective-score]] strategic-rationale field. **Unanswerable** is recorded where the instance exists, the customer can run no test and keeps no record of the control's state, and the vendor supplies neither inspectable output nor an attestation that names the control. An unanswerable criterion never counts as met: its level stays open, and every level above it stays open under cumulative grading. The assessment names what would close it. A criterion that can be not applicable states that condition alongside the criterion. Each level's list below holds criteria only, and a paragraph after a list states no criterion: it carries maturity, market or provenance commentary, or the boundary between this domain and another.

**D3 grades one deployment at a time.** A deployment is the unit the assessment scope names: one agent application, or one agent platform a vendor provides together with the agents the organization runs on it. Evidence of a control counts only for the deployments the control covers, and the D3→D4 cap reads the D3 score of the same deployment, as [[agentic-ai-security-cmm-d2-identity|D2]]'s caps read D2's. Four terms fix what the criteria range over:

- **An agent** is one deployed configuration: its code, instructions, tools and grants as the deployment runs them. Replicas of one configuration are one agent, and two configurations are two agents even where they share code.
- **The agents in scope** are those the deployment runs in production, per rule 2. An agent outside production enters scope once it holds a production credential or reaches production data. Evidence from a pilot outside scope counts for no criterion, and the gap report can cite it as the planned route to a level. A deployment with no agent in scope, such as a pilot that holds no production credential and reaches no production data, takes no D3 result, and the assessment records it as outside scope.
- **An agent's tool calls** are every call it makes to a tool, function, connector, MCP server, command or other agent, whether it makes the call itself or through an orchestration step, under every autonomy mode the deployment permits. A call to an agent of another deployment is a tool call of the calling agent and no delegation hop within the caller's deployment, so the Microsoft 365 Copilot deployment grades a call its assistant makes to a Copilot Studio agent published to Copilot, and the Copilot Studio deployment grades the called agent's own actions, grants and delegations. An agent that holds no tool makes no call this domain governs, so every criterion is not applicable to it.
- **An action** is one operation a call carries out on its target, such as a read, a write, a deletion or a send, and an **action class** groups the actions one decision right governs.

A criterion that names every agent, call or action is met only where it holds for each one. No percentage threshold applies, because the deployment's configuration enumerates its agents and their tools, and one agent outside the rule is the failure D3 grades. An agent whose configuration the organization cannot produce, such as a workstation that has stopped reporting to device management, does not meet a criterion that ranges over it. The assessment names the scope it graded, and where a narrower scope would change an agent's result, such as one repository of a shared CI workflow, it reports that agent beside the deployment's result.

**Grading words.** The criteria use these terms in one sense each:

- **Decision point**: the component outside the model context that returns permit or deny for a tool call, such as a policy engine, a gateway, a tool-execution proxy, an interceptor, or the permission rule set of the runtime that hosts the model. The **decision path** is the decision point together with the approval workflow its confirm decision invokes.
- **Destructive**: an action in any class below. The organization's own standard can add a class and cannot remove one, and for a coding agent the classes include force-push, branch deletion, a mass refactor and any write to production configuration, the four classes [[agentic-ai-security-cmm-2026|the CMM]] names for that shape.
    - Deleting data, records, files, branches or version history.
    - Overwriting any of them where the organization holds no prior version it can restore.
    - Writing in bulk across many records or files.
    - Releasing a payment or another transfer of value.
    - Changing an access right.
    - Sending a communication to a party outside the organization.
- **Human approval**: a person's decision, given for one action before it runs, that the action can run. A standing rule that lets a class of actions run without asking, such as the allow rule an "allow always" answer writes, is no approval. The approver is the human the agent acts for unless a decision-rights matrix names another, and D3-RIGHTS grades that naming.
- **The four tiers**, from [[emerging-cybersecurity-practices-for-agentic-ai-applications|Emerging Cybersecurity Practices for Agentic AI Applications]] §3.2: an auto action runs, a notify action runs and a named person is told, a confirm action waits for a human approval, and a block action is refused whoever asks.
- **Write action**: an action that changes state outside the agent, a send included.
- **Task** and **session**: a task is one unit of work an agent was started for, such as one user request or one scheduled run, and a session is one run of an agent from its start to its end, across the tasks it performs.
- **Delegation hop**: one agent passing a task to a different agent, meaning a different configuration or a different identity. A child session that runs the parent's configuration under the parent's identity is part of the parent's run.
- **Authorization**: a session, a token or a signed grant that a decision point or an identity provider issues to one agent and that the agent presents on later calls, such as the task-bound session and token D2-TASKBIND grades. A credential several agents share is no authorization of any one of them, and D2-IDENTITY grades the sharing. A deployment whose agents hold no authorization holds no instance of D3-NOREPLAY, which is then not applicable.
- **Release**: a change to a decision point's policy that reaches production.
- **Tested**: a test counts where it ran in production, or in another environment on the policy revision, enforcement code and configuration that production runs, and its record names the environment and the revisions. A demonstration the organization runs and the assessor observes is a test.

**Names and precedence.** Each criterion carries a stable name, D3 and a mnemonic for what the criterion requires, and the name leads the criterion in bold. The level is an attribute recorded beside the name, so a criterion that changes level keeps its name. Members of a family share its first mnemonic, as D3-CHAIN and D3-CHAIN-DEPTH do, and each member is a separate criterion because a deployment can hold one without the other and an assessor collects different evidence for each. [[agentic-ai-security-cmm-2026|The CMM]]'s D3 levels restate each criterion under the same name, and [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]]'s D3 questions and artifacts cite each one by that name, in plain text. A level's statement above summarizes its list, and where the two read differently the list governs.

**Vendor-fixed tools.** A vendor fixes an agent's tools where the agent runs on the vendor's infrastructure and the customer can enable or disable the vendor's built-in tools but cannot define them, as with an in-suite assistant. D3-ALLOW then reads the built-in tools from the vendor's own list, shown in the administrative console or stated in a vendor document whose scope names the product, narrowed by the customer's enablement settings, and reads the tools the customer adds, such as connectors, plugins and other agents, from the customer's own settings. Where neither the console nor such a document lists the built-in tools, D3-ALLOW is unanswerable for that agent, and so is each criterion whose instance would be read from that list, such as D3-APPROVE where the assessor cannot establish whether the agent can invoke a destructive action, because not applicable needs a tool list that shows no instance. An agent the organization builds on a vendor's platform, such as a Copilot Studio agent, holds the tools its maker configured, so its allowlist is the customer's own configuration, and the platform's enforcement of that configuration is graded on the evidence the vendor produces. That evidence is the administrative console's list of the tools each such agent can invoke at runtime, of the inspected class, and the list stands in for D3-ALLOW's refused call because the vendor presents it as the actions the agent can invoke[^msagentdetails]; where the console lists no tools for an agent, the platform's refusal of any other call is unanswerable until the vendor states it.

**Conditions the rubric adds.** [[agentic-ai-security-cmm-measurement-protocol|The measurement protocol]]'s rubric adds two conditions to score 3 that no domain's criteria state: operational ID tagging of the domain's findings, and the live observation it requires, a trace, a policy decision and, where D3-APPROVE-GATE applies, a gate fire. A deployment that meets every D3 L3 criterion without them scores 2 under the rubric, and the assessment records which condition held it there.

### L2 detail

- **D3-ALLOW.** Each agent's tools are enumerated in an allowlist, and a component outside the model refuses a call to a tool the list does not hold, or holds the call until a human approves it. For a tool that runs arbitrary commands or requests, such as a shell or an HTTP client, the list also enumerates the commands or destinations the agent runs without a human's approval, and an entry that admits every command or destination enumerates nothing, so an agent holding one does not meet the criterion. The allowlist holds under every autonomy mode the deployment permits, and a mode that suppresses it, such as a bypass or unattended flag, fails the criterion for every agent that can run in that mode. *Evidence:* each agent's allowlist as the enforcing component reads it at the production version, with the autonomy modes the deployment permits and a call outside the list refused under the most permissive of them.
- **D3-APPROVE.** Each destructive action an agent can invoke waits for a human's approval before it runs, or a component outside the model refuses it. The approval can be informal, such as an in-session confirmation by the human the agent acts for, or a draft the agent prepares that leaves only when the user sends it, provided the action cannot run until the person acts. Coverage is complete: a destructive action the agent reaches without approval or refusal, through any tool, rule or autonomy mode, fails the criterion. Not applicable where no agent in the deployment can invoke a destructive action. *Evidence:* the approval step or the refusal governing each destructive action each agent can invoke, as configured in production, and one record of each step operating.

### L3 detail

- **D3-MEDIATE.** Every tool call every agent makes reaches a decision point before it runs, whether the agent makes the call itself or through an orchestration step, and under every autonomy mode the deployment permits. A tool whose calls bypass the decision point, or a mode in which the point is not consulted, fails the criterion. *Evidence:* the inventory of each agent's tools reconciled against the decision point's configuration and its decision log, showing the calls of each tool reaching it.
- **D3-MEDIATE-OUTSIDE.** The decision point sits outside the model context: no instruction or content that reaches the model, such as a prompt, a retrieved document, a tool output or a file in the agent's workspace, changes the decision it returns or the policy it evaluates, because a restriction held only in the model's context is not enforced against an injected instruction.[^aix-testing] The agent's own tool calls cannot write the scope the policy comes from. Where the decision point exposes an interface of its own, such as a gateway, a proxy or a sidecar, a crafted call sent to that interface from the position the agent's tool-execution code holds, bypassing the model, is denied. Where the decision point runs inside the runtime that hosts the model and exposes no interface of its own, that test is not applicable, and the criterion is graded from the deployed configuration: the policy as a production instance of the runtime resolved it, the scope it came from, the write-deny holding the agent out of that scope, and a deny observed under the most permissive autonomy mode the deployment permits. The assessment then records the runtime's version beside that evidence, and that one vendor's code both runs the model and enforces the policy. *Evidence:* the direct-invocation test with its decision-log entry, or for an in-process decision point the substitute set [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]] names, with the policy's source scope.
- **D3-MEDIATE-SYNC.** No tool call runs until the decision point returns its decision, and a call runs only on a permit.[^aix-leastmodelpriv] A call the enforcement point sends for a decision and then runs without waiting fails the criterion, and so does a call that runs whatever the decision says, as in a log-only mode. *Evidence:* the enforcement code or configuration for each tool, showing the call held until the decision returns, and a trace in which the decision precedes the call.
- **D3-MEDIATE-FAILCLOSED.** The enforcement point denies the call when the decision point is unreachable,[^aix-leastmodelpriv] times out or returns an error, and when its own policy source is absent or malformed. An enforcement point that proceeds without a decision, or that falls back to a policy wider than the one that failed to load, fails the criterion. *Evidence:* the configured failure behaviour with the record of a test that exercised it, or for an in-process decision point the behaviour the vendor documents for the running version when the policy source is absent or malformed.
- **D3-MEDIATE-EXACT.** The decision point decides on the action in the form the executor carries it out, so a rule over a shell command reads the command as the shell will run it, and a rule over a path reads the path as the filesystem resolves it ([[guard-canonicalization-gap|Guard Canonicalization Gap]]). A rule that matches the raw text of a command before the shell expands, unquotes and splits it is advisory, and so is a prefix rule that admits a compound command beginning with an allowed one, and either fails the criterion. Not applicable where no agent holds a tool whose executor transforms its input, such as a shell, a file tool that takes a path, or a tool server that rewrites its arguments. *Evidence:* the rules compared with what the executor receives, and a compound or expanded command refused.
- **D3-DENY.** The policy's default for a call no rule permits is deny: the call does not run, or it waits for a human approval under D3-APPROVE-GATE, and it never runs because no rule matched it. A policy whose default is permit fails the criterion, and so does a default that places an unlisted connector or tool in a class the agent can call. *Evidence:* the policy's default and its handling of an unmatched call, at the running revision.
- **D3-POLICY-LOCK.** The decision point's policy changes only through its own administration: neither the agent nor the principal it acts for can widen it. A policy that takes rules from a scope the agent's run or its principal can edit, such as a project settings file a pull request can change for its own run or a user settings file on a developer's own machine, fails the criterion, and so does an "allow always" answer that writes a permanent allow rule. A just-in-time grant the policy issues for one task changes no scope, and D3-ELEVATE grades it. Not applicable where no agent in the deployment holds a tool. *Evidence:* each scope the running policy takes rules from, with the principals able to change each.
- **D3-TIER.** Every action each agent can invoke carries a tier, auto, notify, confirm or block, recorded before the action is available in production. A record in the organization's own vocabulary meets the criterion where it maps each of its values onto one of the four, and a value maps to notify only where a named person receives the notification. An allowlist whose unlisted calls are refused is such a record, with its entries at auto and every other call at block. A tier can hold no action, so a record that places nothing in confirm describes a deployment with no approval queue. *Evidence:* the dated tier record for each agent, covering each action it can invoke.
- **D3-TIER-DESTRUCT.** Every destructive action carries the confirm or the block tier, so none runs at auto or notify. Not applicable where no agent in the deployment can invoke a destructive action. *Evidence:* the destructive-action classification, which lists each agent's destructive actions with the tier each carries.
- **D3-TIER-ENFORCE.** The decision point returns each action's recorded tier as its decision: it permits an auto action, permits a notify action and informs the named person, holds a confirm action for approval, and denies a block action whoever asks. A tier applied outside the decision point, such as a pause in an agent's own code, fails the criterion for that tier, and so does a running policy that disagrees with the tier record. *Evidence:* the policy rules for each tier compared with the tier record, and a decision-log entry for each tier the record uses.
- **D3-APPROVE-GATE.** A confirm-tier action does not run until an approver acts. The gate holds the action outside the model, the agent cannot proceed without a verified approval signal, and a denial, an expiry or an unreachable approval path leaves the action unrun.[^aix-oversight] An instruction to the model to ask first fails the criterion, and so does a notice sent while the action proceeds. Not applicable where no action sits in the confirm tier and the deployment runs no human approval path that its tier record omits. *Evidence:* the gate's configuration with the approval records for a sample of confirm-tier actions, and a gate fire observed live or on the record.
- **D3-RIGHTS.** Every action class each agent can invoke has a row in a decision-rights matrix ([[decision-rights|Decision Rights for AI Agents]]) giving its decision right, approver, justification and time bound, and the decision path applies the row at call time. A class with no row is denied, an approval goes to the approver the row names and is accepted only from a holder of that role, a right outside its time bound is refused, and each rule that applies a row cites it. An approval that any holder of the session can give, with no check of the approver against the row, fails the criterion. *Evidence:* the matrix with the rule or workflow step that applies each row, and one approval routed to the approver its row names.

The tier scheme graded here is [[emerging-cybersecurity-practices-for-agentic-ai-applications|Emerging Cybersecurity Practices for Agentic AI Applications]] §3.2's operationalization of the OWASP ASI least-agency principle; ASI names the principle and supplies no tiers. The tier scheme sorts actions by risk and says nothing about who approves them. The human-involvement axis is the [[owasp-ai-exchange|OWASP AI Exchange]] oversight requirement set, graded at L3 through D3-APPROVE-GATE, at L4 through D3-APPROVE-COVERAGE and at L5 through D3-APPROVE-TOKEN; [[least-agency-principle|Least Agency Principle]] carries both tables side by side.

AWS AgentCore Policy (GA) and the Microsoft Agent Governance Toolkit (OSS) each supply a decision point that intercepts tool calls, and Verified Permissions supplies one that the deployment's own enforcement point calls, so no off-stack purchase stands between a buyer and the L3 decision point. The tier record and the decision-rights matrix stay the organization's own artifacts.

[[agentic-ai-security-cmm-d9-operations|D9]]'s D9-HIGHRISK and D9-HIGHRISK-RECORD, at D9 L3, grade the categories a high-risk approval covers and the tamper-evident record each approval writes, and D3-TIER-DESTRUCT and D3-APPROVE-GATE grade that the destructive actions sit in the confirm or block tier and that the gate holds them. A deployment can meet either domain's criteria without the other's.

### L4 detail

- **D3-PROMOTE.** Each agent holds a recorded autonomy stage, one of four the organization defines, such as the CSA Agentic Trust Framework's Intern, Junior, Senior and Principal, and moves up a stage only on promotion criteria the organization documents for that stage. Each change of stage is recorded against those criteria, and an agent with no recorded stage, or a promotion with no criteria behind it, fails the criterion. *Evidence:* the promotion rubric with each agent's current stage, and the record of each promotion in the period.
- **D3-APPROVE-COVERAGE.** For each action class, the organization measures on a recorded cadence the share of its executions that a human approved, from the decision path's own records, and a review reads each measure against the class's tier and records as a finding any confirm-tier class below full coverage. Not applicable where no action any agent can invoke routes to a human approval. *Evidence:* the coverage report per action class for the latest period, with its cadence and the review that read it.
- **D3-TRIFECTA.** A lethal-trifecta breaker runs at every decision. When a session holds private data, has taken in untrusted content and can reach an external-communications path, the decision point lowers the agent's autonomy automatically, moving its external-communication actions to confirm or block until the task ends or a person clears the session ([[lethal-trifecta|Lethal Trifecta]]). The external-communications leg is read transitively across every dependency the agent can call, and the agent's own network policy alone does not settle it.[^bhusa] Not applicable where no agent can hold all three legs, the third read the same way. *Evidence:* the breaker's configuration with its transitive reading of the external leg, and a downgrade it recorded.
- **D3-ELEVATE.** A grant beyond an agent's standing allowlist is issued just in time for one task, carries an expiry the decision point enforces, and lapses at the expiry or when the task ends, whichever comes first. An elevation that becomes standing, such as an approval answer that writes a permanent allow rule, fails the criterion. Not applicable where no agent can gain a grant beyond its standing allowlist. *Evidence:* the elevation mechanism's configuration, and the expiry log for a sample of elevations.
- **D3-SOD.** Every change an agent proposes to a production system's code, configuration, infrastructure or access policy passes three distinct principals: the one who proposes it, the one who approves it and the one who deploys it. The agent holds no role but proposer, and a pipeline in which the approver's merge is itself the deployment, or in which the proposer can approve or deploy, fails the criterion. Not applicable where no agent in the deployment proposes such a change. *Evidence:* the pipeline's role assignments and protections, and a sample of agent-proposed changes showing three distinct principals.
- **D3-NOREPLAY.** An authorization issued to one agent is refused when any other agent presents it, the agent it delegates to included, so no authorization carries across a delegation hop, and the downstream agent receives an authorization of its own for the delegated task ([[owasp-ai-exchange|OWASP AI Exchange]], [`/go/agenticaioverview/`](https://owaspai.org/go/agenticaioverview/)). Not applicable where the deployment runs a single agent. *Evidence:* the record of a replay test in which another agent and a delegatee each presented the authorization and were refused.
- **D3-TASKSCOPE.** Every tool invocation is authorized against the invoking agent's current task scope and role as well as against the tool's tier, so a call to a tool the agent holds is denied while the agent performs a task outside that tool's scope.[^aix-escape] The task scope is set when the task starts, outside the model, by the principal or the component that starts the task, and the agent cannot widen it during the task. *Evidence:* the policy input carrying the task scope and role, and a denied out-of-scope call.
- **D3-TASKSCOPE-RECORD.** Each out-of-scope call D3-TASKSCOPE denies is recorded as an [[agent-escape|Agent Escape]] event naming the agent, the task, the tool and the scope the call fell outside.[^aix-escape] *Evidence:* the agent-escape record of a denied out-of-scope call.
- **D3-LEDGER.** The decision path keeps a ledger, outside the model, of the write actions each session has executed, and denies a call that would carry a write class past the per-session limit the policy sets for it, as a count or a value, so individually permitted steps cannot add up past that limit.[^aix-leastmodelpriv] A limit that a restart resets while the session continues fails the criterion. Not applicable where no agent can invoke a write action. *Evidence:* the per-session limit for each write class, and a call the ledger denied.
- **D3-CHAIN.** The decision point validates the whole delegation chain behind each delegated call, from the first hop to the presenting agent, and rejects an action outside the scope the chain binds even where the presenting credential is valid.[^aix-leastmodelpriv] No agent in the chain validates only its own link, and a credential issued for one step of the chain fails when presented at another. Not applicable where no agent delegates a task to another agent. *Evidence:* the chain-validation rule, and a splice test in which a credential from one step was presented at another and refused.
- **D3-CHAIN-DEPTH.** The policy sets a maximum delegation depth, and the decision point refuses a delegation past it, by denying the call or by granting no delegation tool to an agent at the last permitted depth. A limit held only in the delegating agent's own code fails the criterion. Not applicable where no agent delegates a task to another agent. *Evidence:* the configured depth, with a delegation refused past it or the grants showing no delegation tool at the last permitted depth.
- **D3-CHAIN-SUBSET.** A downstream agent holds at most the grants its delegator held for the delegated task, and the decision point blocks an action that would take a session's cumulative privilege above the authorization the session started with. A downstream agent holding a grant, connection or credential its delegator lacks fails the criterion. Not applicable where no agent delegates a task to another agent. *Evidence:* a delegation sample setting each downstream agent's grants against its delegator's.
- **D3-ORCHESTRATE.** An orchestrator holds coordination grants only: it can start, instruct and receive results from the agents it delegates to, and holds no grant to a destructive, confirm-tier or external-communication action, each of which runs through the agent the orchestrator delegates it to.[^aix-oversight] Not applicable where no agent delegates a task to another agent. *Evidence:* the orchestrator's grants compared with the tier record.

CSA's Agentic Trust Framework names four maturity levels and five promotion-gate categories — Performance, Security Validation, Business Value, Incident Record, Governance Sign-off — and publishes no threshold or scored rubric behind any of them ([[csa-maestro|CSA MAESTRO / CSA Agentic Trust Framework]]), so the criteria D3-PROMOTE reads are a rubric the assessed organization writes. [[wiki-novelty-and-counterarguments-2026|Wiki Novelty and Counter-Arguments]] tracks this org-authored-rubric dependency as an open contest against the standard this level cites.

D3-NOREPLAY sits at L4 because it binds an authorization to an identity [[agentic-ai-security-cmm-d2-identity|D2]] already issues. D2-TASKBIND grades the binding a session and its token carry, D3-NOREPLAY grades the decision point's refusal when another agent presents them, and the per-task capability tokens that carry the binding cryptographically sit at L5+ as D3-TASKTOKEN. D3-LEDGER limits what a session's writes add up to, while the volume of calls an agent makes falls under D5's per-agent call ceilings and the operation that stops an agent is D2-KILL. AWS AgentCore Policy's temporal policies count and sum over the events one policy session records within a window of at most 24 hours, and the caller supplies the session ID, so each new session starts a new count.[^dogwood] Per-session limits set in them therefore meet D3-LEDGER, from the date they entered the deployment's production, only where each agent session lasts no longer than the window and runs under one policy session the agent cannot replace. Their ordering operators belong to D3-LEDGER-SEQUENCE.

D3-SOD separates the principals around a change an agent proposes. The [[owasp-ai-exchange|OWASP AI Exchange]] also asks for separate author, review and deploy roles over the artifacts that shape an agent's behaviour, among them its system prompt and its configuration.[^aix-devtime] D1-HARNESS-REVIEW, at [[agentic-ai-security-cmm-d1-governance|D1]] L3, grades a documented review of each change to a coding harness's configuration tree, and D3-POLICY-REVIEW grades review of the decision point's policy, and neither D1-HARNESS-REVIEW nor any D3 criterion separates the three roles over an agent's own instructions, tools and grants, which §Open questions records.

### L5 detail

- **D3-APPROVE-TOKEN.** Each human approval yields a token for that one request, cryptographically binding the approver's identity, the exact action parameters approved and an expiry, and the enforcement point rejects execution where a parameter deviates from the approved value or the token has expired.[^aix-oversight] An approval held in a record or a workflow without that binding fails the criterion. Not applicable where no action any agent can invoke routes to a human approval. *Evidence:* an approval-token sample showing the three bound fields, and an execution refused for a deviating parameter.
- **D3-ADAPT.** The decision point reads each agent's D7 anomaly score at call time in production. A score above the threshold the policy sets steps the agent up, raising the tier of its actions, and steps it down, withdrawing the grants the policy names for that case, and both reverse when the score falls back below the threshold or a person clears the agent. A score the decision point does not read, or a response in one direction only, fails the criterion. *Evidence:* the anomaly-score input in the policy, and adaptation records showing a step-up, a step-down and their reversal.
- **D3-POLICY-COMPILE.** Every release of the decision point's policy is compiled or validated by the policy language's own tooling before it reaches production, and a release that fails does not ship. *Evidence:* the compile or validation output for each release in the period.
- **D3-POLICY-REVIEW.** Every release of the decision point's policy is reviewed before it reaches production by a person other than its author, and the review is recorded. *Evidence:* the review record for each release in the period.
- **D3-POLICY-DRIFT.** The policy each decision point runs is compared with the last reviewed release at each policy load and on a recorded schedule, and a difference raises an alert that a person resolves. A deployment that cannot show which revision its decision points run fails the criterion. *Evidence:* the drift check's configuration and its results over the period, with each alert and its resolution.
- **D3-SOD-CRYPTO.** The separation D3-SOD requires is enforced cryptographically: the approval and the deployment of each change are signed with keys that only their role holders hold, and the deploying key cannot produce a valid approval, so no single key both approves and deploys. Not applicable where D3-SOD is not applicable. *Evidence:* the key assignment per role, and a deployment refused because the deploying key signed its approval.

### L5+ detail

- **D3-TASKTOKEN.** The decision point authorizes each call from a capability token issued for one task and bound cryptographically to its holder, and refuses the token when another holder presents it or after its task has closed, so the grant travels in the token and the agent cannot assert a scope the token does not carry. [[agentic-ai-security-cmm-d2-identity|D2]] grades the token's construction under D2-TASKTOKEN, and this criterion grades its evaluation. *Evidence:* the token-verification configuration, with refusals of a token presented by another holder and of one presented after its task closed.
- **D3-CHAIN-ATTENUATE.** A capability token an agent passes on carries a subset of the capabilities it holds, and the decision point refuses a delegated token wider than its parent, so authority narrows at each hop. Not applicable where no agent delegates a task to another agent. *Evidence:* a two-hop token sample showing the narrowed scope, and a widened token refused.
- **D3-QUARANTINE.** Each workload that holds private data, takes in untrusted content and can reach an external-communications path runs a privileged/quarantined split in production ([[camel-pattern|CaMeL Pattern (Compartmentalized Machine Learning)]]): the model that plans and calls tools reads no untrusted content, the model that reads untrusted content holds no tool, and what passes between them moves under an information-flow policy the decision point enforces. Not applicable where no workload holds all three. *Evidence:* the split's production configuration and its information-flow policy, with a flow the policy blocked.
- **D3-POLICY-FORMAL.** For every release of the policies the deployment's credential and tool-call decision points run, including those that govern MCP tool calls, formal analysis proves that the set holds no contradiction, no vacuous rule and no rule shadowed by another, and a release that fails the analysis does not ship. *Evidence:* the analysis report for each release in the period, covering both decision points.
- **D3-LEDGER-SEQUENCE.** The decision point decides on the order and timing of the actions a session has executed, such as a prerequisite that must precede an action, a succession it forbids or a time window, where D3-LEDGER decides on their aggregate. Not applicable where no agent can invoke a write action. *Evidence:* the sequence rules in the running policy, and a call one of them refused.

Rule 2 keeps four of these criteria short of L5 on the reading the tooling map gives, and D3-POLICY-FORMAL sits here on its scope. Capability tokens have one open-source implementation and no platform-native one, and the privileged/quarantined split has one vendor implementation, marked experimental by its vendor and enforcing in tool-call middleware rather than over a generated program.[^fides] Formal analysis ships as open source, and this level adds running it over every release of the policies that govern MCP tool calls. Temporal policies have shipped in AWS AgentCore Policy since 2026-08-06, written in the open-source Dogwood language, and rule 2 holds the capability at this level until it clears the two-quarter window, around February 2027.[^dogwood]

## Right-sizing by deployment shape

| Deployment shape | Realistic D3 target |
|---|---|
| Internal RAG / member-facing chatbot (few/no tools) | L2 → L3 |
| In-suite productivity assistant (Gemini for Workspace, Microsoft 365 Copilot) | L3 |
| Desktop-agent productivity assistant ([[claude-cowork\|Claude Cowork]] class) | L3 |
| Data-science / coding copilot | L3 → L4 |
| MCP / skill provider serving others | L4 → selective L5 |
| High-autonomy multi-agent mesh | L5 (+L5+ where resourced) |

An agent the organization builds on a vendor's platform, such as a Copilot Studio agent, takes the row its own function fits.

**An allowlist, a PDP, and action-risk tiering are the whole of D3 for a chatbot with few or no tools.** With no external-communications reach the trifecta is broken by architecture, so per-task tokens, JIT elevation, and cryptographic SoD are controls for their own sake. [[agentic-ai-security-cmm-recalibration-method-2026|The persona]]'s bot sits here, with few tools and informal approval on its write actions.

**The tool-call mediation this domain grades runs inside an in-suite productivity assistant's vendor.** What the customer holds is per-organizational-unit enablement and data-loss-prevention rules bounding which sources the assistant reaches, so the evidence is configuration that bounds reach rather than a decision point the customer operates. The decision point is graded on the evidence the vendors produce, and two criteria resolve **not met** on it. Microsoft documents a tool-chain analysis at the grounding stage that evaluates tool usage, validates tool capabilities and decides whether to block or allow a request, and records its output as a signal supporting task adherence rather than as an enforcement point the article places in the call path; the article names no policy language, states no coverage over every tool call and states no default-deny posture, so D3-MEDIATE is not met on attested evidence.[^msdefense] D3-MEDIATE-FAILCLOSED is not met on inspected evidence, because the policy gate the customer configures over this shape is Microsoft Purview data-loss prevention, and the interaction audit record carries a `DLPEvaluationDeferred` bitmask marking the prompt, response, grounding or web-grounding stage whose evaluation could not be completed during the original request processing and was deferred for later reevaluation, with a companion reason field whose documented values include a timeout and an unavailable service.[^mscopilotaudit] On the Google side a matching Workspace data-protection rule stops Gemini using the source to generate its response and logs the event, and the page read states no deferral path.[^gdlpgemini] D3-TIER and D3-RIGHTS stay customer artifacts, because the agent registry in the administrative console enumerates the tools an agent can invoke at runtime and records no tier against those tools.[^msagentdetails] That registry is the inspected source D3-ALLOW reads under the vendor-fixed tools rule where it lists an agent's tools, and where neither the registry nor a vendor document the organization holds lists the assistant's built-in tools, D3-ALLOW is unanswerable. The row covers the in-suite variant alone.

**A desktop agent mediates its own local tool calls, and the vendor mediates its connector calls server side.** The two variants land on the same level on different evidence. [[claude-cowork|Claude Cowork]] lets an owner set each permission category of a connector, such as its read-only tools or its write and delete tools, or each individual permission, to always allow, needs approval, or blocked, which is this shape's D3-TIER record and an artifact the assessment can read; it pins permanent file deletion to an explicit approval; and it denies a permission prompt raised by a dispatched child task after ten minutes, with the task continuing without that action, so the gate denies on timeout rather than proceeding. The decision point over local files and the browser sits inside the desktop application, which is the condition D3-MEDIATE-OUTSIDE states: its direct-invocation test is recorded not applicable, and the criterion is graded from the deployed configuration, which on a managed deployment is the device profile's allowed workspace folders, disabled built-in tools and managed MCP server list. [[agentic-ai-security-cmm-measurement-protocol|The measurement protocol]] carries the artifacts that grading collects. D3-RIGHTS is not met, because the approver is whoever holds the session, and the settings recorded there bind a capability to a role and not an action class to an approver. The row covers the desktop-agent variant alone.

**A copilot touches the SDLC, which makes segregation of duties load-bearing.** D3-SOD holds the proposer, the approver and the deployer of each change the copilot proposes to three distinct principals, and D3-ELEVATE stops a maintenance grant from becoming permanent.

**Scoping a grant at issue time bounds third-party blast radius.** An MCP or skill provider is consumed by callers it does not control, so its selective L5 target scopes each grant when it issues it rather than trusting the caller at call time. The holder-bound per-task form of that scoping sits a level above the row, at L5+.

**Delegation-aware capability tokens freeze blast radius at the top of the chain.** Of the six shapes in the table, only the mesh carries enough exposure for the L5+ tail — those tokens and the [[camel-pattern|CaMeL]] split — to earn its cost.

The [[lethal-trifecta|lethal-trifecta]] test is the primary instrument for lowering the required level: removing the sensitive-action or external-comms capability costs less than buying controls to govern it. Its design-constraint restatement, the [[agents-rule-of-two|Agents Rule of Two]], gives the assessor the same test in actionable form.

For the coding-copilot row, a text-matching command allowlist fails D3-MEDIATE-EXACT. The [[guard-canonicalization-gap|guard canonicalization gap]] describes why: the guard inspects a string the shell rewrites before executing. The [[guardfall-shell-injection-audit|GuardFall audit]] of eleven open-source coding and computer-use agents found that construction defeated in five of them: three guards were bypassed outright, and two tokenized guards leaked on quoted substitution and destructive flags. Five more exposed the shell through no static guard or through a container sandbox with a commonly used opt-out, and one guard held.[^guardfall] An organization scoring D3 on a Bash pattern allowlist has overstated by roughly a level, because D3-MEDIATE-EXACT grades such a rule advisory. Control catalog: [[securing-agentic-coding|Securing Agentic Coding]].

Grade the cruder condition first. D3-ALLOW and D3-MEDIATE both hold under every autonomy mode the deployment permits, so an allowlist an autonomy flag suppresses meets neither, and what the guard matches, the question D3-MEDIATE-EXACT asks, arises only once the guard is consulted. The [[gemini-cli-workspace-trust-rce|Gemini CLI Workspace-Trust RCE]] is the case: before 0.39.1, `--yolo` ignored the fine-grained tool allowlist in `settings.json` outright, so a workflow's enumerated permissions were evidence of nothing. Both conditions apply to the CI-runner and unattended-local variants in [[generative-coding-deployment-shape-2026|Generative Coding Deployment Shapes]], where the autonomy modes that suppress these controls are the defaults rather than the exception.

**A managed permission policy the developer's session cannot widen is a decision point, and the harness holding it is where the decision is made.** The policy arrives from a scope outside the session, deployed by device management or delivered to the authenticated session, and the deny rules it sets hold under the autonomy modes the deployment permits ([[securing-agentic-coding|Securing Agentic Coding]]). The harness resolves that policy and returns permit or deny before the tool call runs, and the property D3-MEDIATE-OUTSIDE tests is that an instruction reaching the model's context cannot write the scope the policy came from, which the deployed configuration has to show, and the assessment records the circularity beside that evidence. D3-POLICY-LOCK grades whether the developer can widen that policy, and a deployment whose harness also takes rules from the developer's own settings fails it. The enforcement point sits outside the model's context and inside the vendor's software, so one code path both runs the model and enforces a policy the customer administers, and the resolved policy, the decision and the record of it all come from that path. Injection resistance survives that, because the administrative scope stays beyond the model's reach. The independence of the evidence does not, and [[agentic-ai-security-cmm-measurement-protocol|the measurement protocol]] names the artifacts produced outside the harness that narrow it; [[cmm-known-limitations|CMM Known Limitations]] item 19 records the reading and the residue it leaves. D3-RIGHTS stays not met for this shape, because the approver is whoever holds the session.

## Cost model

Two paths reach the L3 policy decision point at `~0`: a Microsoft E5 incumbent's entitlements, and AWS's consumption-priced route, both platform-native. Google's path runs through IAM Unified Access Policies, generally available since 2026-08-31 and enforced at Agent Gateway,[^agentplatrn] so the licensing line stays near zero there too, and the cost surfaces in design instead. The feature's overview states that it does not support VPC Service Controls,[^uap] and Agent Gateway enforces perimeter rules only on deployments created after 2026-09-08,[^agentplatrn] so a deployment needing both an agent PDP and a service perimeter has to establish which path each one covers. Every stack pays the same for policy-authoring and promotion-rubric labor regardless.

| Level | Licensing | Operational labor | Run-rate |
|---|---|---|---|
| L2 | ~0 | ~0.1–0.25 FTE: allowlists, informal HITL | — |
| L3 | ~0 for an E5 incumbent (the Agent Governance Toolkit is MIT/OSS and Entra is in entitlements; Copilot Studio needs Copilot Credits or a Microsoft 365 Copilot license[^cslicensing]); AWS path is consumption-priced but small | the dominant cost: writing the decision-rights matrix and tier assignments per agent type, standing up the PDP, recurring policy review | negligible PDP eval cost (sub-millisecond) |
| L4 | ~0 incremental (MS) / small (AWS) | the dominant cost: the progressive-autonomy promotion rubric, HITL-coverage measurement, trifecta-breaker tuning, SoD pipeline separation | trifecta-breaker + JIT-elevation logging into the SIEM (couples to D7 ingest spend) |
| L5 | ~0 on Microsoft, where the agent step-down is the Agent Governance Toolkit's trust decay (OSS) | per-release policy-compile / no-drift discipline; crypto-SoD key management | step-up / anomaly-signal logging |
| L5+ | OSS (Cedar Analysis; per-task capability tokens ~0 license) | research-grade integration labor (capability-token integration; formal verification over MCP; CaMeL pilot) | — |

D3 licensing is near-zero through L4 for an incumbent; the dominant cost is policy-authoring and promotion-rubric labor.

The L3 labor line assumes tool access already exists as configuration the PDP can read. Where tool access was historically expressed in prompts alone, capability enforcement has to be reconstructed before it can be graded, and the Exchange records that retrofit as a stated difficulty of the control.[^aix-escape] Budget an inventory pass over prompt-declared tool access ahead of the PDP standup.

## Customer critiques folded in

- *"D3 today is L1–L2; informal HITL on writes."* Addressed: the recalibrated L3 (PDP + action-risk tiers + decision-rights matrix) is the near-term target, and an all-Microsoft shop reaches its decision point with no off-stack purchase. The Agent Governance Toolkit (OSS) hooks into the Microsoft Agent Framework's middleware pipeline and into agents built on Foundry Agent Service, and its own approval workflows carry the confirm tier for those agents.[^agt] Its launch post names no Copilot Studio integration, so a Copilot Studio agent's confirm tier rests on Copilot Studio's own approvals, whose multistage and AI approval stages are in preview.[^copilot] The tier record and the decision-rights matrix remain the organization's to write.
- *"L5 names just-GA'd products."* Addressed by capability-decoupling: D3-APPROVE-TOKEN states an approval token bound to the parameters a human approved, and D3-SOD-CRYPTO a deploying key that cannot approve itself, and neither names a product. Per-task scoped authorization with cryptographic binding is stated at L5+, where the cadence qualifier puts a capability with no production-hardened path in the tooling map above. The slow procurement cadence is the examiner-approved behavior.
- *"Microsoft is thin on per-task tokens and A2A authorization."* Confirmed and narrowed: the Agent Governance Toolkit's ToolPolicy adds declarative approval/justification guards but is not a holder-bound capability token. That is the genuine residual D3 gap, and it sits at L5+.
- *"Cost was invisible."* Addressed: licensing is near-zero through L4; the spend is decision-rights and promotion-rubric labor.

## Open questions

- Per-task holder-bound tokens sit at L5+ on the cadence qualifier. What would return them to L5 is a platform-native product, or production evidence for the open-source primitive from an organization that did not write it. The vault's reading of that primitive dates to August 2026 and records no general-availability declaration and no production deployment, although PyPI had carried release 0.2.0 since 2026-06-22 under the maintainers' classification "Production/Stable"; its reading of the company behind it dates to May 2026 and records the public examples as demo-shaped with case studies pending. Every Tenuo release since carries the same classification, 0.3.0 of 2026-09-11 included,[^tenuo-pypi] and the classification is the vendor's own, so it supplies no production evidence from an organization that did not write it. Re-check quarterly, with [[agentic-ai-security-cmm-d2-identity|D2]] and [[agentic-ai-security-cmm-d5-egress-network|D5]].
- Defender Predictive Shielding is a preview Defender XDR feature that restricts at-risk devices and user accounts during an attack,[^predshield] and [[standards-review-microsoft-zt4ai-2026-Q2|the 2026-Q2 ZT4AI review]] scopes it to devices, users and credentials rather than agent identities, naming the Agent Governance Toolkit's trust decay as the agent-specific step-down. Whether that trust decay, driven by the toolkit's own behavioral scores, meets the step-down half of D3-ADAPT, which names D7 anomaly scores, is open.
- Google ships a declarative access-policy engine for agents, IAM Unified Access Policies, generally available since 2026-08-31 and evaluated at Agent Gateway by Identity-Aware Proxy, with CEL conditions, an allow or a deny effect on each rule, rules of both effects in one policy, Principal Access Boundary on the agent identity, and a DRY_RUN mode ahead of ENFORCE.[^uap][^agentplatrn] The feature's overview states that it does not support VPC Service Controls,[^uap] while Google's release notes of 2026-09-09 record Agent Gateway enforcing perimeter rules on deployments created after 2026-09-08,[^agentplatrn] so whether the agent PDP and the egress perimeter compose on one deployment is unresolved. Whether this domain grades that composition or leaves it to [[agentic-ai-security-cmm-d5-egress-network|D5]] is an open calibration question. No Google approval-gate primitive is documented, so the HITL row above keeps its thin grade.
- The [[agentic-ai-security-cmm-crosswalk-us-fi|US Regulated-Finance Crosswalk]] maps D3 to FFIEC change control and information-security least privilege, lists least-agency and action authorization among the regulators' confirmed silences, and records that the model-risk guidance replacing SR 11-7 carves agentic AI out of its scope. A per-criterion mapping of the SoD and approval-gate criteria to FFIEC, GLBA or NCUA text stays open; the crosswalk carries none.
- Approval tiers are defined over action classes, and the attested agent–agent collusion case ran entirely inside authorized action classes. D8's D8-REPO-WRITE grades one instance at L4, write scoping on internal artifact repositories, and none of D4, D5 or D8 grades the general property. Whether D3 should grade *who else can observe an action's side effects* (a property of the medium rather than of the action) or leave that to D4, D5, or D8 is an open calibration question raised by the [[openai-hugging-face-agent-incident|OpenAI–Hugging Face agent incident]].
- A harness holding its own enforcement point produces every L3 artifact from the code path the policy governs, so the evidence carries no separation between the control and the report of it. [[agentic-ai-security-cmm-measurement-protocol|The measurement protocol]] narrows that with artifacts the harness does not write. Whether the assurance classes should carry a fourth class for a control the customer administers and the vendor interprets, or whether the named-artifact rule already covers it, is an open calibration question.
- The [[owasp-ai-exchange|OWASP AI Exchange]] asks for separate author, review and deploy roles over the artifacts that shape an agent's behaviour, its system prompt and configuration among them.[^aix-devtime] D3-SOD separates the three roles around a change an agent proposes, and D3-POLICY-REVIEW grades review of the decision point's policy. Whether D3 should also separate the three roles over an agent's own instructions, tools and grants, which D1-HARNESS-REVIEW, at D1 L3, covers only for a coding harness, is an open calibration question.

## D3→D4 dependency cap

The active rule set caps D4's effective score at D3's raw score (`effective(D4) ≤ raw(D3)`): runtime guardrails (D4 / PEP) can only enforce decisions a competent PDP (D3) actually makes. A program with strong D4 guardrails but no out-of-context PDP has its D4 effective score capped at the D3 level. For the persona (D4 raw L2–L3 from Prompt Shields and Groundedness, but D3 L1–L2), the cap pulls effective D4 down to roughly L1–L2. The cheapest high-leverage D4 investment is therefore standing up the PDP (D3-L3), which makes the already-owned guardrails load-bearing. See [[agentic-ai-security-cmm-dependency-rules|the dependency rules]].
